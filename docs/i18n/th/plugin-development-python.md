> **กลุ่มเป้าหมาย**: นักพัฒนาที่เขียนปลั๊กอินโปรเซสภายนอก (sidecar) ให้ SpeedMQ ด้วย Python
> **อ่านก่อน**: [คู่มือการพัฒนา ปลั๊กอินโปรเซสภายนอก (sidecar)](plugin-development.md) —— ที่นั่นอธิบายแบบจำลองทางความคิด ฟิลด์คอนฟิก และตารางสรุปโปรโตคอลสาย
> เอกสารนี้อธิบายเฉพาะ **วิธีลงมือทำด้วย Python** พร้อมขั้นตอนและผลลัพธ์ที่ทดสอบจริงบนเครื่องนี้
> **โปรเจกต์ตัวอย่าง**: เวิร์กสเปซ `speedmq-plugin/python/sidecar_plugin.py` (เฉพาะไลบรารีมาตรฐาน ไม่มีการพึ่งพาภายนอก)

## 1. ตอนรันมันเป็นอย่างไร

```
内核进程 ──dial(tcp 本机地址)──► 你的 Python 进程（sidecar.NewServer 的等价物：一个 TCP 服务端）
   ▲                                    │
   │  握手 / 心跳 / 控制面调用（JSON）      │
   │◄───────────────────────────────────┤  反向调用 core.authenticate / session.*（JSON）
   │      客户端字节流（原始字节，不 base64） │
   └────────────────────────────────────┘
```

สามประเด็นสำคัญ (มักเข้าใจผิด จดจำไว้ก่อน):

1. **โปรเซสของคุณคือเซิร์ฟเวอร์**: รับฟังที่อยู่ภายในเครื่องหนึ่ง แล้วรอเคอร์เนลมาเชื่อมต่อ (`plugins.<ชื่อ>.sidecar.address`)
2. **พอร์ตธุรกิจภายนอกเปิดโดยเคอร์เนล**: ไคลเอนต์เชื่อมต่อกับพอร์ตของเคอร์เนล ไบต์ถูกพร็อกซีมาให้คุณ (`protocols[].listeners`)
3. **`prefix` ต้องไม่ว่าง**: เคอร์เนลดักจับตามคำนำหน้าเพื่อตัดสินว่า "การเชื่อมต่อนี้ให้ใคร" `prefix` ว่างหมายถึง**ไม่มีส่วนในการดักจับ**
   การเชื่อมต่อบนตัวรับฟังของมันเองก็จะไม่ถูกส่งให้คุณ (ทดสอบจริง: การเชื่อมต่อจะถูกตัดทันที) ความยาวคำนำหน้า ≤ 8 ไบต์ ASCII

## 2. สามขั้นตอนให้รันขึ้น

### ขั้นที่หนึ่ง: ประกาศปลั๊กอินในคอนฟิก

`speedmqd.json` (**คอนฟิกจริงเป็น JSON มาตรฐาน ใส่คอมเมนต์ไม่ได้**):

```json
{
  "plugins": {
    "py-sidecar": {
      "builtin": false,
      "enabled": true,
      "sidecar": {
        "address": "tcp://127.0.0.1:19001",
        "spawn": ["python", "/opt/speedmq/sidecar_plugin.py", "-addr", "0.0.0.0:19001"],
        "protocols": [
          { "name": "pyecho", "prefix": "PY",
            "listeners": [{ "name": "pyecho", "addr": ":19002" }] }
        ]
      }
    }
  }
}
```

- `address` คือ**ที่อยู่ที่เคอร์เนลไปเชื่อมต่อหาคุณ** (เคอร์เนลเป็นไคลเอนต์ ปลั๊กอินเป็นเซิร์ฟเวอร์)
- `spawn` เว้นว่าง = เคอร์เนลเชื่อมต่ออย่างเดียวไม่ดึงขึ้นมา โปรเซสคุณจัดการเอง (systemd / supervisor / compose)
- `prefix` **ต้องไม่ว่าง**: ไบต์แรกที่ไคลเอนต์ส่งมาต้องขึ้นต้นด้วยค่านี้ (เคอร์เนลดักจับตามคำนำหน้าเพื่อตัดสินว่าส่งการเชื่อมต่อให้ใคร)
- `listeners` คือพอร์ตภายนอก เปิดโดยเคอร์เนล (ไคลเอนต์เชื่อมต่อกับเคอร์เนล ไม่ใช่คุณ)
- เมื่อดีพลอยข้ามคอนเทนเนอร์ `address` ใช้**ชื่อบริการ** (เช่น `tcp://py-sidecar:19001`) และปลั๊กอินต้องรับฟัง `0.0.0.0`

### ขั้นที่สอง: สตาร์ท

```bash
# 由内核 spawn 时不用手起；手动调试：
python sidecar_plugin.py -addr 0.0.0.0:19001 -name py-sidecar -session-demo
```

### ขั้นที่สาม: ตรวจสอบ

```bash
curl -u guest:guest http://127.0.0.1:15672/api/plugins | python -m json.tool   # state 应为 enabled
printf 'PYhello\n' | nc 127.0.0.1 19002                                       # 应回显 PYhello
```

## 3. ประเด็นการ implement

### 3.1 การแบ่งเฟรม (ชั้นไบต์เดียวที่คุณต้องเขียนให้ถูกเอง)

```
+--------+--------+------------------+
| len    | kind   | payload          |
| u32 BE | u8     | (len-1) 字节      |
+--------+--------+------------------+
len = 1 + len(payload)（长度字段**包含** kind 字节）；单帧上限 16 MiB。
```

เพย์โหลดของเฟรมข้อมูล = `4 ไบต์ big-endian หมายเลขสตรีม + ไบต์ดิบ`; เพย์โหลดของระนาบควบคุมเป็น JSON

```python
def read_frame(sock):
    head = read_exact(sock, 5)
    if len(head) < 5:
        return None
    (length,) = struct.unpack(">I", head[:4])
    payload = read_exact(sock, length - 1)
    return head[4], payload          # (kind, payload)
```

### 3.2 การจับมือและฮาร์ตบีต

หลังจากเคอร์เนลเชื่อมต่อ **จะส่ง Hello ก่อน** คุณต้องตอบกลับหนึ่งเฟรม `HelloAck`; เคอร์เนลจะตรวจสอบ
`name == ชื่อปลั๊กอินในคอนฟิก` และ `api_version == APIVersion ของเคอร์เนล` (ปัจจุบัน `v1`)
หลังจากนั้นเคอร์เนลจะส่ง `Ping` ทุก 2 วินาที คุณเพียงตอบ `Pong` (ไม่ตอบจะถูกตัดสินว่าตาย)

### 3.3 ลำดับตรรกะ

เมื่อ `kindOpen` มาถึง → **ตอบ `OpenAck` ก่อน** แล้วจึงเริ่มให้บริการ; เมื่อ `kindData` มาถึง → เขียนกลับตามเดิม (หรือตามที่แยกวิเคราะห์ด้วยโปรโตคอลของคุณ)
เป็น `kindData`; เมื่อประมวลผลเสร็จ → ส่ง `kindClose` หนึ่งสตรีม = หนึ่งการเชื่อมต่อไคลเอนต์

### 3.4 การเรียกย้อนกลับและบริดจ์ความหมายเชิงความหมายของเคอร์เนล

การเรียกจากปลั๊กอิน → เคอร์เนลใช้ `kindCall` และ `"reverse": true` เคอร์เนลตอบ `kindReply` บนการเชื่อมต่อเดียวกัน
**ลำดับสำคัญมาก**:

```
core.authenticate → session.open → session.declare_queue / publish / consume / …
```

`core.authenticate` **ข้ามไม่ได้**: ระนาบการดำเนินการของเคอร์เนลของการเชื่อมต่อไม่มีตัวตนก่อนการยืนยันตัวตน เรียก `session.open` ตรง ๆ จะถูกปฏิเสธ
(`ACCESS_REFUSED - access to vhost '/' refused for user ''`) พารามิเตอร์คือการตอบกลับ SASL ที่คุณแยกวิเคราะห์ได้จากโปรโตคอล:

```python
plain = b"\x00" + user.encode() + b"\x00" + password.encode()
ident = call("core.authenticate", {
    "stream": stream_id, "mechanism": "PLAIN",
    "response": base64.b64encode(plain).decode(),   # 字节在 JSON 里是 base64
})
# 拿到的会话与进程内协议插件完全同一套语义
call("session.open", {"stream": stream_id, "vhost": "/"})
q = call("session.declare_queue", {"stream": stream_id, "exclusive": True, "auto_delete": True})
call("session.publish", {"stream": stream_id, "routing_key": q["name"],
                         "message": {"body": base64.b64encode(b"hi").decode()}})
call("session.consume", {"stream": stream_id, "queue": q["name"], "prefetch": 32})
```

การนำส่งจากการบริโภคถูก**ดันกลับไปข้างหน้า**โดยเคอร์เนล (`kindCall`, `method = "session.deliver"`) เมื่อประมวลผลเสร็จให้ใช้
`session.settle` เคลียร์ (`ack` / `requeue` / `reject` หมายเลขการนำส่งไม่ซ้ำทั้งระบบ ไม่ต้องใช้หมายเลขสตรีม)

### 3.5 แบบจำลองการทำงานพร้อมกัน (ฉบับ Python)

| บทบาท | เธรด |
| --- | --- |
| ลูปอ่านเฟรม | หนึ่งตัวต่อการเชื่อมต่อเคอร์เนลหนึ่งรายการ |
| การประมวลผลสตรีม | หนึ่งตัวต่อสตรีม (จึงรองรับการเชื่อมต่อไคลเอนต์หลายรายการพร้อมกันได้) |
| การประมวลผลการเรียกไปข้างหน้า | หนึ่งตัวต่อการเรียกหนึ่งครั้ง |

**ต้องระวัง**: ในลูปอ่าน**ห้าม**รอการตอบกลับของการเรียกย้อนกลับแบบซิงโครนัส (จะเดดล็อก) —— การเรียกไปข้างหน้า (`session.deliver`)
ต้องโยนไปให้เธรดแยกประมวลผล เพราะระหว่างประมวลผลอาจต้องเรียก `session.settle` อีก การเขียนเฟรมต้องล็อกให้เป็นลำดับ

## 4. อ่านโค้ด (โปรเจกต์ตัวอย่าง)

`speedmq-plugin/python/sidecar_plugin.py` ประมาณ 320 บรรทัด ฟังก์ชันสำคัญ:

| ตำแหน่ง | หน้าที่ |
| --- | --- |
| `read_frame` / `Conn.send` | อ่าน-เขียนแบ่งเฟรม (คำนำหน้ายาว + kind) |
| `Conn.call` | การเรียกย้อนกลับ: หมายเลข → ส่ง → รอการตอบกลับ (จับคู่ด้วย `reverse=true` กับ `id`) |
| `Conn.serve` | ลูปอ่านเฟรมและการกระจาย |
| `Conn._handle_hello` | ตรวจสอบชื่อปลั๊กอิน/เวอร์ชัน API และตอบ HelloAck |
| `Conn._handle_open` / `_serve_stream` / `_echo` | วงจรชีวิตสตรีมและการสะท้อนกลับ |
| `Conn._dispatch` | ประมวลผลการเรียกไปข้างหน้า: `session.deliver` (รวม settle), `stats` |
| `Conn._session_demo` | ยืนยันตัวตน + ประกาศคิว + เผยแพร่ + บริโภค |

## 5. การทดสอบจริง (จำลองบนเครื่องนี้)

สภาพแวดล้อม: Windows + Python 3.12; เคอร์เนลรันบน Docker (`speedmq:1.1.01`) ปลั๊กอินรันบนโฮสต์
เคอร์เนลเชื่อมต่อด้วย `tcp://host.docker.internal:19001`

```
plugin=py-sidecar state=enabled           # /api/plugins
echo=[PYhello]                            # 客户端连内核端口 19002 发 "PYhello\n"

--- 插件 stdout ---
sidecar 已启动 plugin=py-sidecar addr=0.0.0.0:19001 version=0.1.0
内核已接入 plugin=py-sidecar peer=('127.0.0.1', 52864)
握手完成 plugin=py-sidecar kernel=1.1.01
认证通过 user=guest
session 演示完成 queue=amq.gen-9e5d0d695639bad12ce919
收到投递（session.deliver） queue=amq.gen-9e5d0d695639bad12ce919 delivery_id=1 body=hello from python sidecar
```

## 6. ข้อควรระวังเฉพาะของ Python

- **อย่าใช้ `time.sleep` รอฮาร์ตบีต**: ลูปอ่านเป็นแบบบล็อก อาศัย Ping ของเคอร์เนลในการคงการเชื่อมต่อก็พอ;
  หากตั้ง timeout การอ่านให้ socket อย่าลืมถือว่า timeout คือ "การเชื่อมต่อสิ้นสุด" (ตอนเคอร์เนล `kill -9` socket อาจไม่ปิดทันที)
- **`json.dumps` โดยค่าเริ่มต้นจะใส่ช่องว่าง**: ตัวอย่างใช้ `separators=(",", ":")` เพียงเพื่อให้ล็อกดูสวย โปรโตคอลเองไม่กำหนด
- **ไบต์คือ base64**: `message.body`, `core.authenticate.response` ใน JSON เป็นสตริง base64 ทั้งคู่
  อย่าลืม `base64.b64encode/decode`
- **การเขียนเฟรมต้องล็อก**: ฮาร์ตบีต การตอบกลับ บล็อกข้อมูลมาจากเธรดต่างกัน การเขียนสลับกันจะทำให้การเชื่อมต่อทั้งเส้นเสียหาย (ตัวอย่างใช้ `threading.Lock`)
- ใช้ `asyncio` ก็ได้ แต่ต้องรับประกันว่า "เขียนเป็นลำดับ + ลูปอ่านไม่บล็อก" แนวคิดเดียวกับฉบับเธรด

## 7. ขั้นสูง

- หากต้องการให้ปลั๊กอินมีหน้าจอจัดการของตัวเอง: เพิ่ม `console_url` ในคอนฟิก หน้า「การจัดการปลั๊กอิน」ของแบ็กเอนด์จัดการจะมีทางเข้าตรง
  (ดูเอกสารหลัก §5.8)
- ทำให้ปลั๊กอินเป็นบริการอิสระ จัดการโดย systemd / K8s: `spawn: []` + `restart: "never"` ให้ภายนอกดึงขึ้นมา
- ต้องการให้หลายโปรโตคอลอยู่ร่วมกัน: ให้ปลั๊กอินหลายตัวใช้ `prefix` ต่างกันบนตัวรับฟังเดียวกัน หรือเปิดพอร์ตเฉพาะแยกกัน
