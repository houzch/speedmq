## A. การยืนยันตัวตนและการควบคุมการเข้าถึง

### A-1. เปลี่ยนบัญชีเริ่มต้น `guest/guest` 【ยืนยันแล้ว】

- **ทำไม**: มี `guest/guest` ฝังในตัวเป็นค่าเริ่มต้น（แท็ก `administrator`）เปิดให้ภายนอกเข้าถึงก็เท่ากับเปิดประตูทิ้งไว้
- **ทำอย่างไร**: เปลี่ยนรหัสผ่าน / ลบบัญชีระหว่างรัน **อย่า**ไปแก้ไฟล์คอนฟิก（`users` มีผลแค่ตอน bootstrap ครั้งแรก）

```bash
# เปลี่ยนรหัสผ่าน
curl -u guest:guest -X PUT http://127.0.0.1:15672/api/users/guest \
     -H 'Content-Type: application/json' -d '{"password":"<รหัสผ่านใหม่>","tags":["administrator"]}'
# หรือลบบัญชีเริ่มต้นทิ้งไปเลย（ให้แน่ใจว่าสร้างผู้ดูแลใหม่ไว้ก่อนแล้ว）
curl -u guest:guest -X DELETE http://127.0.0.1:15672/api/users/guest
```

- **ตรวจสอบอย่างไร**: หลังแก้ รหัสผ่านเก่าต้องได้ 401 รหัสผ่านใหม่ต้องได้ 200
  **【ยืนยันแล้ว】** output จากการทดสอบจริงบนเครื่องนี้:

  ```
  --- 改密前 guest/guest ---          HTTP 200 {"auth_backend":"internal","name":"guest","tags":"administrator"}
  PUT /api/users/guest -> 204
  --- 改密后 guest/guest（应 401）---  HTTP 401
  --- 改密后 guest/s3cret（应 200）--- HTTP 200 {"auth_backend":"internal","name":"guest","tags":"administrator"}
  ```
- [ ] บัญชีเริ่มต้นเปลี่ยน/ลบแล้ว

### A-2. สิทธิ์น้อยที่สุด: regex `configure` / `write` / `read` ตาม vhost 【ยืนยันแล้ว】

- **ทำไม**: สามหมวดจัดให้ตรงกับ RabbitMQ —— `configure` คุมการประกาศ/ลบโทโพโลยี、`write` คุมการเผยแพร่และ binding、`read` คุมการบริโภคและการดึง;
  เกินสิทธิ์จะคืน 403 ให้บัญชีธุรกิจเปิดเฉพาะที่จำเป็น
- **ทำอย่างไร**: `PUT /api/permissions/{vhost}/{user}` เช่นอ่าน-บริโภคอย่างเดียว: `{"configure":"^$","write":"^$","read":".*"}`

```bash
curl -u guest:guest -X PUT http://127.0.0.1:15672/api/permissions/%2F/appuser \
     -H 'Content-Type: application/json' -d '{"configure":"^$","write":"^$","read":".*"}'
```

- **ตรวจสอบอย่างไร**: ใช้บัญชีที่จำกัดสิทธิ์ลองทำสิ่งที่เกินสิทธิ์ ควรได้ 403 `ACCESS_REFUSED`
  **【ยืนยันแล้ว】** บนเครื่องนี้ใช้ไคลเอนต์ AMQP จริงที่ผู้ใช้มี `configure="^$"` ประกาศเอ็กซ์เชนจ์ จากการทดสอบจริง:

  ```
  FAIL 声明 durable 交换机失败: Exception (403) Reason: "ACCESS_REFUSED - access to configure 'r.ex' refused for user 'restricted'"
  ```
- [ ] บัญชีธุรกิจแต่ละบัญชีให้เฉพาะ regex ที่จำเป็น และไม่ได้ให้แท็ก `administrator`/`management`

### A-3. หลักเกณฑ์ของแท็ก `administrator`（สิทธิ์เต็มโดยนัย）—— ให้อย่างระมัดระวัง 【ยืนยันแล้ว】

- **ทำไม**: **ผู้ใช้ที่มีแท็ก `administrator` มีสิทธิ์เต็มต่อทุก vhost ที่มองเห็น โดยไม่ต้องมีเรกคอร์ดสิทธิ์**
  （จัดให้ตรงกับหลักเกณฑ์ที่ทดสอบจริงของ RabbitMQ ดู README / การออกแบบ M8-7）กล่าวคือเพียงให้แท็กนี้
  regex สิทธิ์ก็ไม่ทำงานอีกต่อไป——มันคือสิทธิ์สูงสุด
- **ทำอย่างไร**: ให้ `administrator` เฉพาะบัญชีฝ่ายจัดการ/ปฏิบัติการ; บัญชีธุรกิจไม่ให้แท็กเลย ใช้เฉพาะ regex สิทธิ์

- **ตรวจสอบอย่างไร（สาธิตสิทธิ์โดยนัย）**: สำหรับ vhost ใหม่ที่**ไม่มีเรกคอร์ดสิทธิ์เลย** ผู้ใช้ `administrator` ควรใช้ได้ทันที
  **【ยืนยันแล้ว】** จากการทดสอบจริงบนเครื่องนี้: หลังสร้าง vhost `drillvh` ใหม่（ยังไม่สร้างเรกคอร์ดสิทธิ์ใด ๆ）`guest`（administrator）ประกาศโทโพโลยีบนนั้นสำเร็จ:

  ```
  --- administrator 隐式权限：guest 在 drillvh 上声明拓扑 ---
  OK  已声明 durable 交换机 a.ex / 队列 a.q，并绑定 key=k   (exit=0)
  ```
- [ ] แท็ก `administrator` ให้เฉพาะบัญชีปฏิบัติการส่วนน้อยเท่านั้น

### A-4. `remote_access`: จำกัดบัญชีให้เข้าสู่ระบบได้เฉพาะเครื่องเดียวกัน 【ยังไม่ได้ยืนยัน（เครื่องเดียวจำลองต้นทางระยะไกลไม่ได้）】

- **ทำไม**: จัดให้ตรงกับ RabbitMQ บัญชี `guest` ในตัวจำกัดให้เข้าสู่ระบบเฉพาะเครื่องเดียวกันเป็นค่าเริ่มต้น; เวลาติดตั้งให้ภายนอกควรทำให้แน่ใจว่าต้นทางของบัญชีสิทธิพิเศษถูกจำกัด
- **ทำอย่างไร / หลักเกณฑ์（ข้อจำกัดสำคัญ）**:
  - `remote_access` เขียนได้เฉพาะใน `users.<name>.remote_access` ของ**ไฟล์คอนฟิก** **มีผลแค่ตอน bootstrap ครั้งแรก**;
  - **บัญชีที่สร้างผ่าน API ฝ่ายจัดการ / `swiftmqctl` จะเป็น `remote_access=true` เสมอ**（อนุญาตให้เข้าสู่ระบบจากต้นทางใดก็ได้）——
    หลักฐาน: คอมเมนต์ `UpsertUser` ของ `internal/broker/observe.go` และจากการทดสอบจริงใน `meta/state.json` มี
    `"remote_access":true`。กล่าวคือ**ตอนนี้ API ไม่สามารถจำกัดบัญชีใดบัญชีหนึ่งให้เข้าสู่ระบบเฉพาะเครื่องเดียวกันได้**
- **ตรวจสอบอย่างไร**: จาก**โฮสต์อีกเครื่อง**（ที่ไม่ใช่ `127.0.0.1`）ใช้บัญชีนั้นเชื่อมต่อ ควรถูกปฏิเสธด้วย 403; เชื่อมต่อจากเครื่องเดียวกันควรสำเร็จ
  **【ยังไม่ได้ยืนยัน】**: สภาพแวดล้อมของเครื่องนี้สร้างต้นทางระยะไกลจริงไม่ได้ ยังไม่ได้ทดสอบจริง
- [ ] ประเมินข้อจำกัดต้นทางของบัญชีสิทธิพิเศษตามหลักเกณฑ์ข้างต้นแล้ว（ระวัง: บัญชีที่สร้างผ่าน API จะเปิดการเข้าถึงระยะไกลเป็นค่าเริ่มต้น）

## B. ความปลอดภัยในการส่ง（TLS）

รายการคอนฟิก TLS（ชั้นเชื่อมต่อและฝ่ายจัดการ**ใช้ฟิลด์ชุดเดียวกัน**）: `cert_file` / `key_file` / `ca_file` / `client_auth` / `min_version`

### B-1. เปิด TLS และถ้าตั้งค่าผิดจะปฏิเสธการสตาร์ท 【ยืนยันแล้ว】

- **ทำไม**: ใบรับรองถูกอ่านและตรวจสอบ**ตอนสตาร์ท**——ตั้งผิดจะปฏิเสธการสตาร์ททันที ไม่ใช่รอให้ไคลเอนต์ตัวแรกเชื่อมต่อเข้ามาจึงเปิดเผย
- **ทำอย่างไร**: ระบุ `cert_file` + `key_file` ใน `listeners.<plugin>[].tls` หรือ `management.tls`（**ให้ทั้งคู่**จึงเปิด）

- **ตรวจสอบอย่างไร**: สตาร์ทด้วยคอนฟิกที่ผิด ควรล้มเหลวทันที
  **【ยืนยันแล้ว】** ทดสอบจริงคอนฟิกผิดสามแบบบนเครื่องนี้ ทั้งหมด `exit=1` ปฏิเสธการสตาร์ท:

  ```
  badtls1: swiftmqd 启动失败: listeners.amqp091[0].tls 需要同时提供 cert_file 与 key_file
  badtls2: swiftmqd 启动失败: listeners.amqp091[0].tls.min_version 取值非法: "1.0"（可选 1.2 / 1.3）
  badtls3: swiftmqd 启动失败: listeners.amqp091[0].tls 无效: 加载服务端证书失败（cert=... key=...）: open ...: The system cannot find the path specified.
  ```
- **ตรวจสอบอย่างไร（ทางบวก/ทางลบ）**: ไคลเอนต์ TLS เชื่อมต่อได้ ไคลเอนต์แบบข้อความล้วนที่เชื่อมต่อพอร์ต TLS จะถูกปฏิเสธ
  **【ยืนยันแล้ว】** บนเครื่องนี้สตาร์ทอินสแตนซ์ TLS（`amqp091` ใช้ TLS）ด้วยโพรบไคลเอนต์จริง:

  ```
  === 正向：TLS 客户端跑全量探针 ===      全部通过（25/25）: ...
  === 反向：明文客户端连 TLS 端口（应失败）===  FAIL ... 拨号失败: Exception (501) Reason: "EOF"   (exit=-1)
  ```
- [ ] พอร์ตโปรโตคอลที่เปิดให้ภายนอกเปิดใช้ TLS แล้ว

### B-2. `min_version` อย่างน้อย 1.2 【ยืนยันแล้ว】

- **ทำไม**: ปิดใช้งาน TLS เวอร์ชันเก่าเกินไป; ค่าเริ่มต้นคือ `1.2` เลือกได้ `1.2` / `1.3`
- **ตรวจสอบอย่างไร**: เขียน `min_version` เป็น `1.0` การสตาร์ทควร error（ดู output `badtls2` ของ B-1）
- [ ] `min_version` เป็น `1.2` หรือ `1.3`

### B-3. การยืนยันตัวตนสองทาง `client_auth: require_and_verify`（mTLS） 【ยืนยันบางส่วน】

- **ทำไม**: กำหนดให้ไคลเอนต์แสดงและยืนยันใบรับรอง ป้องกันไคลเอนต์ที่ไม่ได้รับอนุญาตเชื่อมต่อพอร์ตโปรโตคอล
- **ทำอย่างไร**: ตั้ง `ca_file` + `client_auth: require_and_verify`（สองตัวหลังกำหนดให้ระบุ `ca_file` พร้อมกัน）
- **【ยืนยันแล้ว】**: เส้นทาง TLS แบบ end-to-end และเส้นทางที่ถูกปฏิเสธยืนยันด้วยไคลเอนต์จริงแล้ว（B-1）**ส่วน mTLS（กำหนดให้และตรวจสอบใบรับรองไคลเอนต์）เครื่องนี้ยังไม่ได้ซ้อมแยกต่างหาก**
- [ ] พอร์ตที่ต้องใช้ mTLS ตั้ง `require_and_verify` + `ca_file` แล้ว

### B-4. TLS ของฝ่ายจัดการ 【ยังไม่ได้ยืนยัน】

- **ทำไม**: ฝ่ายจัดการส่งรหัสผ่านผ่าน Basic Auth ต้องเข้ารหัส
- **ทำอย่างไร**: `management.tls` ใช้ฟิลด์เดียวกับตัวรับฟังโปรโตคอล
- **【ยังไม่ได้ยืนยัน】**: การซ้อมบนเครื่องนี้ผูกฝ่ายจัดการกับพอร์ตข้อความล้วนของเครื่องเดียวกัน ยังไม่ได้สตาร์ท HTTPS ฝ่ายจัดการแยกต่างหาก
- [ ] ฝ่ายจัดการเปิดใช้ TLS แล้ว（หรือจำกัดในเครือข่ายที่เชื่อถือได้อย่างเข้มงวด）

## C. การลดพื้นที่เสี่ยงจากการเปิดเผย

### C-1. ลดขอบเขตการรับฟังของฝ่ายจัดการ 【ยืนยันแล้ว（ทดสอบที่อยู่รับฟังจริง）】

- **ทำไม**: ฝ่ายจัดการค่าเริ่มต้นคือ `:15672`（ทุกการ์ดเครือข่าย）เวลาติดตั้งให้ภายนอกควรผูกกับที่อยู่ภายใน/loopback หรือใช้ไฟร์วอลล์จำกัดต้นทาง
- **ทำอย่างไร**: ตั้ง `management.addr` เป็น `127.0.0.1:15672` หรือที่อยู่ภายใน; หรือตั้ง `management.enabled=false` ปิดไปเลย
  （หลังปิดจะไม่มีพอร์ตจัดการ แต่ `swiftmqctl` ก็ใช้ไม่ได้ตามไปด้วย）
- **ตรวจสอบอย่างไร**:
  **【ยืนยันแล้ว】** บนเครื่องนี้ตั้งฝ่ายจัดการเป็น `127.0.0.1:15677` จากการทดสอบจริงที่อยู่รับฟังเป็น loopback:

  ```
  LocalAddress LocalPort
  ------------ ---------
  127.0.0.1        15677
  ```
- [ ] ที่อยู่ binding ของฝ่ายจัดการลดขอบเขตแล้ว（หรือปิดใช้งานแล้ว）

### C-2. เปิดเฉพาะพอร์ตโปรโตคอลที่จำเป็น 【ยังไม่ได้ยืนยัน】

- **ทำไม**: ค่าเริ่มต้นเปิดทั้ง AMQP `5672` และ MQTT `1883` พร้อมกัน; ถ้าไม่ใช้ MQTT ก็ปิดเสีย ลดพื้นที่โจมตี
- **ทำอย่างไร**: `plugins.mqtt.enabled=false`（หรือเอาออกจาก `listeners`）; การปิดใช้งานคือ**ปิดพอร์ตจริง** ไม่ใช่แค่เปลี่ยนบิตสถานะ
- **ตรวจสอบอย่างไร**: หลังปิดใช้งาน พอร์ตที่เกี่ยวข้องไม่รับฟังอีก（`Get-NetTCPConnection -State Listen` มองไม่เห็น）
  **【ยังไม่ได้ยืนยัน】**: การซ้อมบนเครื่องนี้เปิดทั้งสองโปรโตคอล ยังไม่ได้ยืนยันแยกต่างหากว่าหลังปิดแล้วพอร์ตหายไป
- [ ] ปิดใช้งานปลั๊กอินโปรโตคอลที่ไม่ได้ใช้แล้ว

## D. การเสริมความปลอดภัยในการรันคอนเทนเนอร์

ข้อเท็จจริงของอิมเมจใน repository（`Dockerfile`）: ไบนารีลิงก์แบบ static + alpine **รันแบบไม่ใช่ root（uid 10001 ผู้ใช้ `swiftmq`）**
ไดเรกทอรีข้อมูล `/var/lib/swiftmq` เป็น volume `docker-compose.yml` ใช้**named volume** ทำให้คงทน、คอนฟิก**mount แบบอ่านอย่างเดียว**、หมุน log

### D-1. รันแบบไม่ใช่ root 【ยังไม่ได้ยืนยัน（เครื่องนี้ยังไม่ได้รัน Docker）】

- **ทำไม**: สิทธิ์น้อยที่สุด ลดขอบเขตผลกระทบหากคอนเทนเนอร์ถูก escape
- **ทำอย่างไร**: อิมเมจเป็น uid 10001 อยู่แล้วโดยค่าเริ่มต้น; **อย่า**ใช้ `--user root` เขียนทับ
- **ตรวจสอบอย่างไร**: `docker compose run -T --rm broker id` ควรแสดง `uid=10001`。（`run` ในสภาพแวดล้อมไม่โต้ตอบต้องเติม `-T`）
- [ ] คอนเทนเนอร์รันแบบไม่ใช่ root（ไม่ได้เขียนทับด้วย root）

### D-2. ระบบไฟล์รากแบบอ่านอย่างเดียว + การจำกัดทรัพยากร + การตัด capabilities（ข้อเสนอแนะ compose ของ repository ยังไม่เปิดเป็นค่าเริ่มต้น） 【ยังไม่ได้ยืนยัน】

- **ทำไม**: ระบบไฟล์รากแบบอ่านอย่างเดียวสามารถขัดขวางการแก้ไบนารีระหว่างรัน; การจำกัดทรัพยากรกันคอนเทนเนอร์เดียวถ่วงโฮสต์; การตัด capabilities ลดพื้นที่โจมตีของ kernel
- **ทำอย่างไร**（ตัวอย่าง ผสานเข้าเซอร์วิส `broker` ของ compose ตามต้องการ）:

```yaml
services:
  broker:
    read_only: true
    tmpfs:
      - /tmp
    security_opt:
      - no-new-privileges:true
    cap_drop: ["ALL"]
    deploy:
      resources:
        limits:
          cpus: "4"
          memory: 8g
```

- **ตรวจสอบอย่างไร**: ในคอนเทนเนอร์ลองเขียนเส้นทางรากควรล้มเหลว（อ่านอย่างเดียว）; `docker inspect` เห็นการจำกัดทรัพยากร
  **【ยังไม่ได้ยืนยัน】**（เครื่องนี้ยังไม่ได้รัน Docker）; และ**ระบบไฟล์รากแบบอ่านอย่างเดียวต้องยืนยันว่า `data_dir` อยู่บน volume ที่เขียนได้** ไม่งั้น kernel เขียนลงดิสก์ไม่ได้
- [ ] ประเมินระบบไฟล์รากแบบอ่านอย่างเดียวและการจำกัดทรัพยากรแล้ว（ระวัง `data_dir` ต้องอยู่บน volume ที่เขียนได้）

## E. ข้อจำกัดที่ทราบ（ตอนนี้ทำไม่ได้จริง อย่าไปคาดหวัง）

ต่อไปนี้ล้วนเป็น**ช่องว่างเชิงข้อเท็จจริง** โปรดยอมรับอย่างชัดเจนในงานออกแบบความปลอดภัย อย่าสมมติว่ามันมีอยู่:

1. **รหัสผ่านถูกจัดเก็บและคัดลอกเป็นข้อความล้วน** ฟิลด์ `password` ใน `meta/state.json` เป็นข้อความล้วน（**【ยืนยันแล้ว】** จากการทดสอบจริงเห็น
   `"password":"drillpass"`）; ในไฟล์คอนฟิกก็เป็นข้อความล้วน **ไม่มี**การแฮชรหัสผ่าน（การแฮชและ backend การยืนยันภายนอกเว้นไว้ให้ปลั๊กอินยืนยัน）
   → ผลที่ตามมา: **ไดเรกทอรีข้อมูลและไฟล์สำรองเทียบเท่าข้อมูลรับรองอ่อนไหว** ต้องทำการป้องกันด้วยสิทธิ์ไฟล์และการเข้ารหัส
2. **ไม่มี audit log** การเพิ่ม-ลบ-แก้ของฝ่ายจัดการจะพิมพ์ log ปกติ（เช่น `管理面更新用户 actor=... user=...`）
   แต่**ไม่มี**สตรีมตรวจสอบแยกต่างหากที่ดัดแปลงไม่ได้ และไม่มีบันทึกระดับ compliance ว่า「ใครแก้อะไรเมื่อไหร่」
3. **ไม่มีการยืนยันภายนอกเช่น LDAP / OAuth2 / JWT** v1 ในตัวมีเพียง `PLAIN` / `AMQPLAIN`
   （จากการทดสอบจริง `auth.Store.Mechanisms()` คืนเพียงสองตัวนี้）
4. **SASL `EXTERNAL` ยังไม่ถูกนำมาใช้**: แม้ตั้ง mTLS แล้ว ชั้นโปรโตคอล**ยังใช้การยืนยันด้วยรหัสผ่าน PLAIN**
   （ขั้นตอน「ใช้ใบรับรองไคลเอนต์เพื่อไม่ต้องใช้รหัสผ่าน」ยังไม่มี）ใบรับรองเป็นเพียงการตรวจสอบชั้นการส่ง
5. **`remote_access` ตั้งผ่าน API ไม่ได้**: บัญชีที่สร้างโดย API/CLI ฝ่ายจัดการจะอนุญาตการเข้าสู่ระบบระยะไกลเสมอ（ดู A-4）
   ไม่สามารถจำกัดบัญชีเดียวให้เข้าสู่ระบบเฉพาะเครื่องเดียวกันได้
6. **ฝ่ายจัดการไม่มี whitelist ต้นทางแยกต่างหาก / ไม่มี rate limit**: ทำได้เพียงอาศัยที่อยู่ binding、ไฟร์วอลล์、TLS เพื่อลดพื้นที่เปิดเผย
7. **ไม่มี sandbox ปลั๊กอิน**: ปลั๊กอินรูปแบบ A อยู่โปรเซสเดียวกับ kernel; ปลั๊กอินภายนอกรูปแบบ B แม้มีการแยกโปรเซส แต่**ระนาบข้อมูลผ่านพร็อกซีการเชื่อมต่อของเครื่องเดียวกัน**
   และปลั๊กอินเรียกใช้ความหมายของ kernel ได้（ถูกจำกัดด้วย vhost และการตรวจสอบสิทธิ์）**ไม่ใช่** sandbox ความปลอดภัย
8. **แท็กของฝ่ายจัดการมีเพียงสามระดับ `administrator`/`management`/`monitoring`** ไม่มี RBAC ระดับ per-resource ที่ละเอียดกว่า
