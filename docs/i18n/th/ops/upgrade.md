# SpeedMQ แนวทางการอัปเกรดและการย้ายระบบ

> เวอร์ชันที่ใช้ได้: `1.0.0`（`broker.Version` ดูที่ `speedmq_build_info` ของ `/metrics`）
> ข้อสรุปจาก「การทดสอบจริง」ทั้งหมดในเอกสารนี้มาจากการรันจริงบนเครื่องนี้; ส่วนที่ยังไม่ได้ทดสอบจริงจะถูกระบุชัดเจนว่า**【ยังไม่ได้ยืนยัน】**
> สภาพแวดล้อมของเครื่องนี้: Windows + PowerShell 5.1, Go 1.27.1 windows/386, `data_dir` ชั่วคราว + พอร์ตที่ไม่ใช่ค่าเริ่มต้น

---

## 1. การย้ายระบบ（เปลี่ยนจาก RabbitMQ มาเป็น SpeedMQ）

จุดยืนของโปรเจกต์นี้คือ**ความเข้ากันได้ระดับโปรโตคอล AMQP 0-9-1** ดังนั้น「การย้ายระบบ」จึงเน้นที่**เปลี่ยนที่อยู่ที่เชื่อมต่อ**เป็นหลัก:

- โค้ดธุรกิจไม่ต้องแก้เลย เพียงเปลี่ยน `host/port/vhost`（เอกสารออกแบบ G3「ย้ายระบบต้นทุนศูนย์」）
- เครื่องมือจัดการ（`rabbitmqadmin`、UI จัดการ、สคริปต์มอนิเตอร์）ชี้ไปที่พอร์ตฝ่ายจัดการก็ใช้ได้ รูปแบบอินเทอร์เฟซจัดให้ตรงกับ RabbitMQ（`amq.default`、`%2F`、`{error, reason}` เป็นต้นทำตามข้อตกลงเดิม）
- พอร์ตเริ่มต้นเหมือนกับ RabbitMQ: AMQP `5672`、ฝ่ายจัดการ `15672`; MQTT เป็น `1883`、RPC ระหว่างโหนดเป็น `25672`

**ความแตกต่างเชิงความหมายที่ต้องตรวจสอบด้วยตัวเองก่อนย้ายระบบ**（ทั้งหมดเป็นเจตนาของ repository นี้ อ้างอิง README / เอกสารออกแบบ）:

| รายการ | พฤติกรรมของ SpeedMQ | ผลกระทบต่อการย้ายระบบ |
| --- | --- | --- |
| คิวชั่วคราว（ไม่คงทนและไม่ exclusive） | **ปฏิเสธการประกาศ**（541）`auto_delete` ไม่ได้รับการยกเว้น | ไคลเอนต์เก่าที่พึ่งพาคิวประเภทนี้จะล้มเหลว ต้องเปลี่ยนเป็น durable หรือ exclusive |
| vhost เริ่มต้น `/` | **ลบไม่ได้**（400）RabbitMQ อนุญาต | สคริปต์อัตโนมัติถ้าลบ vhost เริ่มต้นจะล้มเหลว（นี่คือข้อจำกัดด้านความปลอดภัยเชิงรุกเพียงข้อเดียว） |
| ข้อมูล classic queue | **ไม่จำลอง** ข้อมูลอยู่ที่โหนด Owner เท่านั้น | ถ้าต้องการสำรองซ้ำข้ามโหนดให้เปลี่ยนไปใช้ quorum queue `x-queue-type=quorum` |
| quorum queue | รองรับการเพิ่ม replica **ไม่รองรับการลดขนาด** | ต้องวางแผนให้ครบตั้งแต่แรก |
| ปลั๊กอิน | ไม่มีระบบนิเวศปลั๊กอิน Erlang, AMQP 1.0 / STOMP ยังไม่ถูกนำมาใช้ | สถานการณ์ที่ใช้โปรโตคอลเหล่านี้ยังย้ายไม่ได้ในตอนนี้ |

**การย้ายข้อมูล**: รูปแบบการจัดเก็บของ SpeedMQ กับ RabbitMQ ไม่เข้ากัน **ไม่มีเครื่องมือขนย้ายข้อมูลแบบออนไลน์/ออฟไลน์**
วิธีการย้ายคือ「สร้าง SpeedMQ เปล่าใหม่ → รันคู่ขนานเพื่อตรวจสอบ → สลับทราฟฟิกแบบค่อยเป็นค่อยไป」。**【ยังไม่ได้ยืนยัน】** เอกสารนี้ไม่มีการซ้อมขนย้ายข้อมูล RabbitMQ จริงใด ๆ

## 2. หลักการโดยรวมของการอัปเกรด

1. **สำรองก่อน**（ดู `backup-restore.md`）——เป็นหลักประกันสำหรับกรณีอัปเกรดล้มเหลว
2. **หยุดโปรเซสก่อนแล้วค่อยเปลี่ยน**（ไดเรกทอรีข้อมูลมีข้อกำหนดผู้เขียนคนเดียว ดู §4.2）
3. **หลังอัปเกรดต้องตรวจสอบ**: โปรเซสสตาร์ทได้、`/api/overview` อ่านได้、`/metrics` ดึงได้、จำนวนข้อความในคิวตรงกับก่อนสำรอง
4. การอัปเกรดคลัสเตอร์**หมุนทีละโหนด** ครั้งละหนึ่งโหนด（ดู §5）

## 3. โครงสร้างไดเรกทอรีข้อมูล（หลักฐานข้อเท็จจริงสำหรับการอัปเกรด/ย้ายระบบ）

โครงสร้าง `data_dir` ที่ได้จาก**การทดสอบจริง**บนอินสแตนซ์เครื่องเดียวของเครื่องนี้:

```
data/
├── meta/
│   ├── state.json        # snapshot metadata ของโหมดเครื่องเดียว（vhost/เอ็กซ์เชนจ์/คิว/binding/ผู้ใช้/สิทธิ์/นโยบาย）
│   ├── users.seeded      # เครื่องหมาย bootstrap: users ในไฟล์คอนฟิกถูกเพาะแล้ว
│   ├── vhosts.seeded     # เครื่องหมาย bootstrap: vhosts ในไฟล์คอนฟิกถูกเพาะแล้ว
│   ├── raft.state        # 【โหมดคลัสเตอร์】วาระ/การลงคะแนนของ Raft
│   ├── raft.log          # 【โหมดคลัสเตอร์】Raft log
│   └── snapshot.json     # 【โหมดคลัสเตอร์】Raft snapshot + ตารางสมาชิก
├── msg_stores/vhosts/<safe(vhost)>/queues/<safe(queue)>/
│   ├── 000001.seg        # ไฟล์ segment（เนื้อความข้อความ + แอตทริบิวต์）รูปแบบเรกคอร์ด: <len u32><crc32 u32><payload>
│   └── index/000001.idx  # ดัชนีคิว: seq-id → (หมายเลข segment, offset ใน segment, ความยาว, สถานะ)
└── quorum/<safe(vhost)>/<safe(queue)>/   # 【คลัสเตอร์】quorum queue หนึ่งคิวมีหนึ่งกลุ่ม Raft（log/snapshot）
```

**ข้อควรระวัง（สองจุดที่ต่างจากสัญชาตญาณ ยึดตามโค้ด/การทดสอบจริงทั้งคู่）**:

- ในโหมดคลัสเตอร์ ไฟล์ที่ Raft ทำให้คงทน**วางไว้ใต้ `meta/` โดยตรง**（`raft.state` / `raft.log` / `snapshot.json`）
  **ไม่มีไดเรกทอรีย่อย `meta/raft/`**。หลักฐาน: ค่าคงที่ชื่อไฟล์ของ `internal/raft/log.go` + ใน `internal/broker/cluster.go`
  ที่ `Dir: filepath.Join(b.cfg.DataDir, "meta")`。**【ยังไม่ได้ทดสอบโครงสร้างคลัสเตอร์】**（เครื่องนี้รันเฉพาะอินสแตนซ์เครื่องเดียว）
- ชื่อไดเรกทอรี**ไม่ใช่ชื่อ vhost / คิวเดิม** แต่เป็นชื่อที่เข้ารหัสโดย `store.SafeDirName`: เติมคำนำหน้า `q_` ไบต์ที่ไม่ใช่ `[A-Za-z0-9._-]` จะถูก escape เป็น `%XX`
  จากการทดสอบจริง: vhost `/` → ไดเรกทอรี `q_%2F`、คิว `persist.q` → ไดเรกทอรี `q_persist.q`
  ที่ออกแบบเช่นนี้เพื่อหลีกเลี่ยง path traversal และชื่ออุปกรณ์สงวนของ Windows（`con`/`nul` เป็นต้น）

## 4. ความเข้ากันได้ของข้อมูล

### 4.1 ข้อมูลเก่าอ่านได้โดยตรงหรือไม่——ได้

- **รูปแบบดัชนีเข้ากันได้ไปข้างหน้า**: M8-1 เพิ่มฟิลด์「หมายเลข segment」ลงในเรกคอร์ดดัชนี（25 ไบต์）;**รูปแบบเก่า（21 ไบต์ ไม่มีหมายเลข segment）ยังอ่านได้ตามเดิม**
  ตอนอ่านจะเทียบเท่ากับ「มีเพียง segment เดียว（seg=1）」**การอัปเกรดไม่ต้องใช้สคริปต์ย้ายข้อมูล**
  หลักฐาน: ค่าคงที่ `indexEntrySize` / `legacyIndexEntrySize` และตรรกะ `recover()` ของ `internal/store/store.go`; README M8-1
- **ความหมายเวลาล่มไม่เปลี่ยน**: แต่ละเรกคอร์ดมีความยาวนำหน้า + CRC32 ตอนกู้คืนจะ**ทิ้งเรกคอร์ดที่เขียนค้างท้ายไฟล์/เสียหาย**และตัดปลาย
  จากการทดสอบจริง（ดู `backup-restore.md` §6）: หลังหยุดโปรเซสแล้วรีสตาร์ท ข้อความคงทน 5 ข้อความของ durable queue **กู้คืนได้ทั้งหมด**
  log ปรากฏ `已从磁盘恢复队列消息 ... messages=5`

### 4.2 หลักเกณฑ์ของ `vhosts` / `users` ในคอนฟิก（จุดที่พลาดง่ายที่สุดตอนอัปเกรด）

- ทั้งสอง**มีผลแค่ตอน bootstrap ครั้งแรกเท่านั้น**: การสตาร์ทครั้งแรกจะเขียน vhosts/users ในคอนฟิกลงใน metadata และทิ้งไฟล์เครื่องหมาย
  `meta/vhosts.seeded` / `meta/users.seeded`; **หลังจากนั้นยึด metadata เป็นหลัก**
- ดังนั้น**ตอนอัปเกรด/เปลี่ยนคอนฟิก อย่าหวังว่าจะเพิ่ม-ลบบัญชีหรือ vhost ด้วยการแก้ไฟล์คอนฟิก**——แก้ไปก็ไม่มีผล
  โปรดใช้ API ฝ่ายจัดการหรือ `speedmqctl`
- ในทางกลับกัน การอัปเกรด**จะไม่**ใช้คอนฟิกเขียนทับบัญชีที่มีอยู่: รหัสผ่านที่แก้ระหว่างรันจะไม่ถูกดึงกลับไปเป็นค่าเก่าในคอนฟิกตอนรีสตาร์ท
  และบัญชีที่ลบระหว่างรันก็จะไม่กลับมา หลักฐาน: ตรรกะเครื่องหมายเพาะของ `cluster.go`; README M8-4 / M8-7

### 4.3 การหมุน segment และการเก็บคืนพื้นที่ดิสก์

- ข้อความถูกแบ่งเป็น segment ตามขนาด（ค่าเริ่มต้น 8 MiB）**เมื่อข้อความใน segment ถูก ack ทั้งหมดและ segment ถูกปิดผนึกแล้วจะลบทั้ง segment** และบีบอัดเขียนดัชนีใหม่ตามไปด้วย
- การอัปเกรดไม่เปลี่ยนพฤติกรรมนี้; ไฟล์ segment เดียวที่อินสแตนซ์เก่าทิ้งไว้จะทำงานได้ตามปกติภายใต้ตรรกะหมุน segment ใหม่

## 5. การอัปเกรดไบนารี（เครื่องเปล่า）

> เครื่องนี้**ยังไม่ได้ซ้อมข้ามเวอร์ชันบนเครื่องจริง**（repository ปัจจุบันมีเวอร์ชันเดียวคือ `1.0.0` ไม่มีไบนารีเก่าให้อัปเกรด）ขั้นตอนด้านล่างคือ**การตรวจสอบซ้ำด้วยเวอร์ชันเดียวกัน + กระบวนการทั่วไป**ตามความสามารถที่ repository นี้มีอยู่ ส่วนที่ข้ามเวอร์ชันจะระบุ **【ยังไม่ได้ยืนยัน】**

### 5.1 ขั้นตอน

```powershell
$base = "C:\speedmq"
$data = "$base\data"

# 1) หยุดโปรเซส（ออกอย่างสง่างามจะ flush เก็บงาน; ดู §4「ความสอดคล้อง」）
#    ถ้ารันแบบ foreground: Ctrl+C; ถ้าแบบ service: Stop-Service / Stop-Process
Stop-Process -Name speedmqd -ErrorAction SilentlyContinue
Start-Sleep -Seconds 2

# 2) สำรองไดเรกทอรีข้อมูล（ต้องทำหลังโปรเซสหยุดแล้ว）
Copy-Item -Recurse -Force $data "$base\backup-$(Get-Date -Format yyyyMMdd-HHmmss)"

# 3) เปลี่ยนไบนารี（วาง speedmqd.exe / speedmqctl.exe เวอร์ชันใหม่ไปที่เส้นทางเดิม）
#    Copy-Item .\new\speedmqd.exe $base\speedmqd.exe -Force

# 4) สตาร์ท
& "$base\speedmqd.exe" -config "$base\configs\speedmqd.json" -log-level info

# 5) ตรวจสอบ: โปรเซสยังอยู่ + API ฝ่ายจัดการอ่านได้
$pair = [Convert]::ToBase64String([Text.Encoding]::ASCII.GetBytes('guest:guest'))
$H = @{ Authorization = "Basic $pair" }
Invoke-WebRequest -Uri 'http://127.0.0.1:15672/api/overview' -Headers $H -UseBasicParsing | Select-Object -ExpandProperty Content
```

### 5.2 รายการตรวจสอบหลังอัปเกรด

- log การสตาร์ทปรากฏ `SpeedMQ 启动中 ... version=<เวอร์ชันใหม่>` และ `管理面已启动`;
- `object_totals` / `queue_totals` ของ `/api/overview` ตรงกับก่อนสำรอง（เทียบกับ `backup-restore.md` §5）;
- `messages` / `messages_ready` ของทุก durable queue ใน `/api/queues` ตรงกับก่อนสำรอง;
- `/metrics` ดึงได้และ `speedmq_plugin_up{name="amqp091"} 1`、`{name="mqtt"} 1`

## 6. การอัปเกรดอิมเมจ（คอนเทนเนอร์）

อิมเมจประมาณ 13 MB（ไบนารีลิงก์แบบ static + alpine）**รันแบบไม่ใช่ root（uid 10001）** ไดเรกทอรีข้อมูล mount ไว้ที่ `/var/lib/speedmq`

```powershell
# 1) ดึง/สร้างอิมเมจใหม่（tag ใช้เลขเวอร์ชันใหม่ เพื่อไม่ให้ old/new สับสน）
docker build -t speedmq:1.0.0 .

# 2) หยุดคอนเทนเนอร์เก่า（compose จะเก็บ named volume speedmq-data ไว้）
docker compose down

# 3) สตาร์ทเวอร์ชันใหม่（แก้ image ในไฟล์ compose เป็น tag ใหม่）
docker compose up -d

# 4) สถานะและ log
docker compose ps
docker compose logs -f --tail 100
```

> **งานครั้งเดียวภายในคอนเทนเนอร์**（เช่นรัน `speedmqctl` ในคอนเทนเนอร์）: `run` ของ `docker compose ...` ในสภาพแวดล้อมที่ไม่โต้ตอบต้องเติม `-T`
> ไม่งั้นจะล้มเหลวเพราะขอ TTY ไม่สำเร็จ:
> ```powershell
> docker compose run -T --rm broker speedmqctl -user guest -pass guest status
> ```

ความคงทนของข้อมูลพึ่งพา**named volume** `speedmq-data` ของ compose สร้างคอนเทนเนอร์ใหม่ข้อมูลไม่หาย（ตั้งแต่ M4 เขียนลงดิสก์จริง）
ถ้าต้องสำรองเนื้อหา volume ก่อนอัปเกรด ก็เทียบเท่ากับการสำรอง `/var/lib/speedmq`（ดู `backup-restore.md` §3.2）**【ยังไม่ได้ทดสอบการอัปเกรดอิมเมจ】**（เครื่องนี้ยังไม่ได้รัน Docker）

## 7. การปล่อยแบบค่อยเป็นค่อยไปและการย้อนกลับ

### 7.1 เครื่องเดียว

- **การปล่อยค่อยเป็นค่อยไป**: SpeedMQ โหมดเครื่องเดียวไม่มีความสามารถในตัวแบบ「สองเวอร์ชันเก่า-ใหม่ในโปรเซสเดียวกัน」การปล่อยค่อยเป็นค่อยไปที่เป็นไปได้คือ**เงาข้างทาง（shadow）**:
  อินสแตนซ์เวอร์ชันใหม่ใช้**การบริโภคแบบอ่านอย่างเดียว/shadow queue**แขวนกับทราฟฟิกต้นทางเดียวกันเพื่อสังเกต ก่อนยืนยันว่าไม่มีปัญหาแล้วค่อยสลับฝั่งที่เขียน
- **การย้อนกลับ**:
  1. หยุดโปรเซสเวอร์ชันใหม่;
  2. เปลี่ยนกลับไปใช้ไบนารีเก่า;
  3. ถ้าเวอร์ชันใหม่เคยเขียนข้อมูลไปแล้ว **ต้องกู้คืน `data_dir` ด้วยไฟล์สำรองก่อนอัปเกรด**（ดูด้านล่าง）
  **จะไม่**มีการรับประกันแบบ「เวอร์ชันใหม่เขียนไปแล้ว เวอร์ชันเก่าอ่านได้โดยตรง」——การดาวน์เกรดข้ามเวอร์ชันดู §8

### 7.2 คลัสเตอร์（การอัปเกรดแบบหมุน）

ฝั่งแพลตฟอร์มไม่มีความสามารถ「อัปเกรดแบบหมุนด้วยปุ่มเดียว」ต้องดำเนินการด้วยมือทีละโหนดตามลำดับด้านล่าง:

1. **อัปเกรดครั้งละหนึ่งโหนด**: หยุดโหนดนั้น → สำรอง `data_dir` ของมัน → เปลี่ยนไบนารี → สตาร์ท → รอให้มันเข้าร่วมใหม่และตามทัน
   （`speedmqctl cluster_status` / `GET /api/cluster` ดู `role`、`commit_index`/`last_applied`）
2. **ลำดับที่แนะนำ**: อัปเกรด **learner / สมาชิกที่ไม่ลงคะแนน**ก่อน（ไม่กระทบฝ่ายข้างมาก）จากนั้นอัปเกรด **follower** สุดท้ายค่อยอัปเกรด **leader**
   （การอัปเกรด leader จะกระตุ้นการเลือกหัวหน้าหนึ่งครั้ง ระหว่างนั้นจะเขียนไม่ได้ชั่วครู่）
3. **ผลกระทบของการหยุดที่มีต่อฝ่ายข้างมาก**（สำคัญ）:
   - คลัสเตอร์ 3 โหนด: **หยุดสมาชิกที่ลงคะแนนได้ครั้งละไม่เกิน 1 ตัว** หยุด 2 ตัวจะเสียฝ่ายข้างมาก ภายใต้ `pause_minority` **ทั้งคลัสเตอร์จะหยุดให้บริการ**
   - คลัสเตอร์ 2 โหนด: หยุด 1 ตัวก็เสียฝ่ายข้างมาก **ไม่มีความสามารถในการอัปเกรดแบบหมุน**（แนะนำอย่างน้อย 3 โหนด）
   - ดังนั้นระหว่างการอัปเกรดแบบหมุน**ห้ามหยุดสมาชิกที่ลงคะแนนหลายตัวพร้อมกันเด็ดขาด**
4. **อย่าทำการเปลี่ยนสมาชิกกับการอัปเกรดพร้อมกัน**: การเปลี่ยนสมาชิก**ไม่มี joint consensus** อนุญาตให้มีการเปลี่ยนแปลงคอนฟิกที่ยังไม่ commit ได้ครั้งละหนึ่งรายการเท่านั้น;
   ระหว่างอัปเกรดโปรดหลีกเลี่ยงการ `add_member` / `remove_member` พร้อมกัน
5. หลังอัปเกรดเสร็จตรวจ `object_totals` ของ `GET /api/cluster` ให้ตรงกับก่อนอัปเกรด

> **【ยังไม่ได้ยืนยัน】** เครื่องนี้ยังไม่ได้ซ้อมการอัปเกรดแบบหมุนของคลัสเตอร์จริง（ทั้งเส้นทางคลัสเตอร์และคอนเทนเนอร์ยังไม่ได้รัน）; ลำดับข้างต้นมาจากข้อจำกัดทั่วไปของ
> มิดเดิลแวร์รับส่งข้อความกับ Raft และข้อเท็จจริงของการทำงาน `pause_minority` / การเปลี่ยนสมาชิกใน repository นี้ ไม่ใช่ข้อสรุปจากการทดสอบจริงบนเครื่องนี้

## 8. ส่วนที่ไม่รองรับ / ยังไม่ได้ยืนยัน（ระบุไว้ชัดเจน）

- **การดาวน์เกรดข้ามเวอร์ชันใหญ่: ไม่รองรับ ไม่ได้ยืนยัน** ถ้าเวอร์ชันใหม่เขียนข้อมูลด้วยรูปแบบ/ความหมายใหม่แล้ว **ไม่มี**การรับประกันว่า「ย้อนกลับไปใช้ไบนารีเก่าแล้วอ่านได้」
  การย้อนกลับทำได้เพียงอาศัยไฟล์สำรองก่อนอัปเกรด
- **รูปแบบคอนฟิกไม่เปลี่ยน**: ยังเป็น JSON + ตัวแปรสภาพแวดล้อม `SPEEDMQ_*`。**ยังไม่รองรับคอนฟิก YAML**（ต้องเพิ่ม dependency ตัวแยกวิเคราะห์ รอประเมินใน M8-17）
  การอัปเกรดจะไม่นำ YAML มาให้
- **การอัปเกรดปลั๊กอิน/โปรโตคอลแบบ hot ออนไลน์**: ปลั๊กอินถูกคอมไพล์เข้ามากับ kernel（รูปแบบ A）หรือถูกดึงขึ้นตามคอนฟิก `spawn`（รูปแบบ B）
  การอัปเกรด kernel = รีสตาร์ทโปรเซส; **ไม่มี**กลไกสลับไบนารีแบบ hot ในที่
- **การย้ายที่เก็บข้อมูลในที่**: การหมุน segment/บีบอัดดัชนีเป็นพฤติกรรมเบื้องหลังระหว่างรัน **ไม่มี**คำสั่ง「ย้าย/บีบอัดข้อมูล」แยกต่างหาก
- **การอัปเกรดคลัสเตอร์บนเครือข่ายจริง**: repository นี้ทำเพียง chaos แบบย่อส่วน（kill ระดับโปรเซส）**ยังไม่ได้ทำ**การซ้อมอัปเกรดภายใต้การแบ่งเครือข่าย/ดิสก์เต็ม
- เอกสารนี้**ไม่ได้รวม**การตรวจสอบการขนย้ายข้อมูลระหว่าง SpeedMQ กับ broker อื่น（RabbitMQ）ใด ๆ
