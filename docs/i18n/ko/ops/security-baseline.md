# SpeedMQ 보안 강화 기준선(체크 가능한 체크리스트)

> 원칙: **이 저장소가 실제로 갖춘 능력만 기술합니다**. 각 항목은 "왜 해야 하는가 + 했다는 것을 어떻게 검증하는가"를 제시하며, 검증 명령은 모두 실행 가능합니다.
> **【검증됨】** 표시는 로컬(Windows + PowerShell 5.1, `1.0.0`)에서 **실제로 실행했음**을 의미하고,
> **【미검증】** 표시는 실행하지 않았거나 현재 불가능함을 의미하며, 절대 꾸며내지 않습니다.
> 모든 명령은 `/bin/sh` 스타일 curl 버전을 제시하고 PowerShell 버전을 함께 첨부합니다(PowerShell 5.1에서는
> `Invoke-WebRequest ... -UseBasicParsing` 사용).

---

## A. 인증과 접근 제어

### A-1. 기본 계정 `guest/guest` 변경 【검증됨】

- **이유**: 기본 내장 `guest/guest`(태그 `administrator`)는 외부에 노출되면 문을 활짝 열어 둔 것과 같습니다.
- **방법**: 런타임에 비밀번호 변경 / 계정 삭제를 하며, 설정 파일을 수정하지 **마세요**(`users`는 최초 부트스트랩 시에만 적용).

```bash
# 비밀번호 변경
curl -u guest:guest -X PUT http://127.0.0.1:15672/api/users/guest \
     -H 'Content-Type: application/json' -d '{"password":"<新口令>","tags":["administrator"]}'
# 또는 기본 계정을 직접 삭제(먼저 새 관리자를 만들어 두세요)
curl -u guest:guest -X DELETE http://127.0.0.1:15672/api/users/guest
```

- **검증 방법**: 변경 후 이전 비밀번호는 401이어야 하고, 새 비밀번호는 200이어야 합니다.
  **【검증됨】** 로컬 실측 출력:

  ```
  --- 改密前 guest/guest ---          HTTP 200 {"auth_backend":"internal","name":"guest","tags":"administrator"}
  PUT /api/users/guest -> 204
  --- 改密后 guest/guest（应 401）---  HTTP 401
  --- 改密后 guest/s3cret（应 200）--- HTTP 200 {"auth_backend":"internal","name":"guest","tags":"administrator"}
  ```
- [ ] 기본 계정 변경/삭제 완료

### A-2. 최소 권한: vhost별 `configure` / `write` / `read` 정규식 【검증됨】

- **이유**: 세 분류는 RabbitMQ에 맞춘 것으로, `configure`는 토폴로지 선언/삭제, `write`는 발행과 바인딩, `read`는 소비와 가져오기를 관리하며,
  권한 초과 시 403을 반환합니다. 비즈니스 계정에는 필요한 것만 부여하세요.
- **방법**: `PUT /api/permissions/{vhost}/{user}`, 예를 들어 읽기 전용 소비: `{"configure":"^$","write":"^$","read":".*"}`.

```bash
curl -u guest:guest -X PUT http://127.0.0.1:15672/api/permissions/%2F/appuser \
     -H 'Content-Type: application/json' -d '{"configure":"^$","write":"^$","read":".*"}'
```

- **검증 방법**: 제한 계정으로 권한 초과 작업을 시도하면 403 `ACCESS_REFUSED`가 나와야 합니다.
  **【검증됨】** 로컬에서 실제 AMQP 클라이언트로 `configure="^$"`인 사용자가 익스체인지를 선언한 실측:

  ```
  FAIL 声明 durable 交换机失败: Exception (403) Reason: "ACCESS_REFUSED - access to configure 'r.ex' refused for user 'restricted'"
  ```
- [ ] 각 비즈니스 계정에 필요한 정규식만 부여했고, `administrator`/`management` 태그를 주지 않았음

### A-3. `administrator` 태그의 규칙(암묵적 완전 권한) — 신중히 부여 【검증됨】

- **이유**: **`administrator` 태그를 가진 사용자는 자신이 볼 수 있는 모든 vhost에 대해 완전 권한을 가지며 권한 기록이 필요 없습니다**
  (RabbitMQ 실측 규칙에 맞춤, README / 설계 M8-7 참고). 즉 이 태그를 부여하면
  권한 정규식이 작동하지 않습니다 — 최고 권한입니다.
- **방법**: 관리면/운영 계정에만 `administrator`를 부여하고, 비즈니스 계정에는 태그를 주지 않고 권한 정규식만 사용합니다.

- **검증 방법(암묵적 권한 시연)**: **권한 기록이 전혀 없는** 새 vhost에 대해 `administrator` 사용자는 바로 사용할 수 있어야 합니다.
  **【검증됨】** 로컬 실측: 새 vhost `drillvh`(권한 기록을 만들지 않음)를 만든 뒤, `guest`(administrator)가 그 위에 토폴로지를 선언하는 데 성공:

  ```
  --- administrator 隐式权限：guest 在 drillvh 上声明拓扑 ---
  OK  已声明 durable 交换机 a.ex / 队列 a.q，并绑定 key=k   (exit=0)
  ```
- [ ] `administrator` 태그는 극소수 운영 계정에만 부여

### A-4. `remote_access`: 계정을 로컬 로그인만 허용하도록 제한 【미검증(동일 머신에서 원격 출처를 시뮬레이션할 수 없음)】

- **이유**: RabbitMQ에 맞춰 내장 `guest`는 기본적으로 로컬 로그인만 허용하며, 외부 배포 시에는 특권 계정의 출처가 제한되도록 해야 합니다.
- **방법 / 규칙(중요한 제한)**:
  - `remote_access`는 **설정 파일**의 `users.<name>.remote_access`에만 쓸 수 있고, **최초 부트스트랩 시에만 적용**됩니다.
  - **관리 API / `speedmqctl`로 생성한 계정은 모두 `remote_access=true`**입니다(모든 출처의 로그인 허용) —
    근거는 `internal/broker/observe.go`의 `UpsertUser` 주석과 `meta/state.json`에서 실측한
    `"remote_access":true`입니다. 즉 **API로는 현재 특정 계정을 로컬 전용으로 제한할 수 없습니다**.
- **검증 방법**: **다른 호스트**(`127.0.0.1`이 아님)에서 해당 계정으로 연결하면 403이어야 하고, 로컬 연결은 성공해야 합니다.
  **【미검증】**: 로컬 환경에서 실제 원격 출처를 구성할 수 없어 실측하지 않았습니다.
- [ ] 특권 계정의 출처 제한을 위 규칙에 따라 평가함(API로 만든 계정은 기본적으로 원격을 허용함에 유의)

## B. 전송 보안(TLS)

TLS 설정 항목(접속 계층과 관리면이 **동일한** 필드 세트를 **공유**): `cert_file` / `key_file` / `ca_file` / `client_auth` / `min_version`.

### B-1. TLS를 켜고 잘못 설정하면 즉시 기동 거부 【검증됨】

- **이유**: 인증서는 **기동 시** 읽고 검증합니다 — 잘못 설정하면 즉시 기동을 거부하며, 첫 클라이언트가 접속할 때까지 기다렸다가 드러나지 않습니다.
- **방법**: `listeners.<plugin>[].tls` 또는 `management.tls`에 `cert_file` + `key_file`을 제공합니다(**둘 다** 주어야 활성화).

- **검증 방법**: 잘못된 설정으로 기동하면 즉시 실패해야 합니다.
  **【검증됨】** 로컬에서 세 가지 잘못된 설정을 실측했으며, 모두 `exit=1`로 기동을 거부:

  ```
  badtls1: speedmqd 启动失败: listeners.amqp091[0].tls 需要同时提供 cert_file 与 key_file
  badtls2: speedmqd 启动失败: listeners.amqp091[0].tls.min_version 取值非法: "1.0"（可选 1.2 / 1.3）
  badtls3: speedmqd 启动失败: listeners.amqp091[0].tls 无效: 加载服务端证书失败（cert=... key=...）: open ...: The system cannot find the path specified.
  ```
- **검증 방법(정방향/역방향)**: TLS 클라이언트는 연결되고, 평문 클라이언트가 TLS 포트에 연결하면 거부됩니다.
  **【검증됨】** 로컬에서 TLS 인스턴스(`amqp091`이 TLS 사용)를 띄우고 실제 클라이언트 프로브 사용:

  ```
  === 正向：TLS 客户端跑全量探针 ===      全部通过（25/25）: ...
  === 反向：明文客户端连 TLS 端口（应失败）===  FAIL ... 拨号失败: Exception (501) Reason: "EOF"   (exit=-1)
  ```
- [ ] 외부 프로토콜 포트에 TLS 활성화됨

### B-2. `min_version`은 최소 1.2 【검증됨】

- **이유**: 너무 오래된 TLS 버전을 비활성화합니다. 기본값이 `1.2`이며 `1.2` / `1.3`을 선택할 수 있습니다.
- **검증 방법**: `min_version`을 `1.0`으로 쓰면 기동 시 오류가 나야 합니다(B-1의 `badtls2` 출력 참고).
- [ ] `min_version`이 `1.2` 또는 `1.3`

### B-3. 상호 인증 `client_auth: require_and_verify`(mTLS) 【부분 검증】

- **이유**: 클라이언트가 인증서를 제시하고 검증하도록 요구해, 미인가 클라이언트의 프로토콜 포트 접속을 방지합니다.
- **방법**: `ca_file` + `client_auth: require_and_verify`를 설정합니다(후자는 `ca_file`을 함께 제공해야 함).
- **【검증됨】**: TLS 엔드투엔드와 거부 경로는 실제 클라이언트로 검증했습니다(B-1). **mTLS(클라이언트 인증서 요구 및 검증)는 로컬에서 별도로 리허설하지 않았습니다**.
- [ ] mTLS가 필요한 포트에 `require_and_verify` + `ca_file` 설정

### B-4. 관리면 TLS 【미검증】

- **이유**: 관리면은 Basic Auth로 비밀번호를 전달하므로 반드시 암호화해야 합니다.
- **방법**: `management.tls`에 프로토콜 수신과 동일한 필드를 사용합니다.
- **【미검증】**: 로컬 리허설에서는 관리면을 로컬 평문 포트에 바인딩했고, 관리면 HTTPS를 별도로 띄우지 않았습니다.
- [ ] 관리면에 TLS 활성화됨(또는 신뢰할 수 있는 네트워크 내로 엄격히 제한)

## C. 노출 면 축소

### C-1. 관리면 수신 범위 축소 【검증됨(수신 주소 실측)】

- **이유**: 관리면은 기본적으로 `:15672`(모든 네트워크 카드)입니다. 외부 배포 시에는 내부망/루프백 주소에 바인딩하거나 방화벽으로 출처를 제한해야 합니다.
- **방법**: `management.addr`을 `127.0.0.1:15672` 또는 내부망 주소로 설정하거나, `management.enabled=false`로 완전히 끕니다
  (끄면 관리 포트가 없어지지만 `speedmqctl`도 함께 사용할 수 없게 됩니다).
- **검증 방법**:
  **【검증됨】** 로컬에서 관리면을 `127.0.0.1:15677`로 설정했고, 실측 수신 주소가 루프백임을 확인:

  ```
  LocalAddress LocalPort
  ------------ ---------
  127.0.0.1        15677
  ```
- [ ] 관리면 바인딩 주소가 축소됨(또는 비활성화됨)

### C-2. 프로토콜 포트는 필요한 것만 개방 【미검증】

- **이유**: 기본적으로 AMQP `5672`와 MQTT `1883`을 동시에 엽니다. MQTT를 쓰지 않으면 꺼서 공격 면을 줄이세요.
- **방법**: `plugins.mqtt.enabled=false`(또는 `listeners`에서 제거)로 설정합니다. 비활성화는 **실제 포트를 닫는** 것이며, 단순히 상태 플래그만 바꾸는 것이 아닙니다.
- **검증 방법**: 비활성화 후 해당 포트가 더 이상 수신하지 않아야 합니다(`Get-NetTCPConnection -State Listen`에서 보이지 않음).
  **【미검증】**: 로컬 리허설에서는 두 프로토콜을 모두 켜 두었고, 종료 후 포트가 사라지는지는 별도로 검증하지 않았습니다.
- [ ] 사용하지 않는 프로토콜 플러그인 비활성화됨

## D. 컨테이너 실행 강화

저장소 이미지 사실(`Dockerfile`): 정적 링크 바이너리 + alpine, **비 root(uid 10001, 사용자 `speedmq`)로 실행**,
데이터 디렉터리 `/var/lib/speedmq`는 볼륨입니다. `docker-compose.yml`은 **명명 볼륨** 영속화, 설정 **읽기 전용 마운트**, 로그 로테이션을 사용합니다.

### D-1. 비 root 실행 【미검증(로컬에서 Docker를 실행하지 않음)】

- **이유**: 최소 권한으로, 컨테이너 탈출 후의 영향 범위를 줄입니다.
- **방법**: 이미지 기본값이 이미 uid 10001입니다. `--user root`로 덮어쓰지 **마세요**.
- **검증 방법**: `docker compose run -T --rm broker id`가 `uid=10001`을 표시해야 합니다.(`run`은 비대화형 환경에서 반드시 `-T`를 붙여야 함)
- [ ] 컨테이너가 비 root로 실행됨(root로 덮어쓰지 않음)

### D-2. 읽기 전용 루트 파일 시스템 + 리소스 제한 + capability 축소(권장, 저장소 compose는 기본적으로 미활성) 【미검증】

- **이유**: 읽기 전용 루트 파일 시스템은 런타임에 바이너리가 변조되는 것을 막고, 리소스 제한은 단일 컨테이너가 호스트를 마비시키는 것을 방지하며, capabilities 축소는 커널 공격 면을 줄입니다.
- **방법**(예시, 필요에 따라 compose의 `broker` 서비스에 병합):

```yaml
services:
  broker:
    read_only: true
    tmpfs:
      - /tmp
    security_opt:
      - no-new-privileges:true
    cap_drop: ["ALL"]
    deploy:
      resources:
        limits:
          cpus: "4"
          memory: 8g
```

- **검증 방법**: 컨테이너 내에서 루트 경로에 쓰기를 시도하면 실패해야 합니다(읽기 전용). `docker inspect`로 리소스 제한을 볼 수 있습니다.
  **【미검증】**(로컬에서 Docker를 실행하지 않음). 또한 **읽기 전용 루트 파일 시스템에서는 `data_dir`이 쓰기 가능한 볼륨에 있는지 확인해야** 하며, 그렇지 않으면 커널이 디스크에 기록할 수 없습니다.
- [ ] 읽기 전용 루트 파일 시스템과 리소스 제한을 평가함(`data_dir`이 반드시 쓰기 가능한 볼륨에 있어야 함에 유의)

## E. 알려진 제한(현재 실제로 불가능하므로 기대하지 마세요)

다음은 모두 **사실적 결함**이므로, 보안 설계에서 명시적으로 인정하고 존재한다고 가정하지 마세요:

1. **비밀번호는 평문으로 저장되고 복제됩니다**. `meta/state.json`의 `password` 필드는 평문이며(**【검증됨】** 실측으로
   `"password":"drillpass"` 확인 가능), 설정 파일에서도 평문입니다. 비밀번호 해시는 **없습니다**(해시와 외부 인증 백엔드는 인증 플러그인에 맡김).
   → 결과: **데이터 디렉터리와 백업 파일은 민감 자격 증명과 동일**하므로 파일 권한과 암호화 보호를 반드시 해야 합니다.
2. **감사 로그가 없습니다**. 관리면의 추가/삭제/수정은 일반 로그로 남지만(예: `管理面更新用户 actor=... user=...`),
   독립적이고 변조 불가능한 감사 스트림이 **없으며**, "누가 언제 무엇을 바꿨는가"에 대한 컴플라이언스 수준 기록도 없습니다.
3. **LDAP / OAuth2 / JWT 등 외부 인증이 없습니다**. v1 내장은 `PLAIN` / `AMQPLAIN`뿐입니다
   (`auth.Store.Mechanisms()` 실측에서 이 둘만 반환).
4. **SASL `EXTERNAL` 미구현**: mTLS를 설정해도 프로토콜 계층은 **여전히 PLAIN 비밀번호 인증을 사용**합니다
   ("클라이언트 인증서로 비밀번호 없이" 단계가 없음). 인증서는 전송 계층 검증일 뿐입니다.
5. **`remote_access`는 API로 설정할 수 없음**: 관리 API/CLI로 만든 계정은 모두 원격 로그인을 허용하며(A-4 참고),
   단일 계정을 로컬 전용으로 제한할 수 없습니다.
6. **관리면에 독립적인 출처 화이트리스트 / 속도 제한이 없음**: 바인딩 주소, 방화벽, TLS로만 노출 면을 축소할 수 있습니다.
7. **플러그인 샌드박스 없음**: A 형태 플러그인은 커널과 같은 프로세스이고, B 형태 외부 플러그인은 프로세스 격리가 있지만 **데이터면은 로컬 연결 프록시를 거치며**,
   플러그인이 커널 시맨틱을 호출할 수 있습니다(vhost와 권한 검증 제약을 받음). **보안 샌드박스가 아닙니다**.
8. **관리면 태그는 `administrator`/`management`/`monitoring` 세 단계뿐**이며, 더 세분화된 리소스별 RBAC는 없습니다.

## F. 종합 체크리스트

- [ ] A-1 기본 계정 변경/삭제 【검증된 절차】
- [ ] A-2 비즈니스 계정 최소 권한(정규식), 관리자 태그 없음 【검증된 403 경로】
- [ ] A-3 `administrator` 태그는 운영 계정에만 부여 【검증된 암묵적 권한 규칙】
- [ ] A-4 특권 계정 출처 제한 평가 완료(API로 만든 계정은 기본적으로 원격을 허용함에 유의)
- [ ] B-1 외부 포트에 TLS 활성화, 잘못 설정 시 기동 거부 【검증됨】
