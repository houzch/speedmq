# SpeedMQ アップグレードと移行計画

> 適用バージョン：`1.0.0`（`broker.Version`、`/metrics` の `speedmq_build_info` を参照）。
> 本書のすべての「実測」結論は本機での実際の実行によるものです。実測していないものはすべて **【未検証】** と明示します。
> 本機環境：Windows + PowerShell 5.1、Go 1.27.1 windows/386、一時 `data_dir` + 非デフォルトポート。

---

## 1. 移行（RabbitMQ から SpeedMQ へ）

本プロジェクトの位置付けは **AMQP 0-9-1 プロトコルレベルの互換**であるため、「移行」は主に**接続先アドレスの変更**です：

- 業務コードはゼロ変更で、`host/port/vhost` のみ変更します（設計文書 G3「移行ゼロコスト」）。
- 管理ツールチェーン（`rabbitmqadmin`、管理 UI、監視スクリプト）は管理面ポートを指定するだけでよく、インターフェース形状は RabbitMQ に合わせています（`amq.default`、`%2F`、`{error, reason}` などの約束事をそのまま踏襲）。
- デフォルトポートは RabbitMQ と一致：AMQP `5672`、管理面 `15672`；MQTT は `1883`、ノード間 RPC は `25672`。

**移行前に自己確認すべきセマンティクスの差異**（いずれも本リポジトリの意図的なもので、README / 設計文書に基づく）：

| 項目 | SpeedMQ の挙動 | 移行への影響 |
| --- | --- | --- |
| 一時（非永続かつ非排他）キュー | **宣言を拒否**（541）、`auto_delete` でも免除されない | この種のキューに依存する古いクライアントは失敗するため、durable または exclusive に変更が必要 |
| デフォルト vhost `/` | **削除不可**（400）、RabbitMQ は許可 | デフォルト vhost を削除する自動化スクリプトは失敗する（唯一の能動的な安全制約） |
| クラシックキューのデータ | **複製しない**、データは Owner ノードのみ | ノード間の冗長化が必要ならクォーラムキュー `x-queue-type=quorum` に変更 |
| クォーラムキュー | レプリカ拡張をサポート、**縮小は非サポート** | 計画時に一度で確定させる |
| プラグイン | Erlang プラグインエコシステムなし、AMQP 1.0 / STOMP は未実装 | これらのプロトコルを使うシーンは現時点では移行不可 |

**データ移行**：SpeedMQ と RabbitMQ はストレージ形式が非互換で、**オンライン/オフラインのデータ移送ツールを提供しません**。
移行方法は「空の SpeedMQ を新規作成 → 二重運用で検証 → グレーリリースで切り替え」。**【未検証】** 本書には実際の RabbitMQ データ移送ドリルは含まれません。

## 2. アップグレードの総原則

1. **先にバックアップ**（`backup-restore.md` を参照）——アップグレード失敗時の保険。
2. **先にプロセスを停止してから置換**（データディレクトリには単一ライターの制約がある、§4.2 を参照）。
3. **アップグレード後は必ず検証**：プロセスが起動できる、`/api/overview` が読める、`/metrics` が取得できる、キューのメッセージ数がバックアップ前と一致する。
4. クラスタのアップグレードは**ノードごとにローリング**し、一度に 1 ノードのみ操作する（§5 を参照）。

## 3. データディレクトリのレイアウト（アップグレード/移行の事実根拠）

本機の単機インスタンスで**実測**して得た `data_dir` レイアウト：

```
data/
├── meta/
│   ├── state.json        # 単機モードのメタデータスナップショット（vhost/エクスチェンジ/キュー/バインディング/ユーザー/権限/ポリシー）
│   ├── users.seeded      # ブートストラップマーカー：設定ファイルの users はシード済み
│   ├── vhosts.seeded     # ブートストラップマーカー：設定ファイルの vhosts はシード済み
│   ├── raft.state        # 【クラスタモード】Raft 任期/投票
│   ├── raft.log          # 【クラスタモード】Raft ログ
│   └── snapshot.json     # 【クラスタモード】Raft スナップショット + メンバー表
├── msg_stores/vhosts/<safe(vhost)>/queues/<safe(queue)>/
│   ├── 000001.seg        # セグメントファイル（メッセージ本体 + 属性）、レコード形式：<len u32><crc32 u32><payload>
│   └── index/000001.idx  # キューインデックス：seq-id → (セグメント番号, セグメント内オフセット, 長さ, 状態)
└── quorum/<safe(vhost)>/<safe(queue)>/   # 【クラスタ】クォーラムキューはキューごとに 1 つの Raft グループ（ログ/スナップショット）
```

**注意（直感と異なる 2 点、いずれもコード/実測に基づく）**：

- クラスタモードでは Raft 永続化ファイルは**直接 `meta/` 配下に置かれ**（`raft.state` / `raft.log` / `snapshot.json`）、
  **`meta/raft/` サブディレクトリは存在しません**。根拠：`internal/raft/log.go` のファイル名定数 + `internal/broker/cluster.go`
  の `Dir: filepath.Join(b.cfg.DataDir, "meta")`。**【検証済み（2026-10-10、本機 Docker Desktop 3 ノードクラスタ）】** —— クラスタノードのボリュームバックアップ内容に `meta/raft.log`、`meta/raft.state`、`meta/*.seeded` が直接見え（`meta/raft/` サブディレクトリは見当たらない）。
- ディレクトリ名は**元の vhost / キュー名ではなく**、`store.SafeDirName` によるエンコード：接頭辞 `q_` を付加し、`[A-Za-z0-9._-]` 以外のバイトは `%XX` でエスケープ。
  実測：vhost `/` → ディレクトリ `q_%2F`、キュー `persist.q` → ディレクトリ `q_persist.q`。
  この設計はパストラバーサルと Windows の予約デバイス名（`con`/`nul` など）を回避するためです。

## 4. データ互換性

### 4.1 旧データを直接読めるか——読める

- **インデックス形式は前方互換**：M8-1 でインデックスレコードに「セグメント番号」フィールド（25 バイト）を追加；**旧形式（21 バイト、セグメント番号なし）もそのまま読め**、
  読み取り時は「セグメントが 1 つだけ（seg=1）」と等価で、**アップグレードに移行スクリプトは不要**。
  根拠：`internal/store/store.go` の `indexEntrySize` / `legacyIndexEntrySize` 定数と `recover()` ロジック；README M8-1。
- **クラッシュセマンティクスは不変**：各レコードは長さプレフィックス + CRC32 を持ち、復元時に**末尾の書きかけ/破損レコードを破棄**して切り詰めます。
  実測（`backup-restore.md` §6 を参照）：プロセス停止後に再起動すると、durable キューの 5 件の永続メッセージが**すべて復元**され、
  ログに `已从磁盘恢复队列消息 ... messages=5` が出現。

**【検証済み（2026-10-10、本機）】** メジャーバージョン間の読み取りを実測済み：tag `v1.1.0` で書き込んだ durable キューのデータが `1.1.05` でそのまま復元される（コマンドと出力は §5 を参照）。

### 4.2 設定の `vhosts` / `users` の扱い（アップグレードで最もつまずきやすい罠）

- 両者は**初回ブートストラップ時のみ有効**：初回起動時に設定の vhosts/users をメタデータに書き込み、マーカーファイル
  `meta/vhosts.seeded` / `meta/users.seeded` を残します；**以降はメタデータを基準**とします。
- したがって**アップグレード/設定変更時に、設定ファイルを変更してアカウントや vhost を追加/削除しようと期待しないでください**——変更しても有効になりません；
  管理 API または `speedmqctl` を使用してください。
- 逆に、アップグレードが設定で既存アカウントを上書きすることは**ありません**：実行時に変更したパスワードが再起動で設定の旧値に戻ることはなく、
  実行時に削除したアカウントが復活することもありません。根拠：`cluster.go` のシードマーカーロジック；README M8-4 / M8-7。

**【検証済み（2026-10-10、本機）】** 実行期の変更は確かに設定で上書きされない：アップグレード前に管理 API 経由で `guest` のパスワードを `rotated` に変更し、`1.1.05` + 同一 `data_dir` で再起動したところ、`guest/guest`（設定の旧パスワード）は **401** を、`guest/rotated` は **200** を返した。

### 4.3 セグメントローテーションとディスク回収

- メッセージはサイズでセグメント化され（デフォルト 8 MiB）、**セグメント内のメッセージがすべて ack され、セグメントが封口されるとセグメントごと削除**され、インデックスもそれに伴い圧縮・書き換えられます。
- アップグレードはこの挙動を変更しません；旧インスタンスが残した単一セグメントファイルも新しいセグメントローテーションロジックで通常どおり動作します。

## 5. バイナリアップグレード（ベアメタル）

> **【検証済み（2026-10-10、本機）】** メジャーバージョン間の実機ドリル：tag `v1.1.0` でビルドした旧バイナリで durable エクスチェンジ/キュー/バインディング + 5 件の永続メッセージ + vhost/アカウント/権限/ポリシーを書き込み、実行期にパスワードを変更；プロセス停止後、現行の `1.1.05` バイナリ + **同一 `data_dir` + 同一ポート**で起動 —— プロセスは正常起動、`/api/queues` のオブジェクトとメッセージ数が一致、実際の AMQP クライアントが 5 件の永続メッセージをすべて取り戻し、`/metrics` が `speedmq_build_info{version="1.1.05"}` を報告。以下の手順は依然として汎用フローであり、任意の隣接バージョンに適用可能；**ダウングレード**は §8 を参照。

### 5.1 手順

```powershell
$base = "C:\speedmq"
$data = "$base\data"

# 1) プロセスを停止（正常終了時に最終フラッシュ；§4「一貫性」を参照）
#    フォアグラウンドで実行中：Ctrl+C；サービスとして実行中：Stop-Service / Stop-Process
Stop-Process -Name speedmqd -ErrorAction SilentlyContinue
Start-Sleep -Seconds 2

# 2) データディレクトリをバックアップ（必ずプロセス停止後）
Copy-Item -Recurse -Force $data "$base\backup-$(Get-Date -Format yyyyMMdd-HHmmss)"

# 3) バイナリを置換（新バージョンの speedmqd.exe / speedmqctl.exe を元のパスに配置）
#    Copy-Item .\new\speedmqd.exe $base\speedmqd.exe -Force

# 4) 起動
& "$base\speedmqd.exe" -config "$base\configs\speedmqd.json" -log-level info

# 5) 検証：プロセスの生存 + 管理 API が読める
$pair = [Convert]::ToBase64String([Text.Encoding]::ASCII.GetBytes('guest:guest'))
$H = @{ Authorization = "Basic $pair" }
Invoke-WebRequest -Uri 'http://127.0.0.1:15672/api/overview' -Headers $H -UseBasicParsing | Select-Object -ExpandProperty Content
```

### 5.2 アップグレード後のチェックリスト

- 起動ログに `SpeedMQ 启动中 ... version=<新版本>` と `管理面已启动` が出現；
- `/api/overview` の `object_totals` / `queue_totals` がバックアップ前と一致（`backup-restore.md` §5 と照合）；
- `/api/queues` の各 durable キューの `messages` / `messages_ready` がバックアップ前と一致；
- `/metrics` が取得でき、`speedmq_plugin_up{name="amqp091"} 1`、`{name="mqtt"} 1`。

## 6. イメージアップグレード（コンテナ）

イメージは約 13 MB（静的リンクバイナリ + alpine）、**非 root（uid 10001）で実行**、データディレクトリは `/var/lib/speedmq` にマウントされます。

```powershell
# 1) 新しいイメージを取得/ビルド（タグは新バージョン番号を使い、old/new の混同を避ける）
docker build -t speedmq:1.0.0 .

# 2) 旧コンテナを停止（compose は名前付きボリューム speedmq-data を保持）
docker compose down

# 3) 新バージョンを起動（compose ファイルの image を新タグに変更）
docker compose up -d

# 4) 状態とログ
docker compose ps
docker compose logs -f --tail 100
```

> **コンテナ内のワンショットタスク**（例：コンテナ内で `speedmqctl` を実行）：`docker compose ...` の `run` は非対話環境では必ず `-T` を付ける必要があり、
> そうしないと TTY 確保に失敗します：
> ```powershell
> docker compose run -T --rm broker speedmqctl -user guest -pass guest status
> ```

データの永続化は compose の**名前付きボリューム** `speedmq-data` に依存し、コンテナを再作成してもデータは失われません（M4 から実際にディスクへ書き込み）。
アップグレード前にボリューム内容をバックアップする必要がある場合、`/var/lib/speedmq` のバックアップと等価です（`backup-restore.md` §3.2 を参照）。

> **【検証済み（2026-10-10、本機 Docker Desktop）】** 実際のイメージアップグレードドリルを実施：旧イメージ `speedmq:1.1.0-old`（git tag `v1.1.0`）と新イメージ `speedmq:1.1.05-new`（現行ソース）をローカルでビルドし、単機 compose で旧イメージを起動 → durable キュー `persist.q` を作成し 5 件の永続メッセージを publish（`delivery_mode=2`）→ `docker compose down`（**`-v` を付けない**、名前付きボリューム `speedmq-data` を保持）→ compose の image tag を新イメージに替えて `docker compose up -d`。
> 結果：新コンテナは正常起動、起動ログに `已从磁盘恢复队列消息 ... queue=persist.q messages=5` が出現、`/metrics` が `speedmq_build_info{version="1.1.05"}` を報告、`/api/overview` の `queue_totals.messages=5` とキュー `persist.q` の `messages=5` がアップグレード前後で一致し、実際の AMQP クライアント（`rabbitmq/amqp091-go`）が 5 件の永続メッセージをすべて 1 件ずつ取り戻した（`deliveryMode=2`）。
> 注：`v1.1.0` は改名前の `speedmq` ブランドのイメージ（バイナリ `speedmqd`、メトリクス `speedmq_build_info`、デフォルトデータディレクトリ `/var/lib/speedmq`）で、現版とは命名が異なる；ドリルでは設定 `data_dir=/var/lib/speedmq` を基準とし、名前付きボリュームに所有者を事前設定した（旧イメージ内にはその書き込み可能パスが存在しない）。これは「tag を替えてコンテナを再作成しても名前付きボリュームのデータは失われない」という結論には影響しない。

## 7. グレーリリースとロールバック

### 7.1 単機

- **グレーリリース**：SpeedMQ 単機には「新旧同プロセスの二重バージョン」能力は内蔵されていません。実現可能なグレーリリースは**バイパスシャドウ**です：
  新バージョンのインスタンスをまず**読み取り専用消費/シャドウキュー**で同じ上流トラフィックに接続して観察し、問題がないことを確認してから書き込み側を切り替えます。
- **ロールバック**：
  1. 新バージョンのプロセスを停止；
  2. 旧バイナリに戻す；
  3. 新バージョンが既にデータを書き込んでいた場合、**必ずアップグレード前のバックアップで `data_dir` を復元**（下記参照）。
  「新バージョンが書いたものを旧バージョンがそのまま読める」という保証は**ありません**——バージョン間のダウングレードは §8 を参照。

### 7.2 クラスタ（ローリングアップグレード）

プラットフォーム側は「ワンクリックのローリングアップグレード」を提供せず、以下の順序で手動でノードごとに操作する必要があります：

1. **一度に 1 ノードのみアップグレード**：そのノードを停止 → `data_dir` をバックアップ → バイナリを交換 → 起動 → 再参加して追いつくのを待つ
   （`speedmqctl cluster_status` / `GET /api/cluster` で `role`、`commit_index`/`last_applied` を確認）。
2. **順序の推奨**：まず **learner / 非投票メンバー**（多数派に影響なし）をアップグレードし、次に **follower**、最後に **leader**
   （leader のアップグレードは選主を 1 回トリガーし、その間は短時間書き込み不可）。
3. **停止が多数派に与える影響**（重要）：
   - 3 ノードクラスタ：投票メンバーは**同時に最大 1 つ**まで停止可能。2 つ停止すると多数派を失い、`pause_minority` 下では**クラスタ全体がサービスを停止**。
   - 2 ノードクラスタ：1 つ停止すると多数派を失い、**ローリングアップグレード能力を持たない**（最低 3 ノードを推奨）。
   - したがってローリングアップグレード時は**複数の投票メンバーを一度に停止することは厳禁**。
4. **メンバー変更とアップグレードを同時に行わない**：メンバー変更には **joint consensus がなく**、一度に 1 つの未コミットの設定変更のみ許可されます；
   アップグレード期間中は `add_member` / `remove_member` の同時実行を避けてください。
5. アップグレード完了後、`GET /api/cluster` の `object_totals` がアップグレード前と一致することを確認する。

> **【検証済み（2026-10-10、本機 Docker Desktop 3 ノードクラスタ）】** 実際のクラスタの**バージョン間**ローリングアップグレードドリルを実施：ベースラインはローカルでビルドした `speedmq:1.1.0-old`（git tag `v1.1.0`）、ノードごと（n1 → n2 → n3、一度に 1 つ：まず停止、次にその名前付きボリュームをバックアップ、次にイメージを交換して起動）に現行の `1.1.05` へアップグレード（ローカルで `speedmq:1.1.05-new` をビルド、compose はノードごとの override でイメージを切替）。全期間を通じてクラスタは常に leader と多数派を保持 —— 現行 leader を停止した際に約 0.6 s で新 leader が選出され、`pause_minority` は一時停止をトリガーせず、停止期間中に外部からの中断もなかった；アップグレード後、`GET /api/cluster` の `object_totals` はアップグレード前と一致（`queues:1`）、3 レプリカ仲裁キュー `qroll` の 25 件の永続メッセージ数は不変で 1 件ずつ読み戻し可能、さらに 5 件の新規メッセージを publish した後は計 30 件すべてを取り戻せる。
> 上記の順序は Raft の一般的制約として依然成立し、今回のドリルは 3 ノードシナリオを対象とする。**【検証済み（2026-10-10、本機 Docker Desktop）2 ノードで 1 つ停止すると多数派を失う】** 別途最小の 2 ノードクラスタ（n1/n2、各 `peers` はこの 2 ノードのみ、`partition_policy=pause_minority`）を立てて実測：両ノードがオンラインのとき `GET /api/cluster` は `has_quorum=true / paused=false`（n1 leader、n2 follower）；n2 を `docker stop` すると n1 は約 2 s で `has_quorum=false / paused=true` に変化 —— すなわち投票メンバーを 1 つ停止するだけで多数派を失い `pause_minority` がサービスを一時停止し、**2 ノードがローリングアップグレード能力を持たないことを裏付けた**；`docker start` で n2 を復旧すると n1 は約 2 s で `has_quorum=true / paused=false` に戻る（サービスは自動復旧）。

> **【検証済み（2026-10-11、本機 Docker Desktop 3 ノードクラスタ）】ネットワーク分断下のローリングアップグレードを実測**（`v1.1.0` → `1.1.05` のバージョン間。分断はデュアルネットワークトポロジを使用：ノード間 Raft RPC は静的 IP の `cluster-net` のみを通り、クライアント/管理面は `client-net` を通り、`docker network disconnect/connect` で分断を切替）：
> - **分断された follower**：多数派側は分断中も quorum を保持し続け、正常に publish/consume し、分断継続中に多数派側 1 ノードの「停止→イメージ交換→起動→追いつき」を完了；混合バージョン（1.1.0 + 1.1.05）クラスタでもサービス可能。分断復旧後、隔離ノード（旧バージョン）は再参加して追いつき、メッセージは一意 ID 集合での突合で 35/35 損失なし。
> - **分断された leader**：多数派は約 **630 ms** で新 leader を選出；隔離された旧 leader は `role=leader` を保持するが `has_quorum=false / paused=true`（`pause_minority` が有効、任期を自発的には上げない）；分断中に多数派側の別ノードのアップグレードも成功；復旧後、旧 leader は再参加し、split-brain もデータ分岐もなし。
> - **PreVote なしの想定挙動（実際に記録）**：隔離された follower は即座に繰り返し選挙を開始し、任期は約 2 s ごとに +2（メタデータとキューの 2 つの Raft グループが交互に上昇）；復旧の瞬間に高い任期で**リーダーを奪取**（実測 1.4 s 以内に当選）—— leader 切替の擾乱はあるが正確性の問題はなし。
> - **2 つの運用上の落とし穴**：① `peers` にホスト名を使い、かつコンテナが到達可能な第 2 のネットワークにも接続していると、Raft トラフィックが迂回して「偽の分断」が発生する（隔離ノードが 1 分経っても `has_quorum=true`）—— ノード間 RPC は必ず 1 枚のネットワークのみを通すこと（peers はそのネットワークの静的 IP を直接指定）；② 復旧時に `docker network connect` は `--ip <元のIP>` を必ず付けること。さもないとノードが新しい IP を取得し、多数派が旧アドレスへ dial し続けるため、隔離ノードが遅れたログを抱えたまま膨張した任期で繰り返し選挙を行い（実測でクラスタ term が 320 から 488 へ、メタデータ commit が 13 から 97 へ跳ね上がった）、leader が `quorum=true` なのに一瞬 `paused=true` になる過渡状態が出ることがある。
> - 分断中、少数派側の管理 API は読み取り可能（観察に便利）、AMQP publish は拒否される（`pause_minority` が有効）。

## 8. 非サポート / 未検証の部分（明示）

- **メジャーバージョン間のダウングレード：非サポート、未検証**。新バージョンが新形式/新セマンティクスでデータを書き込んでいた場合、「旧バイナリに戻してそのまま読む」保証は**ありません**；
  ロールバックはアップグレード前のバックアップに頼るしかありません。
- **設定形式は不変**：引き続き JSON + `SPEEDMQ_*` 環境変数。**YAML 設定は未サポート**（パース依存の導入が必要、M8-17 で評価待ち）、
  アップグレードで YAML がもたらされることはありません。
- **オンラインのプラグイン/プロトコルホットアップグレード**：プラグインはカーネルにコンパイルして組み込む（A 形態）か、設定に従い `spawn` で起動する（B 形態）ため、
  カーネルのアップグレード = プロセスの再起動；バイナリをインプレースでホット置換する仕組みは**ありません**。
- **ストレージエンジンのインプレース移行**：セグメントローテーション/インデックス圧縮は実行期のバックグラウンド挙動で、独立した「データ移行/圧縮」コマンドは**ありません**。
- **ディスク満杯下のクラスタアップグレード**：**未検証**。（ネットワーク分断下のローリングアップグレードは 2026-10-11 に実測済み、§7 末尾の注記を参照。）
- 本書は SpeedMQ と他の broker（RabbitMQ）間のデータ移送検証を**含みません**。
