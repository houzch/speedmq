# SwiftMQ セキュリティ強化ベースライン（チェック可能なチェックリスト）

> 原則：**本リポジトリが実際に備えている能力のみを記載**します。各項目に「なぜ行うか + どうやって実施済みか検証するか」を示し、検証コマンドはすべて実行可能です。
> **【検証済み】** と注記したものは本機（Windows + PowerShell 5.1、`1.0.0`）で**実際に実行済み**であることを示します；
> **【未検証】** は未実行または現時点で実施できないことを示し、決して偽りません。
> すべてのコマンドは `/bin/sh` スタイルの curl 版を示し、併せて PowerShell 版を添えます（PowerShell 5.1 では
> `Invoke-WebRequest ... -UseBasicParsing` を使用してください）。

## A. 認証とアクセス制御

### A-1. デフォルトアカウント `guest/guest` の変更 【検証済み】

- **なぜ**：デフォルトで `guest/guest` を内蔵（タグ `administrator`）しており、外部に露出することは門を全開にするのと同じです。
- **どうする**：実行時にパスワードを変更 / アカウントを削除します。設定ファイルを変更してはいけません（`users` は初回ブートストラップ時のみ有効）。

```bash
# パスワード変更
curl -u guest:guest -X PUT http://127.0.0.1:15672/api/users/guest \
     -H 'Content-Type: application/json' -d '{"password":"<新口令>","tags":["administrator"]}'
# またはデフォルトアカウントを直接削除（先に新しい管理者を作成済みであることを確認）
curl -u guest:guest -X DELETE http://127.0.0.1:15672/api/users/guest
```

- **どう検証する**：変更後、旧パスワードは 401、新パスワードは 200 でなければなりません。
  **【検証済み】** 本機実測出力：

  ```
  --- 改密前 guest/guest ---          HTTP 200 {"auth_backend":"internal","name":"guest","tags":"administrator"}
  PUT /api/users/guest -> 204
  --- 改密后 guest/guest（应 401）---  HTTP 401
  --- 改密后 guest/s3cret（应 200）--- HTTP 200 {"auth_backend":"internal","name":"guest","tags":"administrator"}
  ```
- [ ] デフォルトアカウントを変更済み/削除済み

### A-2. 最小権限：vhost ごとの `configure` / `write` / `read` 正規表現 【検証済み】

- **なぜ**：3 分類は RabbitMQ に合わせています —— `configure` はトポロジ宣言/削除、`write` は publish とバインド、`read` は消費とプルを管理；
  権限外は 403 を返します。業務アカウントには必要なものだけを開けてください。
- **どうする**：`PUT /api/permissions/{vhost}/{user}`、例えば読み取り専用消費：`{"configure":"^$","write":"^$","read":".*"}`。

```bash
curl -u guest:guest -X PUT http://127.0.0.1:15672/api/permissions/%2F/appuser \
     -H 'Content-Type: application/json' -d '{"configure":"^$","write":"^$","read":".*"}'
```

- **どう検証する**：制限付きアカウントで権限外操作を試み、403 `ACCESS_REFUSED` を得るはずです。
  **【検証済み】** 本機で実 AMQP クライアントを用い `configure="^$"` のユーザーでエクスチェンジを宣言、実測：

  ```
  FAIL 声明 durable 交换机失败: Exception (403) Reason: "ACCESS_REFUSED - access to configure 'r.ex' refused for user 'restricted'"
  ```
- [ ] 各業務アカウントに必要な正規表現のみを付与し、`administrator`/`management` タグを付けていない

### A-3. `administrator` タグの扱い（暗黙の完全権限）—— 付与は慎重に 【検証済み】

- **なぜ**：**`administrator` タグを持つユーザーは、自分に見えるすべての vhost に対して完全な権限を保有し、権限レコードを必要としません**
  （RabbitMQ の実測の扱いに合わせる、README / 設計 M8-7 を参照）。つまり、このタグを与えた時点で
  権限正規表現が機能しなくなります——これが最高権限です。
- **どうする**：管理面/運用アカウントにのみ `administrator` を付与；業務アカウントには一切タグを付けず、権限正規表現のみで運用します。

- **どう検証する（暗黙権限のデモ）**：**権限レコードが一切ない**新規 vhost に対して、`administrator` ユーザーはそのまま利用できるはずです。
  **【検証済み】** 本機実測：新規 vhost `drillvh`（権限レコードを一切作成せず）を作成後、`guest`（administrator）がその上でトポロジを宣言することに成功：

  ```
  --- administrator 隐式权限：guest 在 drillvh 上声明拓扑 ---
  OK  已声明 durable 交换机 a.ex / 队列 a.q，并绑定 key=k   (exit=0)
  ```
- [ ] `administrator` タグはごく少数の運用アカウントにのみ付与

### A-4. `remote_access`：アカウントを本機ログインのみに制限 【未検証（同一機ではリモート来源を模擬できない）】

- **なぜ**：RabbitMQ に合わせ、内蔵 `guest` はデフォルトで本機ログインのみ許可されます；外部デプロイ時は特権アカウントの来源を制限すべきです。
- **どうする / 扱い（重要な制限）**：
  - `remote_access` は**設定ファイル**の `users.<name>.remote_access` にのみ記述でき、**初回ブートストラップ時のみ有効**；
  - **管理 API / `swiftmqctl` で作成したアカウントは一律 `remote_access=true`**（任意の来源からのログインを許可）——
    根拠は `internal/broker/observe.go` の `UpsertUser` のコメントと、実測した `meta/state.json` の
    `"remote_access":true`。つまり **API では現時点で特定のアカウントを本機のみに制限できません**。
- **どう検証する**：**別のホスト**（`127.0.0.1` 以外）からそのアカウントで接続すると 403 となるはずです；本機からの接続は成功するはずです。
  **【未検証】**：本機環境では実際のリモート来源を構築できず、未実測です。
- [ ] 特権アカウントの来源制限を上記の扱いに従って評価済み（API でのアカウント作成はデフォルトでリモートを開放することに注意）

## B. 転送セキュリティ（TLS）

TLS 設定項目（アクセス層と管理面で**同一の**フィールド群を共有）：`cert_file` / `key_file` / `ca_file` / `client_auth` / `min_version`。

### B-1. TLS を有効化し、設定ミス時は起動を拒否 【検証済み】

- **なぜ**：証明書は**起動時**に読み込んで検証されます——設定ミスは即座に起動拒否となり、最初のクライアントが接続してくるまで露見しません。
- **どうする**：`listeners.<plugin>[].tls` または `management.tls` に `cert_file` + `key_file` を提供（**両方**与えた場合のみ有効）。

- **どう検証する**：誤った設定で起動し、即座に失敗するはずです。
  **【検証済み】** 本機で 3 種の誤設定を実測、すべて `exit=1`、起動拒否：

  ```
  badtls1: swiftmqd 启动失败: listeners.amqp091[0].tls 需要同时提供 cert_file 与 key_file
  badtls2: swiftmqd 启动失败: listeners.amqp091[0].tls.min_version 取值非法: "1.0"（可选 1.2 / 1.3）
  badtls3: swiftmqd 启动失败: listeners.amqp091[0].tls 无效: 加载服务端证书失败（cert=... key=...）: open ...: The system cannot find the path specified.
  ```
- **どう検証する（正/逆）**：TLS クライアントは接続でき、平文クライアントが TLS ポートに接続すると拒否されます。
  **【検証済み】** 本機で TLS インスタンスを起動（`amqp091` が TLS を使用）、実クライアントプローブで：

  ```
  === 正向：TLS 客户端跑全量探针 ===      全部通过（25/25）: ...
  === 反向：明文客户端连 TLS 端口（应失败）===  FAIL ... 拨号失败: Exception (501) Reason: "EOF"   (exit=-1)
  ```
- [ ] 対外プロトコルポートで TLS を有効化済み

### B-2. `min_version` は最低 1.2 【検証済み】

- **なぜ**：古すぎる TLS バージョンを無効化；デフォルトで `1.2`、`1.2` / `1.3` を選択可能。
- **どう検証する**：`min_version` を `1.0` にすると、起動時にエラーとなるはずです（B-1 の `badtls2` 出力を参照）。
- [ ] `min_version` は `1.2` または `1.3`

### B-3. 相互認証 `client_auth: require_and_verify`（mTLS） 【一部検証】

- **なぜ**：クライアントに証明書の提示と検証を要求し、未承認クライアントのプロトコルポートへの接続を防ぎます。
- **どうする**：`ca_file` + `client_auth: require_and_verify` を設定（後者は `ca_file` の同時提供を要求）。
- **【検証済み】**：TLS のエンドツーエンドと拒否パスは実クライアントで検証済み（B-1）。**mTLS（クライアント証明書の要求と検証）は本機で個別にドリルしていません**。
- [ ] mTLS が必要なポートに `require_and_verify` + `ca_file` を設定済み

### B-4. 管理面 TLS 【未検証】

- **なぜ**：管理面は Basic Auth でパスワードを送るため、暗号化が必須です。
- **どうする**：`management.tls` にプロトコルリスナーと同じフィールドを使用。
- **【未検証】**：本機ドリルでは管理面を本機の平文ポートにバインドし、管理面 HTTPS を個別に起動していません。
- [ ] 管理面で TLS を有効化済み（または信頼できるネットワーク内に厳格に制限済み）

## C. 露出面の収束

### C-1. 管理面リスニング範囲の収束 【検証済み（リスニングアドレス実測）】

- **なぜ**：管理面はデフォルトで `:15672`（すべての NIC）。対外デプロイでは内部/ループバックアドレスにバインドするか、ファイアウォールで来源を制限すべきです。
- **どうする**：`management.addr` を `127.0.0.1:15672` または内部アドレスに設定；または `management.enabled=false` で完全に無効化
  （無効化すると管理ポートがなくなり、`swiftmqctl` も使用できなくなります）。
- **どう検証する**：
  **【検証済み】** 本機で管理面を `127.0.0.1:15677` に設定し、リスニングアドレスが確かにループバックであることを実測：

  ```
  LocalAddress LocalPort
  ------------ ---------
  127.0.0.1        15677
  ```
- [ ] 管理面のバインドアドレスを収束済み（または停止済み）

### C-2. プロトコルポートは必要なものだけを開く 【未検証】

- **なぜ**：デフォルトで AMQP `5672` と MQTT `1883` を同時に開きます；MQTT を使わないなら無効化し、攻撃面を減らします。
- **どうする**：`plugins.mqtt.enabled=false`（または `listeners` から削除）；無効化は**実際のポートを閉じる**もので、状態ビットを変えるだけではありません。
- **どう検証する**：無効化後、対応するポートがリッスンしなくなります（`Get-NetTCPConnection -State Listen` に見えない）。
  **【未検証】**：本機ドリルでは両プロトコルとも有効にしており、無効化後のポート消失を個別に検証していません。
- [ ] 未使用のプロトコルプラグインを無効化済み

## D. コンテナ実行の強化

リポジトリイメージの事実（`Dockerfile`）：静的リンクバイナリ + alpine、**非 root（uid 10001、ユーザー `swiftmq`）で実行**、
データディレクトリ `/var/lib/swiftmq` はボリューム。`docker-compose.yml` は**名前付きボリューム**で永続化、設定は**読み取り専用マウント**、ログローテーション。

### D-1. 非 root 実行 【未検証（本機未 Docker 実行）】

- **なぜ**：最小権限、コンテナ脱出後の影響範囲を低減。
- **どうする**：イメージはデフォルトで既に uid 10001；`--user root` で上書き**しないでください**。
- **どう検証する**：`docker compose run -T --rm broker id` が `uid=10001` を示すはずです。（`run` は非対話環境では必ず `-T` を付ける）
- [ ] コンテナを非 root で実行（root で上書きしていない）

### D-2. 読み取り専用ルートファイルシステム + リソース制限 + 能力の削減（推奨、リポジトリの compose ではデフォルト無効） 【未検証】

- **なぜ**：読み取り専用ルートファイルシステムは実行期のバイナリ改ざんを防ぎ；リソース制限は単一コンテナがホストをダウンさせるのを防ぎ；capabilities の削減はカーネル攻撃面を減らします。
- **どうする**（例、必要に応じて compose の `broker` サービスに統合）：

```yaml
services:
  broker:
    read_only: true
    tmpfs:
      - /tmp
    security_opt:
      - no-new-privileges:true
    cap_drop: ["ALL"]
    deploy:
      resources:
        limits:
          cpus: "4"
          memory: 8g
```

- **どう検証する**：コンテナ内でルートパスへの書き込みが失敗するはずです（読み取り専用）；`docker inspect` でリソース制限が確認できます。
  **【未検証】**（本機未 Docker 実行）；かつ**読み取り専用ルートファイルシステムでは `data_dir` が書き込み可能なボリューム上にあることを確認する必要があります**、そうでないとカーネルがディスクに書き込めません。
- [ ] 読み取り専用ルートファイルシステムとリソース制限を評価済み（`data_dir` は書き込み可能ボリュームにある必要があることに注意）

## E. 既知の制限（現時点で実現できない、期待しないこと）

以下はいずれも**事実上のギャップ**であり、セキュリティ設計において明示的に認識し、存在を仮定しないでください：

1. **パスワードは平文で保存・複製されます**。`meta/state.json` の `password` フィールドは平文（**【検証済み】** 実測で
   `"password":"drillpass"` が見える）；設定ファイル内も平文です。パスワードハッシュは**ありません**（ハッシュと外部認証バックエンドは認証プラグインに委ねます）。
   → 結果：**データディレクトリとバックアップファイルは機密クレデンシャルと同等**であり、ファイル権限と暗号化保護が必須です。
2. **監査ログはありません**。管理面の追加/削除/変更は通常のログ（例 `管理面更新用户 actor=... user=...`）を出力しますが、
   **独立した、改ざん不可の監査ストリームはなく**、「誰がいつ何を変更したか」のコンプライアンス級の記録もありません。
3. **LDAP / OAuth2 / JWT などの外部認証はありません**。v1 の内蔵は `PLAIN` / `AMQPLAIN` のみ
   （`auth.Store.Mechanisms()` は実測でこの 2 つのみを返す）。
4. **SASL `EXTERNAL` は未実装**：mTLS を設定しても、プロトコル層は**依然として PLAIN パスワード認証を行います**
   （「クライアント証明書でパスワード不要」のステップはない）。証明書はトランスポート層の検証のみです。
5. **`remote_access` は API 経由で設定できない**：管理 API/CLI で作成したアカウントは一律リモートログインを許可（A-4 を参照）、
   個々のアカウントを本機のみに制限できません。
6. **管理面に独立した来源ホワイトリスト / レート制限はない**：バインドアドレス、ファイアウォール、TLS のみで露出面を収束できます。
7. **プラグインサンドボックスなし**：A 形態プラグインはカーネルと同一プロセス；B 形態外部プラグインはプロセス分離があるものの**データ面は本機接続プロキシ経由**で、
   かつプラグインはカーネルセマンティクスを呼び出せます（vhost と権限検証の制約を受ける）、**安全サンドボックスではありません**。
8. **管理面タグは `administrator`/`management`/`monitoring` の 3 段のみ**で、より細かい per-resource RBAC はありません。
