# خط أساس تقوية أمان SwiftMQ (قائمة قابلة للتأشير)

> المبدأ: **اكتب فقط القدرات الموجودة فعلًا في هذا المستودع**. ولكل بند بيان «لماذا نفعل ذلك + كيف نتحقق من إنجازه»، وأوامر التحقق كلها قابلة للتشغيل.
> وتشير علامة **【مُتحقَّق منه】** إلى أنه **قد نُفِّذ فعلًا** على هذا الجهاز (Windows + PowerShell 5.1، `1.0.0`)؛
> وتشير **【غير مُتحقَّق منه】** إلى أنه لم يُنفَّذ أو يتعذّر حاليًا، ولا ندّعي خلاف ذلك أبدًا.
> كل الأوامر تُعطى بنسخة curl بأسلوب `/bin/sh`، مع إرفاق نسخة PowerShell (في PowerShell 5.1 استخدم
> `Invoke-WebRequest ... -UseBasicParsing`).

## A. المصادقة والتحكم في الوصول

### A-1. تغيير الحساب الافتراضي `guest/guest` 【مُتحقَّق منه】

- **لماذا**: مدمج افتراضيًا `guest/guest` (بوسم `administrator`)، وكشفه للخارج يعني ترك الباب مفتوحًا على مصراعيه.
- **كيف**: غيّر كلمة المرور / احذف الحساب وقت التشغيل، و**لا** تعدّل ملف الإعداد (`users` فعّالة عند الإقلاع الأول فقط).

```bash
# تغيير كلمة المرور
curl -u guest:guest -X PUT http://127.0.0.1:15672/api/users/guest \
     -H 'Content-Type: application/json' -d '{"password":"<新口令>","tags":["administrator"]}'
# أو احذف الحساب الافتراضي مباشرة (تأكد أولًا من إنشاء مدير جديد)
curl -u guest:guest -X DELETE http://127.0.0.1:15672/api/users/guest
```

- **كيف تتحقق**: بعد التغيير يجب أن تُرجع كلمة المرور القديمة 401، والجديدة 200.
  **【مُتحقَّق منه】** مخرجات الاختبار الفعلي على هذا الجهاز:

  ```
  --- 改密前 guest/guest ---          HTTP 200 {"auth_backend":"internal","name":"guest","tags":"administrator"}
  PUT /api/users/guest -> 204
  --- 改密后 guest/guest（应 401）---  HTTP 401
  --- 改密后 guest/s3cret（应 200）--- HTTP 200 {"auth_backend":"internal","name":"guest","tags":"administrator"}
  ```
- [ ] تم تغيير الحساب الافتراضي/حذفه

### A-2. أقل صلاحية: تعبيرات `configure` / `write` / `read` النمطية حسب vhost 【مُتحقَّق منه】

- **لماذا**: التصنيف الثلاثي محاذٍ لـ RabbitMQ —— `configure` يدير إعلان/حذف الطوبولوجيا، و`write` يدير النشر والارتباط، و`read` يدير الاستهلاك والسحب؛
  وتجاوز الصلاحية يُرجع 403. امنح حساب الأعمال ما يحتاجه فقط.
- **كيف**: `PUT /api/permissions/{vhost}/{user}`، مثال للاستهلاك للقراءة فقط: `{"configure":"^$","write":"^$","read":".*"}`.

```bash
curl -u guest:guest -X PUT http://127.0.0.1:15672/api/permissions/%2F/appuser \
     -H 'Content-Type: application/json' -d '{"configure":"^$","write":"^$","read":".*"}'
```

- **كيف تتحقق**: اعتزم عملية متجاوزة بحساب مقيَّد، فينبغي أن تحصل على 403 `ACCESS_REFUSED`.
  **【مُتحقَّق منه】** على هذا الجهاز، باستخدام عميل AMQP حقيقي وبمستخدم ذي `configure="^$"`، حاول الإعلان عن مبادل، فكانت المخرجات:

  ```
  FAIL 声明 durable 交换机失败: Exception (403) Reason: "ACCESS_REFUSED - access to configure 'r.ex' refused for user 'restricted'"
  ```
- [ ] كل حساب أعمال مُنح فقط التعبيرات النمطية اللازمة، ولم يُمنح وسم `administrator`/`management`

### A-3. ضبط وسم `administrator` (صلاحية كاملة ضمنية) —— يُمنح بحذر 【مُتحقَّق منه】

- **لماذا**: **المستخدم الحامل لوسم `administrator` يملك صلاحية كاملة على كل vhost مرئي له، دون حاجة إلى سجلات أذونات**
  (محاذٍ لضبط RabbitMQ المُختبَر، انظر README / التصميم M8-7). أي أنه بمجرد منح هذا الوسم،
  تتوقف التعبيرات النمطية للأذونات عن العمل — فهو أعلى صلاحية.
- **كيف**: لا تمنح `administrator` إلا لحسابات الواجهة الإدارية/العمليات؛ أما حسابات الأعمال فلا تُمنح أوسمة إطلاقًا، وتُدار بالتعبيرات النمطية فقط.

- **كيف تتحقق (إظهار الصلاحية الضمنية)**: على vhost جديد **بلا أي سجل أذونات**، ينبغي أن يكون مستخدم `administrator` صالحًا مباشرة.
  **【مُتحقَّق منه】** الاختبار الفعلي على هذا الجهاز: بعد إنشاء vhost `drillvh` (دون إنشاء أي سجل أذونات)، نجح `guest` (administrator) في الإعلان عن طوبولوجيا عليه:

  ```
  --- administrator 隐式权限：guest 在 drillvh 上声明拓扑 ---
  OK  已声明 durable 交换机 a.ex / 队列 a.q，并绑定 key=k   (exit=0)
  ```
- [ ] وسم `administrator` ممنوح لعدد قليل جدًا من حسابات العمليات فقط

### A-4. `remote_access`: قصر تسجيل الدخول على الجهاز المحلي 【غير مُتحقَّق منه (يتعذّر محاكاة مصدر بعيد من الجهاز نفسه)】

- **لماذا**: محاذاةً لـ RabbitMQ، يسمح `guest` المدمج افتراضيًا بتسجيل الدخول من الجهاز المحلي فقط؛ وعند النشر الخارجي ينبغي ضمان تقييد مصادر الحسابات ذات الصلاحيات.
- **كيف / الضبط (قيد مهم)**:
  - لا يمكن كتابة `remote_access` إلا في **ملف الإعداد** ضمن `users.<name>.remote_access`، و**فعّال عند الإقلاع الأول فقط**؛
  - **أي حساب يُنشأ عبر واجهة API الإدارية / `swiftmqctl` يكون دائمًا `remote_access=true`** (يسمح بتسجيل الدخول من أي مصدر) ——
    استنادًا إلى تعليق `UpsertUser` في `internal/broker/observe.go` وإلى `"remote_access":true`
    المُشاهَد فعليًا في `meta/state.json`. أي أن **واجهة API لا تستطيع حاليًا قصر حساب على الجهاز المحلي**.
- **كيف تتحقق**: الاتصال من **جهاز آخر** (غير `127.0.0.1`) بذلك الحساب ينبغي أن يُرفض بـ 403؛ والاتصال المحلي ينبغي أن ينجح.
  **【غير مُتحقَّق منه】**: لا تستطيع بيئة هذا الجهاز إنشاء مصدر بعيد حقيقي، فلم يُختبَر فعليًا.
- [ ] قُيِّم تقييد مصادر الحسابات ذات الصلاحيات وفق الضبط أعلاه (لاحظ أن إنشاء الحسابات عبر API يفتح البعيد افتراضيًا)

## B. أمان النقل (TLS)

عناصر إعداد TLS (تشترك طبقة الاتصال والواجهة الإدارية في **نفس** مجموعة الحقول): `cert_file` / `key_file` / `ca_file` / `client_auth` / `min_version`.

### B-1. تمكين TLS والرفض عند بدء التشغيل حال أي خطأ في الإعداد 【مُتحقَّق منه】

- **لماذا**: تُقرأ الشهادات وتُتحقَّق **عند بدء التشغيل** —— فالخطأ في الإعداد يرفض بدء التشغيل فورًا، لا أن ينكشف بعد اتصال أول عميل.
- **كيف**: وفّر `cert_file` + `key_file` في `listeners.<plugin>[].tls` أو `management.tls` (ولا يُفعَّل إلا **بتقديمهما معًا**).

- **كيف تتحقق**: ابدأ التشغيل بإعداد خاطئ، فينبغي أن يفشل فورًا.
  **【مُتحقَّق منه】** على هذا الجهاز، اختُبرت ثلاثة إعدادات خاطئة، وكلها `exit=1` ورفضت بدء التشغيل:

  ```
  badtls1: swiftmqd 启动失败: listeners.amqp091[0].tls 需要同时提供 cert_file 与 key_file
  badtls2: swiftmqd 启动失败: listeners.amqp091[0].tls.min_version 取值非法: "1.0"（可选 1.2 / 1.3）
  badtls3: swiftmqd 启动失败: listeners.amqp091[0].tls 无效: 加载服务端证书失败（cert=... key=...）: open ...: The system cannot find the path specified.
  ```
- **كيف تتحقق (اتجاهان)**: يستطيع عميل TLS الاتصال، ويُرفض اتصال عميل النص الصريح بمنفذ TLS.
  **【مُتحقَّق منه】** على هذا الجهاز شُغِّلت نسخة بـ TLS (`amqp091` عبر TLS)، وبمسبار عميل حقيقي:

  ```
  === 正向：TLS 客户端跑全量探针 ===      全部通过（25/25）: ...
  === 反向：明文客户端连 TLS 端口（应失败）===  FAIL ... 拨号失败: Exception (501) Reason: "EOF"   (exit=-1)
  ```
- [ ] منافذ البروتوكول المكشوفة للخارج مفعّل عليها TLS

### B-2. ألا تقل `min_version` عن 1.2 【مُتحقَّق منه】

- **لماذا**: لتعطيل إصدارات TLS القديمة جدًا؛ والافتراضي هو `1.2`، والاختيار بين `1.2` / `1.3`.
- **كيف تتحقق**: اكتب `min_version` بالقيمة `1.0`، فينبغي أن يخطئ بدء التشغيل (انظر مخرجات `badtls2` في B-1).
- [ ] `min_version` هي `1.2` أو `1.3`

### B-3. المصادقة المتبادلة `client_auth: require_and_verify` (mTLS) 【تحقق جزئي】

- **لماذا**: لطلب تقديم العميل لشهادته والتحقق منها، منعًا لاتصال عملاء غير مصرّح لهم بمنافذ البروتوكول.
- **كيف**: اضبط `ca_file` + `client_auth: require_and_verify` (ويطلب الأخيران معًا تقديم `ca_file`).
- **【مُتحقَّق منه】**: تحقّق مسار TLS من الطرف إلى الطرف والمسار المرفوض بعميل حقيقي (B-1). أما **mTLS (طلب شهادة العميل والتحقق منها) فلم يُمرَّن عليه بمفرده على هذا الجهاز**.
- [ ] المنافذ التي تحتاج mTLS مضبوطة على `require_and_verify` + `ca_file`

### B-4. TLS للواجهة الإدارية 【غير مُتحقَّق منه】

- **لماذا**: تمرر الواجهة الإدارية كلمة المرور عبر Basic Auth، فيجب تشفيرها.
- **كيف**: تستخدم `management.tls` نفس حقول مستمع البروتوكول.
- **【غير مُتحقَّق منه】**: ربط التمرين على هذا الجهاز الواجهة الإدارية بمنفذ نص صريح محلي، ولم تُشغَّل HTTPS للواجهة الإدارية بمفردها.
- [ ] الواجهة الإدارية مفعّل عليها TLS (أو مقيَّدة بصرامة داخل شبكة موثوقة)

## C. تقليص سطح التعرّض

### C-1. تقليص نطاق استماع الواجهة الإدارية 【مُتحقَّق منه (اختبار فعلي لعنوان الاستماع)】

- **لماذا**: الواجهة الإدارية افتراضيًا `:15672` (كل بطاقات الشبكة). وعند النشر الخارجي ينبغي ربطها بعنوان الشبكة الداخلية/العنوان الرجعي، أو تقييد المصادر بجدار ناري.
- **كيف**: اضبط `management.addr` على `127.0.0.1:15672` أو عنوان الشبكة الداخلية؛ أو أغلقها تمامًا بـ `management.enabled=false`
  (فبعد الإغلاق لا يوجد منفذ إداري، لكن `swiftmqctl` يصبح غير متاح تبعًا لذلك).
- **كيف تتحقق**:
  **【مُتحقَّق منه】** على هذا الجهاز ضُبطت الواجهة الإدارية على `127.0.0.1:15677`، فكان عنوان الاستماع المُختبَر فعليًا هو العنوان الرجعي:

  ```
  LocalAddress LocalPort
  ------------ ---------
  127.0.0.1        15677
  ```
- [ ] عنوان ارتباط الواجهة الإدارية مُقلَّص (أو معطَّل)

### C-2. فتح منافذ البروتوكول الضرورية فقط 【غير مُتحقَّق منه】

- **لماذا**: يفتح افتراضيًا AMQP `5672` وMQTT `1883` معًا؛ فإن لم تستخدم MQTT فأغلقه لتقليل سطح الهجوم.
- **كيف**: `plugins.mqtt.enabled=false` (أو إزالته من `listeners`)؛ فالتعطيل **يُغلق المنفذ الفعلي** لا أنه يغيّر بتّ حالة فقط.
- **كيف تتحقق**: بعد التعطيل لا يبقى المنفذ المقابل في وضع الاستماع (لا يظهر في `Get-NetTCPConnection -State Listen`).
  **【غير مُتحقَّق منه】**: أبقى التمرين على هذا الجهاز البروتوكولين مفتوحين، ولم يُتحقق بمفرده من اختفاء المنفذ بعد الإغلاق.
- [ ] إضافات البروتوكول غير المستخدمة معطَّلة

## D. تقوية تشغيل الحاويات

حقائق صورة المستودع (`Dockerfile`): ملف تنفيذي مرتبط ساكنًا + alpine، و**تعمل بمستخدم غير root (uid 10001، المستخدم `swiftmq`)**،
ودليل البيانات `/var/lib/swiftmq` حجم. ويستخدم `docker-compose.yml` **حجمًا مُسمّى** للاستدامة، و**تركيبًا للقراءة فقط** للإعداد، وتدويرًا للسجلات.

### D-1. التشغيل بمستخدم غير root 【غير مُتحقَّق منه (لم يُشغَّل Docker على هذا الجهاز)】

- **لماذا**: أقل صلاحية، لتقليل الأثر بعد هروب الحاوية.
- **كيف**: الصورة افتراضيًا uid 10001؛ و**لا** تتجاوزه بـ `--user root`.
- **كيف تتحقق**: ينبغي أن يُظهر `docker compose run -T --rm broker id` القيمة `uid=10001`. (يجب إضافة `-T` إلى `run` في البيئة غير التفاعلية)
- [ ] الحاوية تعمل بمستخدم غير root (دون تجاوز بـ root)

### D-2. نظام ملفات جذر للقراءة فقط + حدود الموارد + تقليص القدرات (توصية، وcompose في المستودع لا يفعّلها افتراضيًا) 【غير مُتحقَّق منه】

- **لماذا**: نظام ملفات الجذر للقراءة فقط يمنع تلاعب وقت التشغيل بالملف التنفيذي؛ وحدود الموارد تمنع إسقاط حاوية واحدة للمضيف؛ وتقليص capabilities يقلّل سطح هجوم النواة.
- **كيف** (مثال، ادمجه حسب الحاجة في خدمة `broker` بملف compose):

```yaml
services:
  broker:
    read_only: true
    tmpfs:
      - /tmp
    security_opt:
      - no-new-privileges:true
    cap_drop: ["ALL"]
    deploy:
      resources:
        limits:
          cpus: "4"
          memory: 8g
```

- **كيف تتحقق**: محاولة الكتابة إلى مسار الجذر داخل الحاوية ينبغي أن تفشل (قراءة فقط)؛ و`docker inspect` يُظهر حدود الموارد.
  **【غير مُتحقَّق منه】** (لم يُشغَّل Docker على هذا الجهاز)؛ و**يتطلب نظام ملفات الجذر للقراءة فقط التأكد من أن `data_dir` على حجم قابل للكتابة**، وإلا تعذّر على النواة الحفظ على القرص.
- [ ] قُيِّم نظام ملفات الجذر للقراءة فقط وحدود الموارد (لاحظ أن `data_dir` يجب أن يكون على حجم قابل للكتابة)

## E. القيود المعروفة (متعذّرة فعلًا حاليًا، فلا تعوّل عليها)

كل ما يلي **ثغرات واقعية**، فاعترف بها صراحةً في التصميم الأمني، ولا تفترض وجودها:

1. **كلمات المرور تُخزَّن وتُنسخ كنص صريح**. حقل `password` في `meta/state.json` نص صريح (**【مُتحقَّق منه】** يظهر في الاختبار
   `"password":"drillpass"`)؛ وكذلك في ملف الإعداد. و**لا يوجد** تجزئة (hash) لكلمات المرور (فالتجزئة وواجهات المصادقة الخارجية متروكة لإضافة المصادقة).
   → النتيجة: **دليل البيانات وملفات النسخ الاحتياطي تعدّ بيانات اعتماد حساسة**، ويجب حمايتها بأذونات الملفات والتشفير.
2. **لا يوجد سجل تدقيق**. تسجّل الواجهة الإدارية عمليات الإضافة/الحذف/التعديل في السجلات العادية (مثل `管理面更新用户 actor=... user=...`)،
   لكن **لا يوجد** تدفق تدقيق مستقل غير قابل للتلاعب، ولا سجلات بمستوى الامتثال تفيد «مَن عدّل ماذا ومتى».
3. **لا توجد مصادقة خارجية مثل LDAP / OAuth2 / JWT**. فالإصدار v1 مدمج فيه `PLAIN` / `AMQPLAIN` فقط
   (ويُرجع `auth.Store.Mechanisms()` في الاختبار هذين فقط).
4. **`EXTERNAL` في SASL غير مُنفَّذ**: حتى مع ضبط mTLS، تبقى طبقة البروتوكول **تجري مصادقة PLAIN بكلمة المرور**
   (فخطوة «الاستغناء عن كلمة المرور بشهادة العميل» غير موجودة). والشهادة مجرد تحقق في طبقة النقل.
5. **`remote_access` لا يمكن ضبطه عبر API**: فالحسابات المنشأة عبر واجهة API الإدارية/CLI تسمح دائمًا بالدخول البعيد (انظر A-4)،
   ويتعذّر قصر حساب واحد على الجهاز المحلي.
6. **لا قائمة مصادر مسموحة مستقلة للواجهة الإدارية / ولا تحديد معدل**: لا سبيل إلا بـ ارتباط العنوان والجدار الناري وTLS لتقليص سطح التعرّض.
7. **لا صندوق رمل (sandbox) للإضافات**: إضافات الشكل A في نفس عملية النواة؛ وإضافات الشكل B الخارجية، وإن كان فيها عزل للعمليات، فإن **مستوى البيانات يمر عبر وكيل اتصال محلي**،
   ويمكن للإضافة استدعاء دلالات النواة (مقيَّدة بتحقق vhost والأذونات)، و**ليست** صندوق رمل أمنيًا.
8. **أوسمة الواجهة الإدارية ثلاث درجات فقط `administrator`/`management`/`monitoring`**، ولا يوجد RBAC أدق لكل مورد.

## F. القائمة المجمّعة

- [ ] A-1 تغيير/حذف الحساب الافتراضي 【مسار مُتحقَّق منه】
- [ ] A-2 أقل صلاحية لحسابات الأعمال (تعبيرات نمطية)، بلا وسم مدير 【مسار 403 مُتحقَّق منه】
- [ ] A-3 وسم `administrator` يُمنح لحسابات العمليات فقط 【ضبط الصلاحية الضمنية مُتحقَّق منه】
- [ ] A-4 قُيِّم تقييد مصادر الحسابات ذات الصلاحيات (لاحظ أن إنشاء الحسابات عبر API يفتح البعيد افتراضيًا)
- [ ] B-1 تمكين TLS على المنافذ المكشوفة، مع الرفض عند بدء التشغيل حال خطأ الإعداد 【مُتحقَّق منه】
- [ ] B-2 `min_version` ≥ 1.2 【مُتحقَّق منه】
- [ ] B-3 المنافذ التي تحتاج mTLS مضبوطة على `require_and_verify` + `ca_file`
- [ ] B-4 تمكين TLS على الواجهة الإدارية
- [ ] C-1 تقليص عنوان ارتباط الواجهة الإدارية 【عنوان الاستماع مُتحقَّق منه】
- [ ] C-2 تعطيل إضافات البروتوكول غير المستخدمة
- [ ] D-1 تشغيل الحاوية بمستخدم غير root
- [ ] D-2 تقييم نظام ملفات الجذر للقراءة فقط / حدود الموارد / تقليص القدرات
- [ ] E الاعتراف في التصميم الأمني بالقيود المعروفة (كلمات مرور كنص صريح، بلا تدقيق، بلا LDAP/OAuth2، وSASL EXTERNAL غير مُنفَّذ)
