# Руководство по разработке внешних процессных плагинов (sidecar) для SwiftMQ

> **Для кого**: для разработчиков, которые не хотят форкать / перекомпилировать ядро и желают расширять возможности SwiftMQ на **любом языке**.
> **Область**: в этом документе рассматривается только одна форма плагина — **внешний процессный плагин** (термин ядра `sidecar`). Встроенные протокольные плагины ядра (AMQP 0-9-1 / MQTT) в область не входят.
> **Как читать**: разделы 1–2 формируют ментальную модель, раздел 3 — про написание кода, а **раздел 5 посвящён тому, "как после разработки подключить плагин и запустить его вместе с ядром, чтобы он обслуживал клиентов"**;
> **для других языков (Python / Node.js / PHP / Java) смотрите языковые руководства в §4** (каждое идёт с полностью проверенным на практике примером проекта).
> Код в документе — минимальный рабочий скелет, который можно скопировать как отправную точку. Исходный язык — упрощённый китайский.

---

## 1. Что это такое

**Отдельный процесс**, который реализует в своём собственном процессе некий "протокол" (разбирает поток байтов от клиента).
Ядро по конфигурации берёт его под управление: **порты открывает ядро, соединения проксирует ядро**, а регистрация / запуск-остановка / аудит / изоляция целиком переиспользуют уже существующие механизмы ядра.

Сначала зафиксируем три правильные ментальные модели (там, где ошибиться проще всего):

1. **Процесс плагина — это "локальный сервис"**: он слушает только **локальный адрес** (TCP или unix socket) и ждёт, **пока ядро подключится**.
   Направление соединения — **ядро (клиент) → плагин (сервер)**, и рукопожатие также первым отправляет ядро.
2. **Внешний бизнес-порт открывает не плагин**: его создаёт **ядро** по `protocols[].listeners` из конфигурации и отображает наружу для клиентов.
   Клиенты подключаются к **порту ядра**, а байты проксируются ядром в процесс плагина. Процессу плагина **не нужно** самому открывать бизнес-порт.
3. **Семантика необязательна**: плагин может просто "перекладывать байты" (полностью реализуя протокол самостоятельно),
   а может через **обратные вызовы** к `session.*` дотянуться до семантики ядра (очереди / маршрутизация / права / подтверждения),
   обладая **абсолютно той же семантикой**, что и встроенные протокольные плагины (поэтому vhost, права, маршрутизация и поведение очередей не разойдутся).

| Преимущества | Издержки |
| --- | --- |
| Расширение без изменения и перекомпиляции ядра | Ещё одно локальное копирование байтов на плоскости данных (проксирование ядром, без передачи fd, единообразно на всех платформах) |
| Реализация на любом языке (нужно лишь реализовать проводной протокол) | Ещё один локальный RPC на каждый обратный вызов (кодирование/декодирование JSON + копирование) |
| Плагин можно независимо выпускать / обновлять / перезапускать | Сниффинг остаётся на стороне ядра: распознавание возможно только по "префиксу" или "выделенному порту" |
| Падение затрагивает только этот плагин: ядро помечает его `down` и не завершается и не падает | Реально действует только возможность `net.listen`, остальные значения возможностей зарезервированы (см. §7) |

## 2. Как это работает

Установление соединения (**ядро — клиент, плагин — сервер**):

```
内核：读配置 plugins.<名>.sidecar
      ├─（可选）spawn 拉起子进程
      └─ dial(address)
插件：sidecar.NewServer 监听 address（Accept）
```

Рукопожатие:

```
内核 ──Hello(kind=1)─────►  插件 Handler.Hello
内核 ◄─HelloAck(kind=2)──   插件（拒绝接入时回 error，内核据此隔离该插件）
```

Начало обслуживания:

```
内核：按配置 protocols 注册协议 + 创建对外监听（对外端口由内核打开）

客户端 ─► 内核端口 ─嗅探(prefix)─► 建流 Open ─► 插件 Handler.Open(Stream)
                                                  │
  插件 ─反向调用 session.*（BridgeFromContext）─► 内核（队列 / 路由 / 权限 / 确认）
  内核 ─投递回推 session.deliver ──────────────► 插件 Handler.Call
  插件 ─结算 session.settle ───────────────────► 内核
```

**Жизненный цикл** (хост на стороне ядра `internal/plugin/sidecar`):

```
Load → Init：spawn(可选) → dial(address) → 握手 → 按配置注册 protocols（此时才起对外监听）
     → Start：起监督协程（断线重连 / 退避）
     → [运行期] 断线 → 状态 down → 退避重连（restart=always）或等待运维（restart=never）
     → Stop（内核退出）：断开连接、回收桥上会话与未结算投递、终止由内核拉起的子进程
```

**Семантика состояний** (видна в `swiftmqctl plugins show`):

| Состояние | Значение | Действие эксплуатации |
| --- | --- | --- |
| `enabled` | подключён и обслуживает | — |
| `failed` | **не поднялся при запуске** (ошибка конфигурации / рукопожатие отклонено / процесс не запускается) | смотреть `RuntimeNote` и журнал ядра, исправить конфигурацию или плагин; повторная попытка только после перезапуска ядра |
| `down` | **поднимался, но сейчас отсутствует** (процесс упал / соединение разорвано) | запустить процесс плагина; ядро восстановит его согласно политике `restart` |
| `disabled` | в конфигурации `enabled=false` или горячее отключение эксплуатацией | восстановить через `plugins enable <имя>` |

## 3. Разработка (Go)

### 3.1 Создание проекта

Плагин — это **отдельный Go-модуль**, зависящий только от двух публичных контрактных пакетов:

- `github.com/houzch/swiftmq/pkg/sidecar` — проводной протокол и реализация на стороне плагина (**обязательно**)
- `github.com/houzch/swiftmq/pkg/plugin` — только если вам нужны типы вроде `plugin.Message` / `plugin.Error` (необязательно)

```
my-sidecar/
├── go.mod          # module my-sidecar；require github.com/houzch/swiftmq（或 replace 指到本地源码）
├── main.go         # 启动 sidecar.Server
└── handler.go      # 实现 sidecar.Handler
```

```bash
go mod init my-sidecar
go get github.com/houzch/swiftmq@v1.1.01
# 本地联调时可改用 replace 指向源码：
#   go mod edit -replace github.com/houzch/swiftmq=../swiftmq
```

> При совместной отладке через `replace` плагин и ядро должны использовать **один и тот же исходный код**, иначе версия API (`v1`) может совпадать, а типы — отличаться.

### 3.2 Реализация `Handler` (три метода)

Вся бизнес-поверхность процесса плагина — это `Hello` / `Call` / `Open` из `sidecar.Handler`.
Рукопожатие, heartbeat, мультиплексирование и разбиение на блоки обрабатывает `pkg/sidecar`, вам не нужно трогать кадры.

```go
package main

import (
	"context"
	"encoding/json"
	"fmt"
	"log"
	"os"
	"os/signal"
	"strings"
	"sync/atomic"
	"syscall"

	"github.com/houzch/swiftmq/pkg/sidecar"
)

const (
	pluginName = "my-sidecar" // 必须与内核配置里的插件名一致
	version    = "0.1.0"
	apiVersion = "v1" // 必须等于 sidecar / plugin 的 APIVersion
	protocol   = "myproto" // 应与配置里 protocols[].name 一致
)

func main() {
	addr := ":19001" // 内核来连的本机地址；可用 -addr 覆盖
	handler := &handler{}

	srv, err := sidecar.NewServer(handler, sidecar.ServerOptions{
		Address: "tcp://" + addr,
		Logger:  stdLogger{log.New(os.Stdout, "", log.LstdFlags|log.Lmicroseconds)},
	})
	if err != nil {
		fmt.Fprintf(os.Stderr, "my-sidecar 监听失败: %v\n", err)
		os.Exit(1)
	}
	// Address() 能读回实际地址（配置里写 :0 时有用）。
	log.Printf("my-sidecar 已启动 name=%s version=%s addr=%s", pluginName, version, srv.Address())

	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
	defer stop()
	if err := srv.Serve(ctx); err != nil {
		fmt.Fprintf(os.Stderr, "my-sidecar 服务退出: %v\n", err)
		os.Exit(1)
	}
}

type handler struct {
	streams atomic.Int64
}

var _ sidecar.Handler = (*handler)(nil)

// Hello 处理握手：返回的 HelloAck 发给内核。返回 error 即拒绝接入（内核会明确隔离该插件）。
func (h *handler) Hello(_ context.Context, hello sidecar.Hello) (sidecar.HelloAck, error) {
	// 内核版本过旧时可以拒绝，避免带着不兼容跑起来。
	if hello.Plugin != pluginName {
		return sidecar.HelloAck{}, fmt.Errorf("插件名不匹配：内核声明 %q，本插件是 %q", hello.Plugin, pluginName)
	}
	if hello.APIVersion != apiVersion {
		return sidecar.HelloAck{}, fmt.Errorf("插件 API 版本不匹配：内核 %q，插件 %q", hello.APIVersion, apiVersion)
	}
	return sidecar.HelloAck{
		Name:         pluginName,
		Version:      version,
		APIVersion:   apiVersion,
		Capabilities: []string{"net.listen"},
		Protocols:    []string{protocol}, // 展示用；真正生效的是内核配置里的 protocols
		Methods:      []string{"stats"},  // 展示用；内核不提供通用调用入口
	}, nil
}

// Call 处理方法调用。约定的系统方法 session.deliver 是"内核把消费投递回推给插件"，
// 必须在实现里处理（见 §3.4）。
func (h *handler) Call(ctx context.Context, method string, params json.RawMessage) (any, error) {
	switch method {
	case sidecar.MethodSessionDeliver:
		return h.handleDeliver(ctx, params)
	case "stats":
		return map[string]any{"streams": h.streams.Load()}, nil
	default:
		// 未知方法必须明确报错：静默成功会让调用方以为生效了。
		return nil, fmt.Errorf("未知方法 %q", method)
	}
}

// Open 处理一条新打开的流：一条流 = 内核侧的一条客户端连接。
// 通常**阻塞处理到流结束**再返回；返回后该流即结束（内核会关闭对应的客户端连接）。
func (h *handler) Open(ctx context.Context, stream *sidecar.Stream, meta sidecar.Open) error {
	h.streams.Add(1)
	// meta.Remote / meta.Local 是两端地址，meta.Peek 是嗅探阶段读到的前缀字节，可用于更细的分支判断。
	return h.serve(stream)
}

// stdLogger 把 pkg/sidecar 的最小日志接口接到标准库日志。
type stdLogger struct{ l *log.Logger }

func (s stdLogger) Info(msg string, args ...any) {
	s.l.Printf("%s %s", msg, strings.TrimRight(fmt.Sprintln(args...), "\n"))
}
func (s stdLogger) Warn(msg string, args ...any) {
	s.l.Printf("WARN %s %s", msg, strings.TrimRight(fmt.Sprintln(args...), "\n"))
}
```

### 3.3 Плоскость данных: чтение и запись `Stream`

`sidecar.Stream` реализует `io.ReadWriteCloser`, так что его можно использовать прямо как "одно соединение":

```go
func (h *handler) serve(stream *sidecar.Stream) error {
	buf := make([]byte, 4096)
	for {
		n, err := stream.Read(buf)
		if n > 0 {
			// 你的协议解析在这里；示例先原样回显。
			if _, werr := stream.Write(buf[:n]); werr != nil {
				return werr
			}
		}
		if err != nil {
			return nil // 对端关闭
		}
	}
}
```

Ключевые моменты:

- Каждое клиентское соединение = один поток (stream); плагин может начать приём и передачу сразу в `Handler.Open`.
- Большие сообщения автоматически разбиваются библиотекой на блоки (каждый кадр ≤ 64 KiB), **потребление памяти не зависит от размера сообщения**.
- Обратное давление: у приёмного буфера одного потока есть верхняя граница; при заполнении буфера блокируется **горутина диспетчеризации** этого соединения (все потоки ждут вместе) —
  это компромисс между "предсказуемой памятью" и "ограничением скорости одного потока", подробнее см. §7.

### 3.4 Использование семантического моста ядра (`session.*`)

Если вы хотите, чтобы плагин переиспользовал семантику очередей / маршрутизации / прав / подтверждений ядра (а не строил свою собственную), используйте **обратные вызовы**.
На потоке их применяют в порядке `session.open` → остальные `session.*` → (`session.close`):

```go
import (
	"errors"

	"github.com/houzch/swiftmq/pkg/plugin"
	"github.com/houzch/swiftmq/pkg/sidecar"
)

func (h *handler) runDemo(ctx context.Context, stream *sidecar.Stream) error {
	br, ok := sidecar.BridgeFromContext(ctx) // 当前流的内核桥（内核在建流时注入 ctx）
	if !ok {
		return errors.New("ctx 中没有内核桥")
	}
	streamID := stream.ID()

	// 1) 认证：连接的内核操作面在认证前没有身份，会话一定打不开。
	//    response 就是你自己协议里的凭据（这里以 SASL PLAIN 为例）。
	plain := append([]byte("\x00guest\x00"), []byte("guest")...)
	var ident sidecar.AuthIdentityDTO
	if err := br.Call(ctx, sidecar.MethodCoreAuthenticate, sidecar.CoreAuthenticateParams{
		Stream: streamID, Mechanism: "PLAIN", Response: plain,
	}, &ident); err != nil {
		return err
	}

	// 2) 打开会话（内核会做与内置协议插件相同的权限校验）
	if err := br.Call(ctx, sidecar.MethodSessionOpen,
		sidecar.SessionOpenParams{Stream: streamID, VHost: "/"}, nil); err != nil {
		return err
	}

	// 3) 声明一个临时队列
	var q sidecar.QueueInfoResult
	if err := br.Call(ctx, sidecar.MethodSessionDeclareQueue, sidecar.QueueDeclareParams{
		Stream: streamID, Exclusive: true, AutoDelete: true,
	}, &q); err != nil {
		return err
	}

	// 4) 发布一条消息（持久化等待在内核应答前已完成：调用返回即已按 fsync 档位落盘）
	if err := br.Call(ctx, sidecar.MethodSessionPublish, sidecar.PublishParams{
		Stream: streamID, RoutingKey: q.Name,
		Message: sidecar.MessageDTO{Body: []byte("hello")},
	}, nil); err != nil {
		return err
	}

	// 5) 注册消费者；投递随后以正向调用 session.deliver 到达 Handler.Call
	var c sidecar.ConsumeResult
	return br.Call(ctx, sidecar.MethodSessionConsume, sidecar.ConsumeParams{
		Stream: streamID, Queue: q.Name, Prefetch: 32,
	}, &c)
}

// 处理内核回推的投递并结算
func (h *handler) handleDeliver(ctx context.Context, params json.RawMessage) (any, error) {
	var p sidecar.DeliverParams
	if err := json.Unmarshal(params, &p); err != nil {
		return nil, err
	}
	br, ok := sidecar.BridgeFromContext(ctx)
	if !ok {
		return nil, errors.New("ctx 中没有内核桥")
	}
	// 结算不需要流号：投递编号在整条连接上全局唯一。
	// 动作三选一：Ack（消费完成）/ Requeue（重新入队）/ Reject（丢弃，可能进死信）。
	return nil, br.Call(ctx, sidecar.MethodSessionSettle, sidecar.SettleParams{
		DeliveryID: p.DeliveryID, Action: sidecar.SettleActionAck,
	}, nil)
}
```

**Список методов обратного вызова** (константы из `pkg/sidecar/bridge.go` → проводные имена):

| Группа | Проводное имя (константа) | Описание |
| --- | --- | --- |
| Аутентификация | `core.authenticate` (`MethodCoreAuthenticate`) | **Обязательно первым**: передать учётные данные из протокола ядру на проверку; параметры `{stream, mechanism, response}`, возвращает `{user}` |
| Сессия | `session.open` (`MethodSessionOpen`) | Открыть сессию для некоторого vhost на потоке; можно только **после аутентификации** |
| | `session.close` (`MethodSessionClose`) | Освободить сессию на этом потоке (отменить потребителей, удалить эксклюзивные очереди) |
| Обменники | `session.declare_exchange` / `session.delete_exchange` | Добавление/удаление (пассивное объявление несуществующего → `KindNotFound`) |
| | `session.bind_exchange` / `session.unbind_exchange` | Привязка обменника к обменнику |
| Очереди | `session.declare_queue` / `session.delete_queue` | Добавление/удаление; при пустом `name` имя генерирует сервер |
| | `session.bind_queue` / `session.unbind_queue` | Привязка очереди к обменнику |
| | `session.purge_queue` | Очистить готовые сообщения (без неподтверждённых) |
| Публикация | `session.publish` | Возвращает `{routed, rejected}`; персистентность завершается до ответа |
| Получение | `session.get` | Активно забрать одно сообщение; `found=false` означает, что очередь пуста |
| Потребление | `session.consume` / `session.cancel` | Зарегистрировать / отменить потребителя |
| Расчёт | `session.settle` | Рассчитаться по одной доставке (`ack` / `requeue` / `reject`) |
| **Прямой** | `session.deliver` | **Ядро → плагин**: обратная отправка доставки (обрабатывается в вашем `Handler.Call`) |

**Четыре обязательных правила**:

1. **Сначала `core.authenticate`**: у операционной поверхности ядра для соединения до аутентификации нет личности,
   поэтому `session.open` будет отклонён (`ACCESS_REFUSED - access to vhost '/' refused for user ''`).
   Плагин сам извлекает учётные данные из своего протокола; логика аутентификации и таблица пользователей по-прежнему в ядре, плагин не касается хранилища паролей.
2. **Затем `session.open`**: если вызвать другие методы без открытой сессии, ядро вернёт `KindPreconditionFailed` ("поток N ещё не открыл сессию").
3. **Каждая доставка рассчитывается ровно один раз**: `Ack` / `Requeue` / `Reject` — одно из трёх.
   И `Ack`, и `Reject` отбрасывают сообщение; **в dead-letter идёт только `Reject`**.
4. **Нерассчитанные доставки не теряются**: при завершении потока (отключение клиента / возврат `Handler.Open`) или разрыве соединения плагина
   ядро обрабатывает все нерассчитанные доставки **как "возврат в очередь"**, чтобы сообщения не застревали.

**Восстановление ошибок**: ошибка `*plugin.Error` ядра приходит через мост как `*sidecar.RPCError` (поля `Kind` / `Text`),
её можно восстановить в типизированный `plugin.Error`, а не терять категорию внутри строки:

```go
if err := br.Call(ctx, sidecar.MethodSessionPublish, params, nil); err != nil {
	var rpc *sidecar.RPCError
	if errors.As(err, &rpc) {
		return plugin.Errorf(plugin.ErrorKind(rpc.Kind), "%s", rpc.Text)
	}
	return err
}
```

Соответствие распространённых `Kind` встроенным протоколам (чтобы решить, как вернуть ошибку клиенту):

| `plugin.ErrorKind` | Семантика | Соответствие AMQP 0-9-1 |
| --- | --- | --- |
| `KindNotFound` | Объект не существует | 404 NOT_FOUND (закрыть Channel) |
| `KindPreconditionFailed` | Параметр не согласуется с существующим объектом / сессия не открыта | 406 PRECONDITION_FAILED (закрыть Channel) |
| `KindAccessRefused` | Недостаточно прав / зарезервированное имя | 403 ACCESS_REFUSED (закрыть Channel) |
| `KindResourceLocked` | Эксклюзивный ресурс занят | 405 RESOURCE_LOCKED (закрыть Channel) |
| `KindInvalidPath` | vhost не существует | 402 INVALID_PATH (закрыть соединение) |
| `KindNotImplemented` | Возможность не реализована | 540 NOT_IMPLEMENTED (закрыть соединение) |
| `KindInternal` | Внутренняя ошибка ядра | 541 INTERNAL_ERROR (закрыть соединение) |

**Граница точности типов сообщений**: таблица свойств (`MessageDTO.Properties.Headers`) передаётся через JSON,
и, как и в AMQP field-table, **информация о числовых типах с различением `int32` / `double` недоступна**.
Когда нужна строгая точность типов, переносите такую информацию в тело сообщения (сырые байты) и передавайте её самостоятельно.

### 3.5 Состояние и журналирование на стороне плагина

- **Состояние внешнего плагина определяется тем, живо ли соединение**, плагину не нужно сообщать его самому (встроенный `StateReporter` к внешним процессам не применим).
- Журналирование: `sidecar.ServerOptions.Logger` пишет в stdout/stderr процесса плагина;
  **когда процесс поднимается ядром через `spawn`, эти выходные данные перенаправляются ядром в его журнал** (с меткой `plugin`), что удобно для централизованного сбора.
- При независимом развёртывании (не через spawn) журналы плагина собираются вашим собственным способом.

### 3.6 Автономное тестирование без подключения к ядру

`Handler` — обычный Go-интерфейс; в модульных тестах достаточно создать экземпляр и вызвать `Hello` / `Call` / `Open`, чтобы покрыть бизнес-логику, без поднятия сети:

```go
func TestHelloRejectsWrongName(t *testing.T) {
	h := &handler{}
	if _, err := h.Hello(context.Background(), sidecar.Hello{Plugin: "other", APIVersion: "v1"}); err == nil {
		t.Fatal("插件名不一致时应当拒绝")
	}
}
```

Сквозная проверка описана в §5.

## 4. Разработка на других языках (спецификация проводного протокола)

`pkg/sidecar` — публичный контракт без зависимостей; сам проводной протокол очень прост, его можно реализовать на любом языке.
Для интеграции нужно реализовать приведённые ниже "байтовые" соглашения (исходники см. в `pkg/sidecar/frame.go`, `proto.go`).

> **Уже есть языковые руководства с полными примерами проектов** (все примеры прошли проверку: рукопожатие → аутентификация → семантический мост → доставка/расчёт → поток байтов):
>
> | Язык | Руководство | Пример проекта (рабочая область `swiftmq-plugin/`) |
> | --- | --- | --- |
> | Python | [plugin-development-python.md](plugin-development-python.md) | `python/sidecar_plugin.py` (только стандартная библиотека) |
> | Node.js | [plugin-development-nodejs.md](plugin-development-nodejs.md) | `nodejs/index.js` (только стандартная библиотека) |
> | PHP | [plugin-development-php.md](plugin-development-php.md) | `php/sidecar_plugin.php` (только стандартная библиотека) |
> | Java | [plugin-development-java.md](plugin-development-java.md) | `java/SidecarPlugin.java` (один файл, только JDK) |
>
> Полную эталонную реализацию на Go см. в отдельном тестовом проекте `swiftmq-test/test/integration/echosidecar/` (он напрямую использует `pkg/sidecar.Server`,
> так что о байтовых деталях ниже заботиться не нужно).

**Формат кадра** (единый для всех кадров):

```
+--------+--------+------------------+
| len    | kind   | payload          |
| u32 BE | u8     | (len-1) 字节      |
+--------+--------+------------------+
len = 1 + len(payload)，即长度字段**包含** kind 字节；单帧上限 16 MiB。
```

**Типы кадров `kind`**:

| kind | Название | Направление | Полезная нагрузка |
| --- | --- | --- | --- |
| 1 | Hello | ядро → плагин | JSON `Hello` |
| 2 | HelloAck | плагин → ядро | JSON `HelloAck` |
| 3 | Ping | ядро → плагин | пусто |
| 4 | Pong | плагин → ядро | пусто |
| 5 | Call | в обе стороны | JSON `Call` |
| 6 | Reply | в обе стороны | JSON `Reply` |
| 7 | Open | ядро → плагин | JSON `Open` |
| 8 | OpenAck | плагин → ядро | JSON `OpenAck` |
| 9 | Data | в обе стороны | `u32 BE stream` + сырые байты |
| 10 | Close | в обе стороны | JSON `Close` |

**JSON-структуры плоскости управления** (имена полей совпадают с `proto.go`).

> Этот фрагмент — **примеры сообщений проводного протокола** (в одном блоке по порядку приведено несколько сообщений, поэтому они разделены `//`),
> а **не конфигурация, которую можно напрямую записать в `swiftmqd.json`**.

```jsonc
// Hello（内核 → 插件）
{ "plugin": "my-sidecar", "protocol_version": "v1", "kernel_version": "1.1.01", "api_version": "v1" }
// HelloAck（插件 → 内核）；deny 非空表示拒绝服务
{ "name": "my-sidecar", "version": "0.1.0", "api_version": "v1",
  "capabilities": ["net.listen"], "protocols": ["myproto"], "methods": ["stats"], "deny": "" }
// Call / Reply：方向字段 reverse 区分"内核→插件"（false）与"插件→内核"（true）
{ "id": 1, "method": "session.open", "reverse": false, "params": { } }
{ "id": 1, "reverse": false, "ok": true, "error": "", "data": { } }
// Open（内核 → 插件）／OpenAck（插件 → 内核）／Close（双向）
{ "stream": 7, "remote": "1.2.3.4:5000", "local": "0.0.0.0:19002", "peek": "" }
{ "stream": 7, "ok": true, "error": "" }
{ "stream": 7, "reason": "closed by peer" }
```

**Обязательная семантика**:

- **Рукопожатие**: ядро первым отправляет `Hello`, плагин обязан ответить одним кадром `HelloAck`.
  Ядро проверяет `HelloAck.name == имени плагина в конфигурации` и `HelloAck.api_version == APIVersion ядра`;
  непустой `deny` считается отказом от подключения (плагин изолируется).
- **Heartbeat**: по умолчанию ядро каждые 2 с отправляет `Ping`, плагин должен ответить `Pong` в течение 8 с; если на стороне плагина в течение 24 с не пришло ни одного кадра, он может сам закрыть соединение.
- **Два пространства ID**: `reverse` в `Call` различает направление; в каждом направлении счётчик увеличивается с 1,
  поэтому `Reply` **обязан вернуть `reverse`**, иначе ответ будет доставлен не тому ожидающему.
- **Плоскость данных без base64**: крупные данные вроде тела сообщения кладутся прямо в полезную нагрузку кадра `Data` (`stream` + сырые байты) с разбиением по необходимости.

> Если используете Go, просто возьмите `pkg/sidecar`, и все перечисленные детали реализовывать не придётся.

## 5. Совместный запуск: подключение, обслуживание клиентов, упаковка ★

Этот раздел отвечает на вопрос "как после разработки подключить плагин к SwiftMQ и как начать обслуживать клиентов".

### 5.1 Объявление плагина в конфигурации

Внешний плагин **полностью управляется конфигурацией**, для него не нужно менять код ядра. Добавьте пункт в раздел `plugins` файла `swiftmqd.json`
(**реальная конфигурация — это стандартный JSON, комментарии недопустимы**):

```json
{
  "listeners": {
    "myproto": [{ "addr": ":19002" }]
  },
  "plugins": {
    "my-sidecar": {
      "builtin": false,
      "enabled": true,
      "required": false,
      "sidecar": {
        "address": "tcp://127.0.0.1:19001",
        "spawn": ["/usr/local/bin/my-sidecar", "-addr", "tcp://127.0.0.1:19001"],
        "restart": "always",
        "protocols": [
          {
            "name": "myproto",
            "prefix": "MP",
            "listeners": [{ "name": "myproto", "addr": ":19002" }]
          }
        ]
      }
    }
  }
}
```

Пояснения по пунктам (полный список полей — в таблице ниже):

- Имя ключа `plugins.<имя плагина>` **должно совпадать с сообщаемым плагином `HelloAck.name`**, иначе рукопожатие будет отклонено.
- `builtin: false`: явное объявление внешнего плагина (без него панель управления покажет его как встроенный).
- `enabled`: если отключить — процесс не запускается, слушатели не создаются.
- При `required: true` неудачный запуск заблокирует старт ядра — для внешних плагинов не включайте.
- `address` — **адрес, к которому подключается ядро** (ядро — клиент); если `spawn` непуст, процесс поднимает ядро.
- `protocols[].prefix` **обязан быть непустым** (правила сниффинга см. §5.3).
- `listeners` — **внешние порты этого протокола, открываемые ядром** (клиенты подключаются к ядру).

Список полей:

| Поле | Обязательно | Описание |
| --- | --- | --- |
| `sidecar.address` | ✅ | Адрес процесса плагина: `tcp://host:port` или `unix:///path` |
| `sidecar.spawn` | ✕ | Командная строка для запуска ядром (первый элемент — исполняемый файл); **пусто = ядро только подключается, но не запускает**, процессом управляете вы сами |
| `sidecar.restart` | ✕ | `always` (по умолчанию, автоматическое восстановление после разрыва/падения) или `never` (только пометка `down`, ожидание вмешательства эксплуатации) |
| `sidecar.protocols[].name` | ✅ | Имя протокола (глобально уникально, участвует в приоритете сниффинга) |
| `sidecar.protocols[].prefix` | ✕ | Префикс сниффинга (ASCII); **пусто = не участвует в сниффинге** |
| `sidecar.protocols[].listeners[]` | ✕ | Внешние слушатели этого протокола (`name` + `addr`), создаются ядром |
| `sidecar.handshake_timeout_seconds` | ✕ | Переопределить тайм-аут рукопожатия (по умолчанию 5 с) |
| `sidecar.heartbeat_seconds` | ✕ | Переопределить интервал heartbeat (по умолчанию 2 с) |

> **Имя плагина и имя протокола**: они **могут различаться** (например, плагин `my-sidecar` предоставляет протокол `myproto`).
> При горячем отключении сначала по имени плагина находятся все зарегистрированные им протоколы, а затем закрываются порты этих протоколов, поэтому специально давать одинаковые имена не нужно.

### 5.2 Три способа подключения

| Способ | Конфигурация | Когда подходит |
| --- | --- | --- |
| **Один хост + запуск ядром (spawn)** | `spawn: [...]`, `address` указывает на адрес, который он слушает | Развёртывание на одной машине, один контейнер; проще всего, запуск и очистку берёт на себя ядро |
| **Один хост + самостоятельное управление (dial)** | `spawn: []`, `address` указывает на уже запущенный процесс | Управление жизненным циклом плагина через systemd / supervisor |
| **Разные хосты / контейнеры (dial, обязательно tcp)** | `spawn: []`, `address: "tcp://<имя сервиса>:19001"` | Плагин и ядро развёрнуты в разных контейнерах / на разных машинах |

Выбор адреса:

- **На одной машине рекомендуется unix socket** (`unix:///tmp/my-sidecar.sock`): не занимает TCP-порт и не зависит от занятости портов хоста.
  Обратите внимание, что путь к socket должен быть доступен на запись процессу ядра (в контейнере это непривилегированный пользователь `swiftmq`).
- **Между контейнерами обязателен TCP**, при этом процесс плагина должен слушать `0.0.0.0`, а в `address` указывается **имя сервиса в сети контейнеров**.

> Не перепутайте направление: **адрес, который слушает плагин** = `address`; **порт, открытый наружу для клиентов** = `protocols[].listeners`.

### 5.3 Обслуживание клиентов: распознавание по `prefix`

При распределении соединений уровень подключения **смотрит только на результат сниффинга**: для каждого включённого протокола в порядке регистрации он опрашивает `Sniff(peek)` (peek — не более 8 байт),
и совпавший протокол забирает это соединение. Поэтому:

1. **`prefix` обязан быть непустым** (ASCII, ≤ 8 байт). Соединение передаётся вашему плагину только если первые байты от клиента совпадают с ним.
   Пример: `"prefix": "PY"` → первый байт от клиента должен быть `PY` (префикс можно считать магическим заголовком вашего протокола).
2. **Пустой `prefix` означает, что протокол не участвует в сниффинге**: такие соединения **не** передаются плагину (проверено на практике: соединение на порту прослушивания сразу разрывается).
   Поэтому пустой `prefix` подходит только для сценария "есть другой протокол, который на том же порту переславит за вас", **не** используйте его для выделенного порта.
3. `listeners[].addr` определяет, "на каком порту открываться наружу", а `prefix` — "считается ли это соединение вашим" —
   их нужно применять в паре: **даже выделенному порту нужен непустой `prefix`** (именно поэтому в примере конфигурации ядра
   у `echo-sidecar` одновременно указаны `prefix: "ECHO"` и `listeners: [":1885"]`).
4. Сниффинг сопоставляется в порядке регистрации протоколов, **срабатывает первый совпавший**: когда несколько плагинов сосуществуют, префиксы должны различаться (например, если все начинаются с одного байта, они будут перекрывать друг друга).

### 5.4 Переопределение адресов прослушивания и TLS

- Адрес внешнего прослушивания можно задать в **двух местах**: `sidecar.protocols[].listeners[].addr` (по умолчанию) и
  `listeners.<имя протокола>` (полное переопределение по имени протокола). Если заданы оба, приоритет у `listeners.<имя протокола>`.
- Если нужен TLS, сертификат задаётся в `listeners.<имя протокола>[i].tls` (поля такие же, как у встроенных протоколов).
  Ниже фрагмент `listeners` (**стандартный JSON, комментарии недопустимы**): первый элемент без TLS, второй — через TLS.

```json
"listeners": {
  "myproto": [
    { "addr": ":19002" },
    { "addr": ":19003", "tls": { "cert_file": "/etc/swiftmq/tls/cert.pem",
                                 "key_file":  "/etc/swiftmq/tls/key.pem" } }
  ]
}
```

> TLS терминируется **ядром** на стороне прослушивания, процесс плагина получает открытый текст — плагину не нужно обрабатывать TLS.

### 5.5 Упаковка: запуск плагина вместе с ядром

**Вариант A — упаковать в тот же образ** (рекомендуется для плагинов, выпускаемых вместе с ядром): добавьте строку на этапе выполнения в `swiftmq/Dockerfile`:

```dockerfile
COPY --from=<构建你的插件的 stage> /out/my-sidecar /usr/local/bin/my-sidecar
# 或直接拷预编译产物：
# COPY bin/my-sidecar /usr/local/bin/my-sidecar
```

Затем в конфигурации укажите `spawn: ["/usr/local/bin/my-sidecar", "-addr", "unix:///tmp/my-sidecar.sock"]`,
а `address` — то же значение. При запуске ядро поднимет его.

**Вариант B — смонтировать бинарник** (без изменения образа, подходит для совместной отладки):

```yaml
services:
  swiftmq:
    image: houzch/swiftmq:1.1.01
    command: ["-config", "/etc/swiftmq/swiftmqd.json", "-log-level", "info"]
    volumes:
      - ./configs/swiftmqd.json:/etc/swiftmq/swiftmqd.json:ro
      - ./bin/my-sidecar:/usr/local/bin/my-sidecar:ro   # 插件二进制
    ports:
      - "5672:5672"        # AMQP（内置）
      - "15672:15672"      # 管理面
      - "19002:19002"      # ← 你的协议对外端口（由内核监听）
```

В конфигурации используется unix socket (чтобы не занимать лишний порт). Ниже фрагмент `sidecar` внутри `plugins.my-sidecar`
(**стандартный JSON, комментарии недопустимы**; `prefix` по-прежнему должен быть непустым, см. §5.3):

```json
"sidecar": {
  "address": "unix:///tmp/my-sidecar.sock",
  "spawn": ["/usr/local/bin/my-sidecar", "-addr", "unix:///tmp/my-sidecar.sock"],
  "protocols": [{ "name": "myproto", "prefix": "MP", "listeners": [{ "name": "myproto", "addr": ":19002" }] }]
}
```

**Вариант C — отдельный контейнер** (независимый выпуск / независимое масштабирование плагина):

```yaml
services:
  swiftmq:
    image: houzch/swiftmq:1.1.01
    volumes: ["./configs/swiftmqd.json:/etc/swiftmq/swiftmqd.json:ro"]
    ports: ["5672:5672", "15672:15672", "19002:19002"]
    depends_on: [my-sidecar]

  my-sidecar:
    image: my-sidecar:0.1.0
    command: ["-addr", "tcp://0.0.0.0:19001"]   # 对外（对内）监听 0.0.0.0
```

В конфигурации `spawn: []` (ядро только подключается, но не запускает) и `address: "tcp://my-sidecar:19001"` (имя сервиса compose).

### 5.6 Запуск и проверка

```bash
# 1) 内核日志里应能看到握手与接入
docker compose logs swiftmq | grep -E "外部插件已接入|外部插件进程"

# 2) 经 CLI 看插件状态（state=enabled 且 RuntimeNote 为空）
./bin/swiftmqctl plugins list
./bin/swiftmqctl plugins show my-sidecar

# 3) 经管理 API 看（等价入口）
curl -u guest:guest http://127.0.0.1:15672/api/plugins/my-sidecar

# 4) 实测对外服务：你的协议端口由内核监听，直接连它
#    若你的协议是文本行协议，可以这样冒烟：
printf 'hello\n' | nc 127.0.0.1 19002
```

В `plugins show` в первую очередь обращайте внимание на `state` и `RuntimeNote`:
`failed` будет содержать причину сбоя (рукопожатие отклонено / порт не поднимается…); `down` будет содержать причину разрыва (процесс упал / соединение оборвалось).

### 5.7 Эксплуатация во время работы

| Операция | Команда / интерфейс | Эффект |
| --- | --- | --- |
| Горячее отключение | `swiftmqctl plugins disable my-sidecar` или `PUT /api/plugins/my-sidecar/disable` | **Закрыть внешние слушатели этого плагина** (отключение на уровне возможностей); ядро и другие плагины не затрагиваются |
| Горячее включение | `swiftmqctl plugins enable my-sidecar` | Снова открыть его слушатели; если ранее был сбой запуска, будет одна повторная попытка |
| Просмотр состояния | `swiftmqctl plugins list/show` | Состояние + причина сбоя/разрыва |
| Выход ядра | — | Разорвать соединение с плагином, освободить сессии на мосте, **завершить дочерние процессы, запущенные ядром через `spawn`** |

> Горячее отключение закрывает только "возможности" (порты прослушивания) и **не** убивает процесс плагина, запущенный через `spawn`; освобождение процесса происходит при выходе ядра.

### 5.8 Предоставление точки входа в панели управления (необязательно)

Если у плагина есть собственный интерфейс управления, добавьте в раздел `plugins.<имя плагина>` поле `console_url` (адрес интерфейса управления, остальные поля см. §5.1).
Ниже показан только пункт `plugins.my-sidecar` (**стандартный JSON, комментарии недопустимы**; содержимое раздела `sidecar` — как в §5.1):

```json
"plugins": {
  "my-sidecar": {
    "builtin": false,
    "enabled": true,
    "console_url": "http://127.0.0.1:19003/",
    "sidecar": { }
  }
}
```

- На странице **управления плагинами** в панели управления (данные берутся из поля `console_url` в `GET /api/plugins`) для таких плагинов отображается
  кнопка "Открыть интерфейс управления", которая **открывается в новой вкладке**.
- Если `console_url` не объявлен, кнопка недоступна, а при наведении всплывает подсказка "этот плагин не предоставляет интерфейс управления".
- Это лишь **метаданные, записанные развёртывающей стороной в конфигурацию**: они не относятся к API плагинов (`pkg/plugin`), не участвуют в запуске-остановке плагинов,
  а сам интерфейс плагин размещает самостоятельно (хоть в процессе плагина, хоть в любом отдельном сервисе).

## 6. Жизненный цикл и матрица отказоустойчивости

| Ситуация | Поведение ядра | Влияние на сторону плагина |
| --- | --- | --- |
| Процесс плагина не запущен / рукопожатие отклонено | Повтор подключения в течение 8 с, при неудаче пометка `failed` и изоляция (не блокирует запуск ядра) | Нет |
| Процесс, запущенный через `spawn`, завершился | Запись в журнал; пометка `down`; повторное подключение / перезапуск с задержкой согласно политике `restart` | Новый процесс заново проходит рукопожатие |
| Процесс плагина упал (во время работы) | Ядро не затронуто; `down` + повторное подключение с задержкой | `pkg/sidecar.Server` закроет это соединение |
| Ядро убито `kill -9` | — | Сторона плагина сама освобождает соединение по тайм-ауту простоя (по умолчанию 24 с без кадров), не оставляя зомби |
| Нормальный выход ядра | Вызов `Stop`: разрыв соединения, освобождение нерассчитанных доставок (возврат в очередь), `Kill` дочерних процессов | Получение SIGKILL |
| Доставки во время разрыва соединения плагина | Нерассчитанные доставки всегда **возвращаются в очередь** и не теряются | — |
| Отключение клиента / возврат `Open` | Закрытие соответствующего потока, освобождение сессии и потребителей этого потока | `Stream.Read` возвращает EOF |

## 7. Красные линии и известные границы

**Красные линии**

1. Плагину разрешено зависеть только от `pkg/sidecar` (и, при необходимости, от `pkg/plugin`); **запрещено** зависеть от `internal/**` ядра.
2. Имя плагина должно совпадать с конфигурацией, а `APIVersion` — с ядром, иначе подключение невозможно (это защита от "работает молча, но без эффекта").
3. При использовании `session.*`: **сначала `core.authenticate`, затем `session.open`**, и каждая доставка **рассчитывается ровно один раз**.
4. `protocols[].prefix` должен быть непустым, иначе соединение не будет передано плагину (см. §5.3).
5. Отказ в `Hello` должен **явно возвращать error** (не молча) — иначе ядро увидит только "соединение закрыто" и не сможет определить причину.

**Известные границы**

- **Сниффинг на стороне ядра**: внешний плагин не может задать собственную функцию сниффинга, возможна только проверка по `prefix` (ASCII, ≤ 8 байт);
  при пустом `prefix` "соединение не получить" (см. §5.3).
- **Плоскость данных идёт через локальное проксирование**: без передачи fd (в Windows нет `SCM_RIGHTS`), это на одно копирование памяти больше, чем внутри процесса;
  каждый обратный вызов тоже добавляет один локальный RPC.
- **Типы в таблице свойств деградируют**: `Properties.Headers` передаётся через JSON, различение вроде `int32` / `double` теряется (см. §3.4).
- **Обратное давление одного потока влияет на всё соединение**: при заполнении приёмного буфера одного потока блокируется горутина диспетчеризации этого соединения; ограничение скорости по потокам — будущая оптимизация.
- **При сбое аутентификации передаётся только текст**: сбой аутентификации ядра — это `*plugin.AuthError` (не та же классификация, что `plugin.ErrorKind`),
  и через мост к плагину доходит только текст; плагин должен сам сопоставить его с кодами ошибок своего протокола.
- **Реально действует только возможность `net.listen`**: `store.read/write`, `http.route`, `cluster.metadata.write`,
  `auth.verify` — это **зарезервированные места**, после объявления они участвуют только в аудите (см. демонстрацию управления в §5.6); соответствующих точек расширения сейчас нет.

## 8. FAQ по устранению неполадок

| Симптом | Причина и решение |
| --- | --- |
| Состояние `failed`, причина содержит "имя плагина не совпадает" | Имя плагина в конфигурации ≠ `HelloAck.name`; приведите к одному значению |
| Состояние `failed`, причина содержит "несовпадение версии API" | `HelloAck.api_version` ≠ `APIVersion` ядра; приведите к одному значению |
| Состояние `failed`, причина содержит "рукопожатие отклонено" | Плагин `Hello` вернул error (`deny`); смотрите перенаправленный вывод плагина в журнале ядра |
| Состояние `failed`, причина содержит "не удалось подключиться к внешнему плагину" | Процесс не запустился / `address` указан неверно / путь к socket недоступен на запись (в контейнере учтите права пользователя `swiftmq`) |
| Состояние `down` | Процесс плагина упал или соединение оборвалось; при `restart=always` переподключится автоматически, при `never` нужно поднять вручную |
| Порт не открыт / клиент не может подключиться | Не настроен `protocols[].listeners` или адрес перекрыт `listeners.<имя протокола>`; проверьте оба места |
| Клиент подключается к другому порту и сразу отключается | Этот порт не соответствует вашему протоколу (`prefix` пуст или префикс не совпадает); задайте протоколу непустой `prefix` (см. §5.3) |
| Сообщение `ACCESS_REFUSED - ... for user ''` | Перед семантическим мостом **нет аутентификации**; сначала вызовите `core.authenticate`, затем `session.open` |
| Обратный вызов сообщает "поток N ещё не открыл сессию" | Сначала `core.authenticate`, затем `session.open`, и только потом можно вызывать остальные `session.*` |
| Не приходят доставки потребления | Доставки приходят в ваш `Call` как **прямой вызов** `session.deliver`; убедитесь, что этот метод обработан |
| Плагин вне контейнера, ядро внутри контейнера, подключиться не удаётся | В `address` используйте `tcp://host.docker.internal:<port>` (либо поместите плагин в контейнер и используйте имя сервиса); плагин должен слушать `0.0.0.0` |
