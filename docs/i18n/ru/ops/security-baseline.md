# Базовый уровень безопасности SwiftMQ (чек-лист с отметками)

> Принцип: **описываем только реально имеющиеся в этом репозитории возможности**. По каждому пункту указано «зачем это делать + как проверить, что сделано», команды проверки выполнимы.
> Пометка **【Проверено】** означает, что это **действительно выполнялось** на локальной машине (Windows + PowerShell 5.1, `1.0.0`);
> **【Не проверялось】** означает, что это не выполнялось или сейчас невыполнимо — и мы ни в коем случае не делаем вид, что это не так.
> Для всех команд даны варианты curl в стиле `/bin/sh`, а также вариант для PowerShell (в PowerShell 5.1 используйте
> `Invoke-WebRequest ... -UseBasicParsing`).

## A. Аутентификация и контроль доступа

### A-1. Изменение учётной записи по умолчанию `guest/guest` 【Проверено】

- **Зачем**: по умолчанию встроена `guest/guest` (тег `administrator`), и при внешнем доступе это равносильно открытым настежь дверям.
- **Как делать**: менять пароль / удалять учётную запись во время работы, **не** трогая конфигурационный файл (`users` действует только при первом начальном заполнении).

```bash
# сменить пароль
curl -u guest:guest -X PUT http://127.0.0.1:15672/api/users/guest \
     -H 'Content-Type: application/json' -d '{"password":"<新口令>","tags":["administrator"]}'
# или сразу удалить учётную запись по умолчанию (сначала убедитесь, что создан новый администратор)
curl -u guest:guest -X DELETE http://127.0.0.1:15672/api/users/guest
```

- **Как проверить**: после изменения старый пароль должен давать 401, новый — 200.
  **【Проверено】** реальный вывод на локальной машине:

  ```
  --- 改密前 guest/guest ---          HTTP 200 {"auth_backend":"internal","name":"guest","tags":"administrator"}
  PUT /api/users/guest -> 204
  --- 改密后 guest/guest（应 401）---  HTTP 401
  --- 改密后 guest/s3cret（应 200）--- HTTP 200 {"auth_backend":"internal","name":"guest","tags":"administrator"}
  ```
- [ ] Учётная запись по умолчанию изменена/удалена

### A-2. Минимальные права: регулярные выражения `configure` / `write` / `read` по vhost 【Проверено】

- **Зачем**: три категории выровнены под RabbitMQ —— `configure` управляет объявлением/удалением топологии, `write` — публикацией и привязкой, `read` — потреблением и получением;
  при превышении прав возвращается 403. Бизнес-учётной записи выдавайте только то, что ей нужно.
- **Как делать**: `PUT /api/permissions/{vhost}/{user}`, например, только чтение и потребление: `{"configure":"^$","write":"^$","read":".*"}`.

```bash
curl -u guest:guest -X PUT http://127.0.0.1:15672/api/permissions/%2F/appuser \
     -H 'Content-Type: application/json' -d '{"configure":"^$","write":"^$","read":".*"}'
```

- **Как проверить**: попробуйте ограниченной учётной записью выполнить операцию вне её прав, ожидается 403 `ACCESS_REFUSED`.
  **【Проверено】** на локальной машине реальным клиентом AMQP пользователем с `configure="^$"` объявлялся обменник, на практике:

  ```
  FAIL 声明 durable 交换机失败: Exception (403) Reason: "ACCESS_REFUSED - access to configure 'r.ex' refused for user 'restricted'"
  ```
- [ ] Каждой бизнес-учётной записи выданы только необходимые регулярные выражения и не выдан тег `administrator`/`management`

### A-3. О трактовке тега `administrator` (неявные полные права) — выдавать с осторожностью 【Проверено】

- **Зачем**: **пользователь с тегом `administrator` обладает полными правами на все видимые ему vhost без записей о правах**
  (выровнено под реальную трактовку RabbitMQ, см. README / проектный документ M8-7). Иначе говоря, как только выдан этот тег,
  регулярные выражения прав перестают играть роль——это высший уровень прав.
- **Как делать**: тег `administrator` давать только учётным записям управляющей панели/эксплуатации; бизнес-учётным записям тег вообще не давать, использовать только регулярные выражения прав.

- **Как проверить (демонстрация неявных прав)**: на новом vhost, **у которого нет ни одной записи о правах**, пользователь `administrator` должен работать сразу.
  **【Проверено】** на локальной машине: после создания vhost `drillvh` (без каких-либо записей о правах) `guest` (administrator) успешно объявил на нём топологию:

  ```
  --- administrator 隐式权限：guest 在 drillvh 上声明拓扑 ---
  OK  已声明 durable 交换机 a.ex / 队列 a.q，并绑定 key=k   (exit=0)
  ```
- [ ] Тег `administrator` выдан лишь минимальному числу учётных записей эксплуатации

### A-4. `remote_access`: ограничение входа учётной записи только с локальной машины 【Не проверялось (на той же машине нельзя смоделировать удалённый источник)】

- **Зачем**: в соответствии с RabbitMQ встроенная `guest` по умолчанию допускает вход только с локальной машины; при внешнем развёртывании следует убедиться, что источник привилегированных учётных записей ограничен.
- **Как делать / трактовка (важное ограничение)**:
  - `remote_access` можно задать только в **конфигурационном файле**, в `users.<name>.remote_access`, и он **действует только при первом начальном заполнении**;
  - **учётные записи, созданные через управляющий API / `swiftmqctl`, всегда имеют `remote_access=true`** (разрешён вход из любого источника) ——
    основание: комментарий к `UpsertUser` в `internal/broker/observe.go` и реально наблюдаемое `"remote_access":true` в
    `meta/state.json`. Иначе говоря, **через API сейчас нельзя ограничить учётную запись входом только с локальной машины**.
- **Как проверить**: подключитесь этой учётной записью **с другой машины** (не `127.0.0.1`) — должно быть 403; с локальной машины — должно быть успешно.
  **【Не проверялось】**: на локальном окружении невозможно создать реальный удалённый источник, не тестировалось.
- [ ] Ограничение источника привилегированных учётных записей оценено с учётом изложенной трактовки (учтите: учётные записи, созданные через API, по умолчанию допускают удалённый вход)

## B. Безопасность передачи (TLS)

Параметры конфигурации TLS (уровень доступа и управляющая панель **используют один и тот же набор полей**): `cert_file` / `key_file` / `ca_file` / `client_auth` / `min_version`.

### B-1. Включение TLS и отказ запуска при ошибке конфигурации 【Проверено】

- **Зачем**: сертификат читается и проверяется **при запуске** — при ошибке конфигурации запуск немедленно отклоняется, а не всплывает только при подключении первого клиента.
- **Как делать**: в `listeners.<plugin>[].tls` или `management.tls` укажите `cert_file` + `key_file` (включается только при **наличии обоих**).

- **Как проверить**: запустите с ошибочной конфигурацией, должно сразу упасть.
  **【Проверено】** на локальной машине проверены три ошибочные конфигурации, все `exit=1`, запуск отклонён:

  ```
  badtls1: swiftmqd 启动失败: listeners.amqp091[0].tls 需要同时提供 cert_file 与 key_file
  badtls2: swiftmqd 启动失败: listeners.amqp091[0].tls.min_version 取值非法: "1.0"（可选 1.2 / 1.3）
  badtls3: swiftmqd 启动失败: listeners.amqp091[0].tls 无效: 加载服务端证书失败（cert=... key=...）: open ...: The system cannot find the path specified.
  ```
- **Как проверить (прямая/обратная проверка)**: TLS-клиент подключается, а открытый клиент к TLS-порту получает отказ.
  **【Проверено】** на локальной машине поднят TLS-экземпляр (`amqp091` через TLS) и выполнен пробинг реальным клиентом:

  ```
  === 正向：TLS 客户端跑全量探针 ===      全部通过（25/25）: ...
  === 反向：明文客户端连 TLS 端口（应失败）===  FAIL ... 拨号失败: Exception (501) Reason: "EOF"   (exit=-1)
  ```
- [ ] Для внешних протокольных портов включён TLS

### B-2. `min_version` не ниже 1.2 【Проверено】

- **Зачем**: отключает слишком старые версии TLS; по умолчанию уже `1.2`, допустимы `1.2` / `1.3`.
- **Как проверить**: задайте `min_version` равным `1.0`, запуск должен выдать ошибку (см. вывод `badtls2` в B-1).
- [ ] `min_version` равен `1.2` или `1.3`

### B-3. Взаимная аутентификация `client_auth: require_and_verify` (mTLS) 【Частично проверено】

- **Зачем**: требовать от клиента предъявления и проверки сертификата, чтобы не допустить неавторизованных клиентов к протокольным портам.
- **Как делать**: настроить `ca_file` + `client_auth: require_and_verify` (при последнем требуется одновременное предоставление `ca_file`).
- **【Проверено】**: сквозной TLS и путь отказа проверены реальным клиентом (B-1). **mTLS (запрос и проверка клиентского сертификата) на локальной машине отдельно не прогонялся**.
- [ ] Для портов, требующих mTLS, настроены `require_and_verify` + `ca_file`

### B-4. TLS управляющей панели 【Не проверялось】

- **Зачем**: управляющая панель передаёт пароль через Basic Auth, поэтому шифрование обязательно.
- **Как делать**: `management.tls` использует те же поля, что и протокольные прослушиватели.
- **【Не проверялось】**: в локальном прогоне управляющая панель была привязана к локальному открытому порту, отдельный HTTPS управляющей панели не поднимался.
- [ ] Для управляющей панели включён TLS (или она строго ограничена доверенной сетью)

## C. Сокращение поверхности атаки

### C-1. Сокращение диапазона прослушивания управляющей панели 【Проверено (адрес прослушивания измерен)】

- **Зачем**: управляющая панель по умолчанию `:15672` (все сетевые адаптеры). При внешнем развёртывании следует привязать её к внутреннему/loopback-адресу или ограничить источники через firewall.
- **Как делать**: задать `management.addr` равным `127.0.0.1:15672` или внутреннему адресу; либо полностью отключить через `management.enabled=false`
  (после отключения управляющего порта нет, но и `swiftmqctl` становится недоступен).
- **Как проверить**:
  **【Проверено】** на локальной машине управляющая панель настроена на `127.0.0.1:15677`, реально измеренный адрес прослушивания оказался loopback:

  ```
  LocalAddress LocalPort
  ------------ ---------
  127.0.0.1        15677
  ```
- [ ] Адрес привязки управляющей панели сокращён (или она отключена)

### C-2. Открывать только необходимые протокольные порты 【Не проверялось】

- **Зачем**: по умолчанию одновременно открыты AMQP `5672` и MQTT `1883`; если MQTT не нужен, отключите его, чтобы уменьшить поверхность атаки.
- **Как делать**: `plugins.mqtt.enabled=false` (или убрать из `listeners`); отключение выполняется через **закрытие реального порта**, а не просто сменой бита состояния.
- **Как проверить**: после отключения соответствующий порт больше не прослушивается (в `Get-NetTCPConnection -State Listen` его не видно).
  **【Не проверялось】**: в локальном прогоне оба протокола были включены, отдельно проверка исчезновения порта после отключения не выполнялась.
- [ ] Неиспользуемые протокольные плагины отключены

## D. Упрочнение работы контейнера

Факты об образе репозитория (`Dockerfile`): статически слинкованный бинарный файл + alpine, **работает не от root (uid 10001, пользователь `swiftmq`)**,
каталог данных `/var/lib/swiftmq` является томом. В `docker-compose.yml` используется **именованный том** для персистентности, конфигурация **монтируется только для чтения**, логи ротируются.

### D-1. Запуск от имени не root 【Не проверялось (локально Docker не запускался)】

- **Зачем**: минимальные права, снижение последствий после побега из контейнера.
- **Как делать**: образ по умолчанию уже uid 10001; **не** переопределяйте через `--user root`.
- **Как проверить**: `docker compose run -T --rm broker id` должен показать `uid=10001`. (в неинтерактивном окружении к `run` обязательно добавлять `-T`)
- [ ] Контейнер работает не от root (не переопределено на root)

### D-2. Файловая система только для чтения + лимиты ресурсов + урезание capabilities (рекомендация, в compose репозитория по умолчанию не включено) 【Не проверялось】

- **Зачем**: корневая файловая система только для чтения предотвращает изменение бинарного файла во время работы; лимиты ресурсов не дают одному контейнеру обрушить хост; урезание capabilities уменьшает поверхность атаки на ядро.
- **Как делать** (пример, по мере необходимости объедините со службой `broker` в compose):

```yaml
services:
  broker:
    read_only: true
    tmpfs:
      - /tmp
    security_opt:
      - no-new-privileges:true
    cap_drop: ["ALL"]
    deploy:
      resources:
        limits:
          cpus: "4"
          memory: 8g
```

- **Как проверить**: попытка записи в корневой путь внутри контейнера должна завершиться ошибкой (только для чтения); через `docker inspect` видны лимиты ресурсов.
  **【Не проверялось】** (локально Docker не запускался); и **для корневой файловой системы только для чтения нужно убедиться, что `data_dir` находится на записываемом томе**, иначе ядро не сможет сбросить данные на диск.
- [ ] Оценены файловая система только для чтения и лимиты ресурсов (учтите: `data_dir` должен находиться на записываемом томе)

## E. Известные ограничения (сейчас действительно невозможно, не рассчитывайте на них)

Всё ниже — **фактические пробелы**; явно признайте их в проекте безопасности и не предполагайте, что они существуют:

1. **Пароли хранятся и копируются в открытом виде**. В `meta/state.json` поле `password` хранится в открытом виде (**【Проверено】** на практике видно
   `"password":"drillpass"`); в конфигурационном файле тоже открытый вид. **Хеширования пароля нет** (хеширование и внешний бэкенд аутентификации оставлены плагину аутентификации).
   → Следствие: **каталог данных и файлы резервных копий равносильны чувствительным учётным данным**, необходимы права доступа к файлам и шифрованное хранение.
2. **Нет журнала аудита**. Изменения в управляющей панели попадают в обычные логи (например, `管理面更新用户 actor=... user=...`),
   но **отдельного неизменяемого потока аудита нет**, как и записи уровня соответствия «кто, когда и что изменил».
3. **Нет внешней аутентификации типа LDAP / OAuth2 / JWT**. В v1 встроены только `PLAIN` / `AMQPLAIN`
   (`auth.Store.Mechanisms()` на практике возвращает только эти два).
4. **SASL `EXTERNAL` не реализован**: даже при настроенном mTLS на уровне протокола **всё ещё используется парольная аутентификация PLAIN**
   (шага «вход по клиентскому сертификату без пароля» нет). Сертификат — это только проверка на транспортном уровне.
5. **`remote_access` нельзя задать через API**: учётные записи, созданные через управляющий API/CLI, всегда допускают удалённый вход (см. A-4),
   нельзя ограничить отдельную учётную запись входом только с локальной машины.
6. **У управляющей панели нет отдельного белого списка источников / ограничения частоты**: поверхность атаки сужается только через привязку адреса, firewall и TLS.
7. **Нет песочницы для плагинов**: плагин формы A находится в одном процессе с ядром; у внешнего плагина формы B есть изоляция процесса, но **плоскость данных идёт через локальный прокси-соединение**,
   и плагин может вызывать семантику ядра (с учётом проверок vhost и прав), это **не** безопасная песочница.
8. **У управляющей панели есть только три уровня тегов `administrator`/`management`/`monitoring`**, более детального RBAC по ресурсам нет.
