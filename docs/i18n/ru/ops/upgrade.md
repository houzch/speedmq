# SpeedMQ: схема обновления и миграции

> Применимая версия: `1.0.0` (`broker.Version`, см. `speedmq_build_info` в `/metrics`).
> Все выводы «по факту» в этом документе получены при реальном запуске на локальной машине; всё, что не тестировалось, явно помечено **【Не проверялось】**.
> Локальное окружение: Windows + PowerShell 5.1, Go 1.27.1 windows/386, временный `data_dir` + нестандартные порты.

---

## 1. Миграция (переход с RabbitMQ на SpeedMQ)

Позиционирование этого проекта — **совместимость на уровне протокола AMQP 0-9-1**, поэтому «миграция» сводится в основном к **изменению адреса подключения**:

- Ноль изменений в бизнес-коде, меняются только `host/port/vhost` (проектный документ G3 «нулевая стоимость миграции»).
- Инструментальная цепочка управления (`rabbitmqadmin`, панель управления, скрипты мониторинга) — достаточно направить на порт управляющей панели; форма интерфейса выровнена под RabbitMQ (соглашения `amq.default`, `%2F`, `{error, reason}` и т. п. скопированы).
- Порты по умолчанию совпадают с RabbitMQ: AMQP `5672`, управляющая панель `15672`; MQTT — `1883`, RPC между узлами — `25672`.

**Семантические различия, которые нужно проверить перед миграцией** (все они намеренные в этом репозитории, на основании README / проектных документов):

| Пункт | Поведение SpeedMQ | Влияние на миграцию |
| --- | --- | --- |
| Транзитные (не персистентные и не эксклюзивные) очереди | **Отказывает в объявлении** (541), `auto_delete` не является исключением | Старые клиенты, полагающиеся на такие очереди, будут получать ошибку; нужно перейти на durable или exclusive |
| vhost по умолчанию `/` | **Нельзя удалить** (400), тогда как RabbitMQ это позволяет | Скрипты автоматизации, удаляющие vhost по умолчанию, будут получать ошибку (это единственное активное ограничение безопасности) |
| Данные классических очередей | **Не реплицируются**, данные находятся только на узле-владельце | Если нужна избыточность между узлами, перейдите на кворумные очереди `x-queue-type=quorum` |
| Кворумные очереди | Поддерживается увеличение числа реплик, **уменьшение не поддерживается** | Планируйте сразу окончательную конфигурацию |
| Плагины | Нет экосистемы плагинов на Erlang, AMQP 1.0 / STOMP не реализованы | Сценарии, использующие эти протоколы, пока мигрировать нельзя |

**Миграция данных**: форматы хранения SpeedMQ и RabbitMQ несовместимы, **онлайн- и офлайн-инструмент переноса данных не предоставляется**.
Способ миграции — «создать пустой SpeedMQ → проверить в режиме двойного запуска → переключать трафик постепенно». **【Не проверялось】** В этом документе нет ни одного реального прогона переноса данных из RabbitMQ.

## 2. Общие принципы обновления

1. **Сначала резервная копия** (см. `backup-restore.md`) — подстраховка на случай неудачного обновления.
2. **Сначала остановить процесс, потом заменять** (у каталога данных есть ограничение единственного писателя, см. §4.2).
3. **После обновления обязательна проверка**: процесс запускается, `/api/overview` читается, `/metrics` собирается, число сообщений в очередях совпадает с состоянием до резервного копирования.
4. Обновление кластера — **поочерёдным скользящим способом**, за раз трогаем только один узел (см. §5).

## 3. Структура каталога данных (фактическая основа для обновления/миграции)

Структура `data_dir`, полученная **на практике** на локальном одиночном экземпляре:

```
data/
├── meta/
│   ├── state.json        # снимок метаданных в режиме одиночного узла (vhost/обменники/очереди/привязки/пользователи/права/политики)
│   ├── users.seeded      # маркер начального заполнения: users из конфигурационного файла уже заполнены
│   ├── vhosts.seeded     # маркер начального заполнения: vhosts из конфигурационного файла уже заполнены
│   ├── raft.state        # 【режим кластера】срок/голосование Raft
│   ├── raft.log          # 【режим кластера】журнал Raft
│   └── snapshot.json     # 【режим кластера】снимок Raft + таблица участников
├── msg_stores/vhosts/<safe(vhost)>/queues/<safe(queue)>/
│   ├── 000001.seg        # файл сегмента (тело сообщения + свойства), формат записи: <len u32><crc32 u32><payload>
│   └── index/000001.idx  # индекс очереди: seq-id → (номер сегмента, смещение в сегменте, длина, состояние)
└── quorum/<safe(vhost)>/<safe(queue)>/   # 【кластер】для каждой кворумной очереди отдельная группа Raft (журнал/снимок)
```

**Внимание (два момента, расходящихся с интуицией, оба основаны на коде/практике)**:

- В режиме кластера файлы персистентности Raft **находятся прямо в `meta/`** (`raft.state` / `raft.log` / `snapshot.json`),
  **подкаталога `meta/raft/` не существует**. Основание: константы имён файлов в `internal/raft/log.go` + `Dir: filepath.Join(b.cfg.DataDir, "meta")`
  в `internal/broker/cluster.go`. **【Структура кластера не тестировалась】** (локально запускался только одиночный экземпляр).
- Имя каталога — это **не исходное имя vhost / очереди**, а кодирование `store.SafeDirName`: добавляется префикс `q_`, байты, не входящие в `[A-Za-z0-9._-]`, экранируются как `%XX`.
  На практике: vhost `/` → каталог `q_%2F`, очередь `persist.q` → каталог `q_persist.q`.
  Такая схема нужна, чтобы избежать обхода пути и зарезервированных имён устройств Windows (`con`/`nul` и т. п.).

## 4. Совместимость данных

### 4.1 Можно ли читать старые данные напрямую — да

- **Формат индекса совместим вперёд**: M8-1 добавил в запись индекса поле «номер сегмента» (25 байт); **старый формат (21 байт, без номера сегмента) по-прежнему читается как есть**,
  при чтении он равносилен «только один сегмент (seg=1)», **для обновления не нужен скрипт миграции**.
  Основание: константы `indexEntrySize` / `legacyIndexEntrySize` и логика `recover()` в `internal/store/store.go`; README M8-1.
- **Семантика сбоя не меняется**: каждая запись содержит префикс длины + CRC32, при восстановлении **отбрасываются недописанные/повреждённые записи в хвосте** и файл усекается.
  На практике (см. `backup-restore.md` §6): после остановки и перезапуска процесса все 5 персистентных сообщений durable-очереди **восстановлены полностью**,
  в журнале появляется `已从磁盘恢复队列消息 ... messages=5`.

### 4.2 О трактовке `vhosts` / `users` в конфигурации (самая частая ловушка при обновлении)

- Оба параметра **действуют только при первом начальном заполнении**: при первом запуске vhosts/users из конфигурации записываются в метаданные и создаются маркерные файлы
  `meta/vhosts.seeded` / `meta/users.seeded`; **далее приоритет у метаданных**.
- Поэтому **при обновлении/смене конфигурации не рассчитывайте добавить или удалить учётные записи либо vhost изменением конфигурационного файла** — изменения не вступят в силу;
  используйте управляющий API или `speedmqctl`.
- И наоборот, обновление **не** перезаписывает существующие учётные записи конфигурацией: пароли, изменённые во время работы, не вернутся после перезапуска к старым значениям из конфигурации,
  а удалённые во время работы учётные записи не оживут. Основание: логика маркеров начального заполнения в `cluster.go`; README M8-4 / M8-7.

### 4.3 Ротация сегментов и освобождение места на диске

- Сообщения разделяются на сегменты по размеру (по умолчанию 8 MiB); **после того как все сообщения сегмента подтверждены (ack) и сегмент закрыт, он удаляется целиком**, индекс при этом сжимается и перезаписывается.
- Обновление не меняет это поведение; одиночный сегментный файл, оставшийся от старого экземпляра, продолжает работать при новой логике ротации сегментов.

## 5. Обновление бинарного файла (на «голом железе»)

> На локальной машине **не выполнялся реальный прогон между версиями** (в репозитории сейчас только одна версия `1.0.0`, старого бинарного файла для обновления нет). Приведённые ниже шаги — это **повторная проверка в пределах одной версии + общий порядок** возможностей, уже имеющихся в этом репозитории; части, касающиеся перехода между версиями, помечены **【Не проверялось】**.

### 5.1 Шаги

```powershell
$base = "C:\speedmq"
$data = "$base\data"

# 1) остановить процесс (при корректном завершении выполняется финальный сброс на диск; см. §4 «Согласованность»)
#    если запущен в переднем плане: Ctrl+C; если как служба: Stop-Service / Stop-Process
Stop-Process -Name speedmqd -ErrorAction SilentlyContinue
Start-Sleep -Seconds 2

# 2) сделать резервную копию каталога данных (обязательно после остановки процесса)
Copy-Item -Recurse -Force $data "$base\backup-$(Get-Date -Format yyyyMMdd-HHmmss)"

# 3) заменить бинарный файл (положить новые speedmqd.exe / speedmqctl.exe в исходные пути)
#    Copy-Item .\new\speedmqd.exe $base\speedmqd.exe -Force

# 4) запустить
& "$base\speedmqd.exe" -config "$base\configs\speedmqd.json" -log-level info

# 5) проверка: процесс жив + управляющий API читается
$pair = [Convert]::ToBase64String([Text.Encoding]::ASCII.GetBytes('guest:guest'))
$H = @{ Authorization = "Basic $pair" }
Invoke-WebRequest -Uri 'http://127.0.0.1:15672/api/overview' -Headers $H -UseBasicParsing | Select-Object -ExpandProperty Content
```

### 5.2 Чек-лист проверки после обновления

- В журнале запуска появились `SpeedMQ 启动中 ... version=<新版本>` и `管理面已启动`;
- `object_totals` / `queue_totals` в `/api/overview` совпадают с состоянием до резервного копирования (сверьте с `backup-restore.md` §5);
- `messages` / `messages_ready` каждой durable-очереди в `/api/queues` совпадают с состоянием до резервного копирования;
- `/metrics` собирается и содержит `speedmq_plugin_up{name="amqp091"} 1`, `{name="mqtt"} 1`.

## 6. Обновление образа (контейнер)

Образ весит около 13 MB (статически слинкованный бинарный файл + alpine), **работает не от root (uid 10001)**, каталог данных смонтирован в `/var/lib/speedmq`.

```powershell
# 1) скачать/собрать новый образ (в теге используйте новый номер версии, чтобы не путать old/new)
docker build -t speedmq:1.0.0 .

# 2) остановить старый контейнер (compose сохранит именованный том speedmq-data)
docker compose down

# 3) запустить новую версию (в файле compose измените image на новый тег)
docker compose up -d

# 4) статус и логи
docker compose ps
docker compose logs -f --tail 100
```

> **Одноразовая задача внутри контейнера** (например, запуск `speedmqctl` внутри контейнера): в неинтерактивном окружении к `run` команды `docker compose ...` обязательно нужно добавлять `-T`,
> иначе произойдёт сбой из-за запроса TTY:
> ```powershell
> docker compose run -T --rm broker speedmqctl -user guest -pass guest status
> ```

Персистентность данных обеспечивается **именованным томом** `speedmq-data` из compose; данные не теряются при пересоздании контейнера (реальная запись на диск с M4).
Если перед обновлением нужно зарезервировать содержимое тома, это эквивалентно резервному копированию `/var/lib/speedmq` (см. `backup-restore.md` §3.2). **【Обновление образа не тестировалось】** (локально Docker не запускался).

## 7. Поэтапный выпуск и откат

### 7.1 Одиночный узел

- **Поэтапный выпуск**: в одиночном SpeedMQ нет встроенной возможности «запускать старую и новую версии в одном процессе». Реализуемый поэтапный выпуск — это **боковое зеркало**:
  экземпляр новой версии сначала подключают к тому же входящему трафику в режиме **потребителя только для чтения / зеркальной очереди** для наблюдения, а после подтверждения отсутствия проблем переключают сторону записи.
- **Откат**:
  1. остановить процесс новой версии;
  2. вернуть старый бинарный файл;
  3. если новая версия уже записывала данные, **обязательно восстановите `data_dir` из резервной копии, сделанной до обновления** (см. ниже).
  Гарантии «новая версия уже записала, а старая читает напрямую» **не будет** — см. понижение версии между версиями в §8.

### 7.2 Кластер (rolling upgrade)

На стороне платформы нет «однокнопочного rolling upgrade», нужно вручную действовать узел за узлом в следующем порядке:

1. **Обновлять по одному узлу за раз**: остановить этот узел → зарезервировать его `data_dir` → заменить бинарный файл → запустить → дождаться повторного присоединения и догона
   (`speedmqctl cluster_status` / `GET /api/cluster` смотреть `role`, `commit_index`/`last_applied`).
2. **Рекомендуемый порядок**: сначала обновить **learner / не голосующего участника** (на большинство не влияет), затем **follower**, и в конце **leader**
   (обновление leader вызовет выборы лидера, в течение которых будет кратковременная недоступность записи).
3. **Влияние остановки на большинство** (ключевой момент):
   - Кластер из 3 узлов: одновременно можно останавливать **не более 1** голосующего участника; остановка 2 означает потерю большинства, и при `pause_minority` **весь кластер приостанавливает обслуживание**.
   - Кластер из 2 узлов: остановка 1 узла уже означает потерю большинства, **возможности rolling upgrade нет** (рекомендуется минимум 3 узла).
   - Поэтому при rolling upgrade **строго запрещено останавливать одновременно несколько голосующих участников**.
4. **Не совмещайте изменение состава и обновление**: у изменения состава **нет joint consensus**, одновременно допускается только одно незавершённое изменение конфигурации;
   во время обновления избегайте одновременных `add_member` / `remove_member`.
5. После завершения обновления сверьте `object_totals` в `GET /api/cluster` с состоянием до обновления.

> **【Не проверялось】** На локальной машине реальный прогон rolling upgrade кластера не выполнялся (ни путь кластера, ни контейнер не запускались); приведённый порядок основан на общих
> ограничениях промежуточного ПО обмена сообщениями и Raft, а также на фактах реализации `pause_minority` / изменения состава в этом репозитории, а не на локальных измерениях.

## 8. Неподдерживаемые / непроверенные части (перечислены явно)

- **Понижение версии между крупными версиями: не поддерживается, не проверялось**. Если новая версия уже записала данные в новом формате/с новой семантикой, гарантии «откатиться на старый бинарный файл и читать как есть» **нет**;
  откат возможен только через резервную копию, сделанную до обновления.
- **Формат конфигурации не меняется**: по-прежнему JSON + переменные окружения `SPEEDMQ_*`. **YAML-конфигурация пока не поддерживается** (потребуется зависимость для разбора, M8-17 ожидает оценки),
  обновление не принесёт YAML.
- **Горячее обновление плагинов/протоколов на лету**: плагин либо компилируется вместе с ядром (форма A), либо поднимается по конфигурации через `spawn` (форма B);
  обновление ядра = перезапуск процесса; механизма **горячей замены бинарного файла на месте нет**.
- **Миграция движка хранения на месте**: ротация сегментов/сжатие индекса — это фоновая работа во время выполнения; **отдельной команды «миграции/сжатия данных» нет**.
- **Обновление кластера в условиях реальной сети**: в этом репозитории проводился только уменьшенный хаос (kill на уровне процесса), **не выполнялся** прогон обновления при сетевом разделении и заполненном диске.
- Этот документ **не содержит** проверки переноса данных между SpeedMQ и другими брокерами (RabbitMQ).
