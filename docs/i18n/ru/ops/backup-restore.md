# SpeedMQ: резервное копирование и восстановление

> Все выводы «по факту» в этом документе получены в ходе одного реального прогона на **Windows + PowerShell 5.1** (временный `data_dir` и временные порты).
> Команды прогона и ключевой вывод приведены дословно в §6. Части, помеченные **【Не проверялось】**, указаны явно (например, реальное отключение питания физической машины).

> **【Проверено (2026-10-11, локальный кластер из 3 узлов Docker Desktop)】** Жёсткое убийство процесса (`docker kill`) и параллельная запись во время восстановления проверены на практике,
> записи см. в §6.2 / §6.3; трактовка «отключения питания» в §2.3 и список статуса проверки в §7 синхронно обновлены.

## 1. Что нужно резервировать

Под `data_dir` **необходимо резервировать всё целиком**, ключевыми являются следующие элементы (структура см. в `upgrade.md` §3):

| Путь | Назначение | Что будет, если потерять |
| --- | --- | --- |
| `meta/state.json` | Снимок метаданных одиночного узла: vhost / обменники / очереди / привязки / пользователи / права / политики | Полностью теряются топология и учётные записи |
| `meta/raft.log`, `meta/raft.state`, `meta/snapshot.json` | 【Кластер】Журнал Raft / голосование по срокам / снимок + таблица участников | Теряются идентичность кластера и согласованность метаданных |
| `meta/users.seeded`, `meta/vhosts.seeded` | Маркеры начального заполнения | При потере users/vhosts из конфигурации будут **заполнены повторно** (удалённые учётные записи/vhost оживут) |
| `msg_stores/vhosts/<safe(vhost)>/queues/<safe(queue)>/0000NN.seg` + `index/0000NN.idx` | Данные и индекс сообщений классической очереди | Теряются персистентные сообщения |
| `quorum/<safe(vhost)>/<safe(queue)>/` | 【Кластер】Журнал/снимок Raft кворумной очереди | Теряются данные кворумной очереди |
| Файлы сертификатов (PEM, на которые указывают `cert_file`/`key_file`/`ca_file` в конфигурации) | Сертификаты TLS | Резервируются отдельно от `data_dir`, после перезапуска TLS не поднимется |

> Мягкое состояние (неподтверждённые сообщения, потребители, счётчики prefetch) **находится только в памяти** и не сохраняется на диск; резервная копия **не содержит** его и не должна содержать.

## 2. Требование согласованности: **сначала обязательно остановите процесс**; горячее резервирование **небезопасно**

### 2.1 Вывод

- ✅ **Безопасный способ**: **остановить процесс broker** (при корректном завершении выполняется финальный сброс на диск), затем скопировать `data_dir`.
- ❌ **Горячее резервирование (прямое копирование файлов при работающем процессе): небезопасно, гарантий нет.**

### 2.2 Почему горячее резервирование небезопасно

Хранилище сообщений — это **два файла** (файл сегмента `*.seg` и файл индекса `index/*.idx`), и они **не фиксируются атомарно**:

- При восстановлении **ориентируются на индекс**, чтобы определить, «какие сообщения живы», а затем по `(номер сегмента, смещение, длина)` из индекса читают данные из файла сегмента.
- При горячем резервировании можно скопировать промежуточное состояние, когда **индекс уже ссылается на запись, а файл сегмента ещё не дописан полностью** (или наоборот):
  - индекс ссылается на несуществующую в сегменте запись → это сообщение **не читается и пропускается** (по сути потеря подтверждённого персистентного сообщения);
  - в сегменте запись есть, но индекс на неё не ссылается → это сообщение **не восстанавливается**.
- Хотя при восстановлении через CRC32 **отбрасываются недописанные записи в хвосте**, это покрывает только «повреждение хвоста одного файла» и **не может исправить рассинхронизацию между индексом и сегментом**.

### 2.3 О том, «когда запись попадает на диск» (наблюдения по факту)

- По умолчанию `fsync: os` + `flush_interval_ms: 200`: сообщения фоновым сбросом в течение **примерно не более 200 мс** выполняют `write()` в операционную систему
  (без fsync), и publisher confirm также возвращается после этого.
- На практике: если **сразу** после публикации персистентного сообщения проверить размер файла сегмента, данные уже видны (`t=0ms seg=832`); то есть «байты, видимые ОС», и confirm практически синхронны.
- **Внимание**: это говорит лишь о том, что данные «попали в буфер ОС»; **жёсткое убийство процесса не приведёт к потере** (при убийстве процесса буфер ОС не теряется), но **при отключении питания данные потеряются**.
  Чтобы «получение confirm означало уже выполненный fsync на диск», измените `storage.fsync` на `batch` / `always`.
  **【Проверено (2026-10-11, локальный кластер из 3 узлов Docker Desktop)】** Практическая проверка жёсткого убийства узла с `docker kill` (SIGKILL) во время записи: в обоих режимах подтверждённые сообщения не теряются:
  `fsync: os` убийство follower (50 000 сообщений, все подтверждены, сверка missing=0), `fsync: always` убийство leader кворумной очереди (200 000 сообщений, все подтверждены,
  missing=0; дополнительно 1 355 уже записанных на диск, но не подтверждённых сообщений были переотправлены — семантика at-least-once это допускает, дедупликация по ID сообщения на стороне потребителя делает идемпотентным).
  Бонус: в режиме по умолчанию во время публикации вся VM Docker была аварийно остановлена через `wsl --shutdown` (приближает отключение питания всей машины с потерей буфера ОС); после восстановления 69 669 подтверждённых сообщений
  сверены по ID с missing=0. **Всё ещё не проверено**: реальное отключение питания физической машины (потеря питания хоста, слой кэша диска) — на этой машине невозможно смоделировать.

## 3. Порядок резервного копирования

### 3.1 Одиночный узел (рекомендуется)

```powershell
# 1) остановить процесс (в переднем плане: Ctrl+C; в фоне: Stop-Process)
Stop-Process -Name speedmqd -ErrorAction SilentlyContinue
Start-Sleep -Seconds 2

# 2) скопировать весь data_dir (с меткой времени)
$data = "C:\speedmq\data"
Copy-Item -Recurse -Force $data "C:\backup\speedmq-$(Get-Date -Format yyyyMMdd-HHmmss)"

# 3) (необязательно) проверить, что снимок метаданных в резервной копии разбирается
Get-Content "C:\backup\speedmq-...\meta\state.json" -Raw | ConvertFrom-Json | Select-Object -ExpandProperty VHosts
```

### 3.2 Кластер

- **Каждый узел резервирует свой собственный `data_dir`** (метаданные реплицируются через Raft на всех участников, данные сообщений находятся на узле-владельце, реплики кворумных очередей — в своих каталогах Raft).
- Порядок остановки: **останавливать по одному узлу за раз**; не останавливайте одновременно несколько голосующих участников (см. `upgrade.md` §7.2).
- Чтобы получить **согласованный снимок всего кластера**, нужно последовательно остановить все узлы и затем скопировать данные каждого; в эксплуатации чаще встречается «остановить/скопировать/запустить узел за узлом».
- **【Проверено (2026-10-10, локальный кластер из 3 узлов Docker Desktop)】** В кластере compose из 3 узлов поузловое «остановить/скопировать/запустить»: каждый узел упаковывал свой именованный том одноразовым контейнером alpine
  (`docker run --rm -v <том>:/data -v <каталог-хоста>:/backup alpine tar czf ...`), в архиве были `meta/raft.log`, `meta/raft.state`, `meta/*.seeded`, `quorum/...`;
  после восстановления узел смог повторно присоединиться как существующий участник и догнать остальных (см. §4.2; доказательство то же, что и в `upgrade.md` §7.2).

### 3.3 Docker (именованный том)

```powershell
# после остановки контейнера упаковать и скопировать содержимое тома через одноразовый контейнер
docker compose down
docker run --rm -v speedmq-data:/data -v ${PWD}:/backup alpine `
  tar czf /backup/speedmq-data.tar.gz -C /data .
```
> **【Проверено (2026-10-10, локальный Docker Desktop)】** Эта команда реально выполнялась на именованном томе кластера из 3 узлов (в архиве были `meta/`, `quorum/`),
> и на её основе выполнен прогон восстановления тома одного узла (см. §4.2).

## 4. Порядок восстановления

### 4.1 Одиночный узел

```powershell
# 1) убедиться, что процесс остановлен
Get-Process -Name speedmqd -ErrorAction SilentlyContinue

# 2) убрать (или удалить) текущий data_dir, чтобы старые и новые файлы не смешались
Move-Item "C:\speedmq\data" "C:\speedmq\data.broken"

# 3) восстановить из резервной копии
Copy-Item -Recurse -Force "C:\backup\speedmq-YYYYMMDD-HHMMSS" "C:\speedmq\data"

# 4) запустить
& "C:\speedmq\speedmqd.exe" -config "C:\speedmq\configs\speedmqd.json" -log-level info
```

Ключевые моменты:
- **Обязательно сначала уберите старый каталог**, нельзя «накрывать полуоставшийся каталог файлами из резервной копии»;
- восстановленный `data_dir` должен соответствовать **той же совокупности vhost/очередей**, что и при резервном копировании (имена каталогов закодированы, переносимы между машинами);
- **не** используйте восстановление как повод изменить `vhosts`/`users` в конфигурационном файле (они действуют только при первом начальном заполнении, изменение бесполезно, см. `upgrade.md` §4.2).

### 4.2 Кластер

- Восстановление отдельного узла: восстановите `data_dir` этого узла по §4.1 и запустите его; он заново присоединится как существующий участник и догонит журнал Raft.
- Восстановление всего кластера: **сначала восстановите и запустите узлы большинства** (≥ половины голосующих участников), только тогда кластер сможет выбрать leader; затем восстановите остальные узлы.
- **【Проверено (2026-10-10, локальный кластер из 3 узлов Docker Desktop)】** Измерено «остановить n3 → очистить его том → перезаписать из резервной копии §3.3 → перезапустить»:
  n3 повторно присоединился как follower и догнал leader (`commit_index == last_applied`), число сообщений кворумной очереди и таблица участников не изменились.

## 5. Способ проверки после восстановления

Перекрёстная сверка через управляющий API и реальный клиент (рекомендуется выполнить всё):

```powershell
$pair = [Convert]::ToBase64String([Text.Encoding]::ASCII.GetBytes('guest:guest'))
$H = @{ Authorization = "Basic $pair" }

# a) общее число объектов и сообщений (очередей/обменников/привязок/пользователей; messages/ready/unacked)
Invoke-WebRequest -Uri 'http://127.0.0.1:15672/api/overview' -Headers $H -UseBasicParsing | Select-Object -ExpandProperty Content

# b) сверить по каждой очереди messages / messages_ready (можно сравнить с записями до резервного копирования)
Invoke-WebRequest -Uri 'http://127.0.0.1:15672/api/queues' -Headers $H -UseBasicParsing | Select-Object -ExpandProperty Content

# c) все ли на месте vhost / пользователи / политики
Invoke-WebRequest -Uri 'http://127.0.0.1:15672/api/vhosts' -Headers $H -UseBasicParsing | Select-Object -ExpandProperty Content
Invoke-WebRequest -Uri 'http://127.0.0.1:15672/api/users' -Headers $H -UseBasicParsing | Select-Object -ExpandProperty Content
Invoke-WebRequest -Uri 'http://127.0.0.1:15672/api/policies' -Headers $H -UseBasicParsing | Select-Object -ExpandProperty Content

# d) кластер (на одиночном узле вернёт enabled=false / mode=local / role=single)
Invoke-WebRequest -Uri 'http://127.0.0.1:15672/api/cluster' -Headers $H -UseBasicParsing | Select-Object -ExpandProperty Content
```

- **Смотрите журнал запуска**: должны появиться `已从磁盘恢复队列消息 ... messages=N` и `队列已恢复持久化消息 ... messages=N`; N должно совпадать с состоянием до резервного копирования.
- **Предупреждения в журнале**: если по какой-либо очереди ранее происходило потребление/очистка, при восстановлении могут появиться
  `恢复消息失败，已跳过 ... seq=K err="读取记录头失败: EOF"` и `恢复时清理了无存活消息的段`.
  Это остатки индекса по **уже завершённым (ack/purge) записям**, они относятся к **известному шуму в журнале и не влияют на корректность данных** (см. §7).
- **Реальный клиент**: получить сообщения из очереди и сверить количество/содержимое (см. §6 шаг (7)).

### 6.1 Сравнение: восстановление очереди без потребления/purge проходит «тише»

Чтобы понять, являются ли предупреждения выше общим явлением, был сделан отдельный **контрольный прогон**: создана новая durable-очередь `clean.q`, отправлены 3 персистентных сообщения,
**без потребления и без очистки**, процесс остановлен и перезапущен:

```
level=INFO msg=已从磁盘恢复队列消息 component=broker vhost=/ queue=clean.q messages=3 segments=1
level=INFO msg=队列已恢复持久化消息 component=broker vhost=/ queue=clean.q queue=clean.q messages=3
```
**Никаких WARN нет**. Это показывает, что WARN возникает только в сценарии, когда «в индексе остаются уже завершённые записи» (см. §7).

### 6.2 Жёсткое убийство узла во время записи (`docker kill`, 2026-10-11)

Кластер из 3 узлов (`partition_policy=pause_minority`), кворумная очередь `pwr.q` с 3 репликами; клиент использует publisher confirms, каждое сообщение имеет уникальный ID, подтверждённые ID записываются на диск для сверки.

**Раунд 1 (`fsync: os`, убийство follower n3)**: `docker kill pwr-n3` во время публикации 50 000 сообщений:

```
DONE published=50000 confirmed=50000 nacked=0 retries=0 elapsed=28.267s   # 杀后速率无可见变化
docker start pwr-n3 → 三节点 commit_index==last_applied==12，has_quorum=true
DRAIN total=50000 unique=50000 duplicates=0
confirmed_unique=50000 consumed_unique=50000 missing=0 extra=0
```

**Раунд 2 (`fsync: always`, убийство кворумного leader n1)**: `docker kill pwr-n1` во время публикации 200 000 сообщений:

```
DONE published=200000 confirmed=200000 nacked=3843 retries=3843 elapsed=2m7.494s
# nack 来自转发到已死 leader 的发布（"与节点 n1 通信失败"），客户端重投全部成功

## 7. Известные проблемы и ограничения (зарегистрированы как есть)

1. **Шум в журнале восстановления (наблюдалось в реальности)**: когда по очереди исторически происходило потребление/очистка (сообщения уже ack/purge),
   в её индексе остаются ссылки на освобождённые записи, и при восстановлении для каждой из них **по одной печатается WARN `恢复消息失败，已跳过`**,
   а также создаётся/очищается пустой `000000.seg` (в журнале `恢复时清理了无存活消息的段`).
   **Это не влияет на корректность данных** (выжившие неподтверждённые сообщения восстанавливаются корректно), но **засоряет журнал** и при больших очередях/высокой пропускной способности может залить экран.
   Рекомендация: ориентируйтесь на `已从磁盘恢复队列消息 ... messages=N`, игнорируйте эти WARN по уже завершённым записям;
   если объём журнала неприемлем, сообщите об этом сопровождающим ядра (этот документ код не меняет).
2. **Горячее резервирование небезопасно** (§2): не копируйте `data_dir` напрямую при работающем процессе.
3. **`fsync: os` не гарантирует отсутствие потерь при отключении питания**: для «confirm означает запись на диск» используйте `batch` / `always`.
4. **Пароли в открытом виде**: в `meta/state.json` пароли пользователей хранятся **в открытом виде** (на практике видно `"password":"drillpass"`) —
   поэтому файлы резервных копий **обязательно должны обрабатываться как чувствительные данные** (контроль доступа, шифрованное хранение). Подробнее см. `security-baseline.md`.
5. **【Статус проверки】** Жёсткое убийство процесса (включая убийство кворумного leader во время записи, в режимах `fsync: os`/`always`) и параллельная запись во время восстановления (продолжение публикации во время догона со скоростью около 4 000~6 000 сообщений/с, догон за 4 с через снимок, точный подсчёт, сверка missing=0) — **【Проверено (2026-10-11, локальный кластер из 3 узлов Docker Desktop)】**; `wsl --shutdown` для аварийной остановки всей VM Docker (приближает отключение питания всей машины): в единственном образце ни одно подтверждённое сообщение не потеряно, но **реальное отключение питания физической машины всё ещё не проверено**; поузловое резервное копирование/восстановление кластера и резервное копирование/восстановление именованных томов Docker — **【Проверено (2026-10-10, локальный кластер из 3 узлов Docker Desktop)】** (см. §3.2 / §3.3 / §4.2).
6. **Сопутствующие наблюдения (зарегистрированы как есть в ходе прогона 2026-10-11, неблокирующие)**: ① после жёсткого убийства кворумного leader путь пересылки публикаций у followers ещё около 76 секунд указывал на мёртвого leader (новые публикации в этот период получали nack, клиент успешно переотправлял, подтверждённые сообщения не терялись) — есть окно колебания доступности; ② при одномоментной вычитке большой очереди (438 тыс. сообщений) наблюдалась примерно 153-кратная амплификация переотправки (семантика at-least-once сохраняется, в итоге корректно обнулено); ③ во время догона большой очереди при запуске потребителя через follower эпизодически возникал `i/o timeout`; напрямую к leader работает нормально.
