# Руководство по разработке внешних процессных плагинов (sidecar) для SwiftMQ — Python

> **Для кого**: для разработчиков, пишущих внешние процессные плагины (sidecar) для SwiftMQ на Python.
> **Сначала прочитайте**: [Руководство по разработке внешних процессных плагинов (sidecar)](plugin-development.md) — там изложены ментальная модель, поля конфигурации и сводная таблица проводного протокола;
> этот документ рассказывает только о том, **как это реализовать на Python**, а также о шагах и результатах, проверенных на практике на локальной машине.
> **Пример проекта**: рабочая область `swiftmq-plugin/python/sidecar_plugin.py` (только стандартная библиотека, без сторонних зависимостей).

---

## 1. Как это выглядит в работе

```
内核进程 ──dial(tcp 本机地址)──► 你的 Python 进程（sidecar.NewServer 的等价物：一个 TCP 服务端）
   ▲                                    │
   │  握手 / 心跳 / 控制面调用（JSON）      │
   │◄───────────────────────────────────┤  反向调用 core.authenticate / session.*（JSON）
   │      客户端字节流（原始字节，不 base64） │
   └────────────────────────────────────┘
```

Три ключевых момента (легко перепутать, запомните сразу):

1. **Ваш процесс — это сервер**: он слушает локальный адрес и ждёт, пока ядро подключится (`plugins.<имя>.sidecar.address`).
2. **Внешний бизнес-порт открывает ядро**: клиенты подключаются к порту ядра, а байты проксируются вам (`protocols[].listeners`).
3. **`prefix` обязан быть непустым**: ядро по префиксу сниффинга решает, "кому передать это соединение". Пустой `prefix` означает **неучастие в сниффинге**,
   и на своём слушателе соединение вам тоже не передадут (проверено на практике: соединение сразу разрывается). Длина префикса ≤ 8 байт, ASCII.

## 2. Запуск в три шага

### Шаг первый: объявление плагина в конфигурации

`swiftmqd.json` (**реальная конфигурация — стандартный JSON, комментарии недопустимы**):

```json
{
  "plugins": {
    "py-sidecar": {
      "builtin": false,
      "enabled": true,
      "sidecar": {
        "address": "tcp://127.0.0.1:19001",
        "spawn": ["python", "/opt/swiftmq/sidecar_plugin.py", "-addr", "0.0.0.0:19001"],
        "protocols": [
          { "name": "pyecho", "prefix": "PY",
            "listeners": [{ "name": "pyecho", "addr": ":19002" }] }
        ]
      }
    }
  }
}
```

- `address` — **адрес, к которому ядро подключается к вам** (ядро — клиент, плагин — сервер).
- Пустой `spawn` = ядро только подключается, но не запускает; процессом управляете вы сами (systemd / supervisor / compose).
- `prefix` **обязан быть непустым**: первый байт от клиента должен начинаться с него (ядро по префиксу сниффинга решает, кому передать соединение).
- `listeners` — внешние порты, открываемые ядром (клиенты подключаются к ядру, а не к вам).
- При развёртывании между контейнерами в `address` используйте **имя сервиса** (например, `tcp://py-sidecar:19001`), а плагин должен слушать `0.0.0.0`.

### Шаг второй: запуск

```bash
# 由内核 spawn 时不用手起；手动调试：
python sidecar_plugin.py -addr 0.0.0.0:19001 -name py-sidecar -session-demo
```

### Шаг третий: проверка

```bash
curl -u guest:guest http://127.0.0.1:15672/api/plugins | python -m json.tool   # state 应为 enabled
printf 'PYhello\n' | nc 127.0.0.1 19002                                       # 应回显 PYhello
```

## 3. Ключевые моменты реализации

### 3.1 Разбиение на кадры (единственный байтовый уровень, который нужно написать правильно самому)

```
+--------+--------+------------------+
| len    | kind   | payload          |
| u32 BE | u8     | (len-1) 字节      |
+--------+--------+------------------+
len = 1 + len(payload)（长度字段**包含** kind 字节）；单帧上限 16 MiB。
```

Полезная нагрузка кадра данных = `4-байтовый big-endian номер потока + сырые байты`; полезная нагрузка плоскости управления — JSON.

```python
def read_frame(sock):
    head = read_exact(sock, 5)
    if len(head) < 5:
        return None
    (length,) = struct.unpack(">I", head[:4])
    payload = read_exact(sock, length - 1)
    return head[4], payload          # (kind, payload)
```

### 3.2 Рукопожатие и heartbeat

После подключения ядро **первым отправляет Hello**, вы обязаны ответить одним кадром `HelloAck`; ядро проверит
`name == имени плагина в конфигурации` и `api_version == APIVersion ядра` (сейчас `v1`).
Затем ядро каждые 2 с отправляет `Ping`, а вам достаточно отвечать `Pong` (если не отвечать, соединение будет признано мёртвым).

### 3.3 Логические потоки

Приходит `kindOpen` → **сначала отвечаем `OpenAck`**, затем начинаем обслуживание; приходит `kindData` → пишем обратно
`kindData` как есть (или после разбора по вашему протоколу); обработка завершена → отправляем `kindClose`. Один поток = одно клиентское соединение.

### 3.4 Обратные вызовы и семантический мост ядра

Вызовы плагин → ядро идут через `kindCall` с `"reverse": true`, а ядро отвечает `kindReply` по тому же соединению.
**Порядок важен**:

```
core.authenticate → session.open → session.declare_queue / publish / consume / …
```

`core.authenticate` **опускать нельзя**: у операционной поверхности ядра для соединения до аутентификации нет личности, и прямой `session.open` будет отклонён
(`ACCESS_REFUSED - access to vhost '/' refused for user ''`). Параметры — это разобранный из вашего протокола ответ SASL:

```python
plain = b"\x00" + user.encode() + b"\x00" + password.encode()
ident = call("core.authenticate", {
    "stream": stream_id, "mechanism": "PLAIN",
    "response": base64.b64encode(plain).decode(),   # 字节在 JSON 里是 base64
})
# 拿到的会话与进程内协议插件完全同一套语义
call("session.open", {"stream": stream_id, "vhost": "/"})
q = call("session.declare_queue", {"stream": stream_id, "exclusive": True, "auto_delete": True})
call("session.publish", {"stream": stream_id, "routing_key": q["name"],
                         "message": {"body": base64.b64encode(b"hi").decode()}})
call("session.consume", {"stream": stream_id, "queue": q["name"], "prefetch": 32})
```

Доставки потребления **приходят обратно от ядра** прямым вызовом (`kindCall`, `method = "session.deliver"`); после обработки рассчитайтесь через
`session.settle` (`ack` / `requeue` / `reject`; номер доставки глобально уникален, номер потока не нужен).

### 3.5 Модель параллелизма (версия для Python)

| Роль | Нить |
| --- | --- |
| Цикл чтения кадров | По одной на каждое соединение с ядром |
| Обработка потока | По одной на каждый поток (поэтому несколько клиентских соединений могут работать параллельно) |
| Обработка прямого вызова | По одной на каждый вызов |

**Важно**: в цикле чтения **нельзя** синхронно ждать ответа обратного вызова (это приведёт к взаимоблокировке) — прямой вызов (`session.deliver`)
нужно выносить в отдельную нить, потому что в процессе обработки он может сам инициировать `session.settle`. Записи кадров должны быть сериализованы под блокировкой.

## 4. Разбор кода (пример проекта)

`swiftmq-plugin/python/sidecar_plugin.py` — около 320 строк, ключевые функции:

| Место | Назначение |
| --- | --- |
| `read_frame` / `Conn.send` | Чтение и запись кадров (префикс длины + kind) |
| `Conn.call` | Обратный вызов: номер → отправка → ожидание ответа (сопоставление по `reverse=true` и `id`) |
| `Conn.serve` | Цикл чтения и диспетчеризация кадров |
| `Conn._handle_hello` | Проверка имени плагина/версии API и ответ HelloAck |
| `Conn._handle_open` / `_serve_stream` / `_echo` | Жизненный цикл потока и эхо |
| `Conn._dispatch` | Обработка прямых вызовов: `session.deliver` (включая settle), `stats` |
| `Conn._session_demo` | Аутентификация + объявление очереди + публикация + потребление |

Окружение: Windows + Python 3.12; ядро работает в Docker (`swiftmq:1.1.01`), плагин — на хост-машине,
ядро подключается к нему по `tcp://host.docker.internal:19001`.

```

session 演示完成 queue=amq.gen-9e5d0d695639bad12ce919
```

## 6. Особенности, специфичные для Python

- **Не используйте `time.sleep` для ожидания heartbeat**: цикл чтения блокирующий, соединение поддерживается за счёт `Ping` от ядра;
  если задали тайм-аут чтения для socket, не забудьте трактовать тайм-аут как "конец соединения" (при `kill -9` ядра socket может закрыться не сразу).
- **`json.dumps` по умолчанию добавляет пробелы**: в примере `separators=(",", ":")` используется только ради читаемости журналов, сам протокол этого не требует.
- **Байты — это base64**: `message.body` и `core.authenticate.response` в JSON являются строками base64,
  не забывайте про `base64.b64encode/decode`.
- **Записям кадров нужна блокировка**: heartbeat, ответы и блоки данных приходят из разных нитей, а перемежающаяся запись испортит всё соединение (в примере используется `threading.Lock`).
- Можно использовать и `asyncio`, но нужно обеспечить "последовательную запись + неблокирующий цикл чтения"; подход тот же, что и в версии с нитями.

## 7. Дополнительно

- Если хотите дать плагину собственный интерфейс управления: добавьте в конфигурацию `console_url`, и на странице "управление плагинами" в панели управления появится прямая ссылка
  (см. §5.8 основного документа).
- Чтобы сделать плагин отдельным сервисом под управлением systemd / K8s: `spawn: []` + `restart: "never"`, запуск извне.
- Для сосуществования нескольких протоколов: дайте нескольким плагинам разные `prefix` на одном слушателе или откройте каждому выделенный порт.
